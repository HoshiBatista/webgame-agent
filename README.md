# GameForge — генератор мини-игр

Короткий запрос → HTML5-игра → проверка в изолированном браузере → сохранённая версия,
доработки, публикация и ремикс. Стек: Django/DRF, PostgreSQL 18, Celery/Redis,
React/TypeScript/SCSS. Игровую механику генерирует модель; каталог готовых игр её не заменяет.

**Основной путь для команды — локальный Docker Compose и существующее HTTPS-реле.**
GPU на компьютере разработчика и VPN для этого пути не нужны. GameForge обращается
к очереди на облачном сервере; исполнитель рядом с vLLM получает задания и возвращает
сохранённые ответы. Установка реле и GPU-исполнителя не входит в запуск GameForge.

Подробная пошаговая инструкция: **[локальный запуск для команды](docs/team-local-setup.ru.md)**.
Готовая конфигурация без секретов: [.env.team.example](.env.team.example).

## Фактический статус

Реализован ограниченный цикл: компактная генерация → проверка синтаксиса → проверка
управления и игровых условий → при необходимости до трёх исправлений. Синтаксическая
ошибка останавливает игровые сценарии; следующий запрос получает основные причины,
а полный отчёт сохраняется. Codex, vLLM и relay используют этот общий цикл.

Это **этапы проверки и исправления**, а не полная декомпозиция игры на независимо
генерируемые модули. Последний живой прогон «Змейки» не дал проверенную рабочую игру:
доставка ответов работала, но модельные правки не устранили проблемы. Успешные тесты
инфраструктуры и протокола не доказывают качество генерации через Qwen. Сохранённый
неудачный кандидат не объявляется готовым. Подробности: [отчёт](docs/verification.md),
[модель процесса](docs/game-creation-model.ru.md), [история подключения](docs/relay-deployment.md).

`GAMEFORGE_MAX_REPAIR_ATTEMPTS=3` означает один основной вызов и максимум три исправления;
допустимы 2 или 3. Лимит фиксируется в каждом новом запуске и не сбрасывается после
перезапуска. Старые задания сохраняют прежний предел. Новая модельная попытка, получение
уже готового ответа и повторная проверка — разные операции, которые учитываются отдельно.

## Получение этой версии

Текущая поставка передаётся команде как **ZIP исходников с каталогом `GameForge/`**.
Распакуйте его и откройте терминал в этом каталоге: рядом должны находиться `manage.py`,
`compose.yaml` и `README.md`. Команды ниже выполняются именно оттуда.

ZIP создан из зафиксированной версии Git и не содержит `.git`, личный `.env`, `.data`,
токены, пользовательскую БД или вход Codex. Новые локальные коммиты пока не отправлены
на GitHub: обычный clone ветки `mini-games` до отдельного push не даст этот снимок.
После публикации коммита можно использовать Git и сверить полученный commit ID с поставкой.

Архив переносит только исходники. Первичная сборка всё ещё требует интернета для Docker
images и зависимостей Python/npm; работа через relay требует доступа к облачному HTTPS API.

## Docker Compose: рекомендуемый запуск

Нужны работающий Docker Engine/Desktop с Docker Compose, интернет, свободные локальные
порты **8080 и 8081** и персональный **client-токен реле**, выданный администратором.
Python, Node, PostgreSQL и Redis устанавливаются внутри контейнеров. Не запускайте второй
Compose-проект под тем же именем одновременно.

### 1. Подготовьте приватную конфигурацию

Создайте `.env`, только если его ещё нет:

```sh
(
  set -e
  umask 077
  if [ -e .env ]; then
    echo '.env уже существует: сравните его с шаблоном, не перезаписывайте.'
    exit 1
  fi
  cp .env.team.example .env
)
```

Откройте `.env` локальным редактором и заполните:

- `DJANGO_SECRET_KEY` — новый случайный секрет;
- `DJANGO_SUPERUSER_USERNAME` и `DJANGO_SUPERUSER_PASSWORD` — первоначальный вход в GameForge,
  пароль не короче 10 символов;
- `POSTGRES_PASSWORD` — отдельный пароль контейнерной БД, удобно случайный hex:
  Compose вставляет его в URL подключения;
- `GAMEFORGE_RELAY_API_KEY` — ваш client-токен очереди.

Новые случайные значения можно получить командой `openssl rand -hex 32`: каждый запуск
даёт отдельное значение. Токен реле выдаётся администратором и этим способом не создаётся.
Не добавляйте `.env` в Git и не передавайте его в общий чат. Не используйте для реле
worker-токен GPU, ключ скачивания установщика или старый `VLLM_API_KEY`.

Для текущего стенда в шаблоне должны остаться следующие настройки:

```dotenv
CONTAINER_PROVIDER=relay
CONTAINER_MODEL=qwen38
GAMEFORGE_RELAY_URL=https://129.101.114.59
GAMEFORGE_VLLM_JSON_MODE=json_schema
GAMEFORGE_VLLM_CONTEXT_CHECK=server
GAMEFORGE_MAX_REPAIR_ATTEMPTS=3
GAMEFORGE_PRICES_JSON={"qwen38":{"input":0,"cached":0,"output":0,"context_window":32768,"max_output_tokens":16384}}
```

`CONTAINER_PROVIDER`/`CONTAINER_MODEL` выбирают провайдера в Compose;
`GAMEFORGE_PROVIDER`/`GAMEFORGE_MODEL` используются нативным запуском.
URL реле — **origin без `/v1`**: адаптер сам использует `/bridge/v1/…`.
Прежний синхронный `/v1/chat/completions` не является текущим командным маршрутом.
Нулевые цены отражают отсутствие оплаты за токены собственного vLLM; нагрузка и usage
всё равно учитываются. Размеры контекста/ответа относятся к этому стенду, не ко всем моделям.

В Compose токен передаётся значением `GAMEFORGE_RELAY_API_KEY` только worker.
`GAMEFORGE_RELAY_API_KEY_FILE` доступен нативному запуску, но не подключён в текущем Compose.
Не помещайте секреты в `VITE_*`: эти значения могут оказаться в браузерной сборке.

### 2. Соберите и запустите

```sh
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps -a
```

Используйте именно `config --quiet`: обычный вывод конфигурации может раскрыть подставленные
секреты. Сервис `init` запускает миграции, затем `bootstrap`; его `Exited (0)` — нормальное
завершение. После него стартуют app, preview, worker и beat. Повторный bootstrap не меняет
пароль существующей учётной записи. Новых пользователей создаёт оператор; открытой регистрации нет.

Откройте **http://127.0.0.1:8080/** и войдите данными `DJANGO_SUPERUSER_*`.
Игровой origin — **http://localhost:8081/**. Его корень возвращает 404: игра открывается
по ссылке `/preview/…`, которую создаёт приложение. Разные hostname отделяют игровые
страницы от cookie приложения; не подменяйте адрес приложения на `localhost`.

Compose по умолчанию, без `CONTAINER_PROVIDER=relay`, выбирает `fake`: это тестовая сцена,
не настоящая модель. В `/api/session/` поле `capabilities.provider` должно быть `relay`,
а модель — `qwen38`. Параметр `GAMEFORGE_PROVIDER_CONCURRENCY` сейчас не проброшен в Compose:
действует значение приложения по умолчанию — один одновременно обрабатываемый запуск.

### 3. Проверьте готовность и логи

```sh
curl --fail --show-error http://127.0.0.1:8080/api/health/
curl --fail --show-error http://127.0.0.1:8080/api/session/
docker compose logs --tail=80 init app preview worker beat validator edge
```

Health должен вернуть `{"status":"ok"}`. Это проверка доступности Django, **не пробная
генерация** и не доказательство доступности GPU-исполнителя. Проверки TLS реле и среды
браузера без модельного вызова приведены в [командной инструкции](docs/team-local-setup.ru.md).
Для наблюдения за обработкой задания:

```sh
docker compose logs -f --tail=80 worker beat validator
```

`Ctrl+C` завершает просмотр логов, контейнеры продолжают работу. Для безопасной диагностики
последнего вызова без текста запроса, ответа и токенов:

```sh
docker compose exec worker python manage.py diagnose_invocation
```

## Нативный запуск на macOS/Linux

Этот вариант нужен для разработки Python/React или локального провайдера Codex.
Нужны **Python 3.12**, **Node 22+**, PostgreSQL **18+**, Redis **7** и Docker для изолированного
валидатора. Сервер PostgreSQL должен быть запущен, а ваш пользователь — иметь доступ к
отдельной БД проекта. Если эти службы ещё не настроены, используйте описанный выше
Compose: командная инструкция рассчитана на него и не требует установки служб на хост.

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.lock
npm ci --prefix web
npm run build --prefix web
```

Подготовьте `.env` по защищённой процедуре выше. Для нативного relay-стенда дополнительно
проверьте значения:

```dotenv
DATABASE_URL=postgresql:///gameforge_mini
REDIS_URL=redis://127.0.0.1:56379/0
GAMEFORGE_PROVIDER=relay
GAMEFORGE_MODEL=qwen38
GAMEFORGE_APP_ORIGIN=http://127.0.0.1:8000
GAMEFORGE_PREVIEW_ORIGIN=http://localhost:8001
DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost
CSRF_TRUSTED_ORIGINS=http://127.0.0.1:8000,http://localhost:8000
```

`postgresql:///gameforge_mini` использует локальный PostgreSQL и роль текущего пользователя.
Если БД требует отдельные логин, пароль, host или port, укажите их в `DATABASE_URL`
с корректным URL-кодированием. Создайте базу один раз, если она ещё не существует:

```sh
createdb gameforge_mini
```

Если Redis проекта ещё не установлен и контейнера `gf-mini-redis` нет:

```sh
docker run -d --name gf-mini-redis -p 127.0.0.1:56379:6379 \
  -v gf-mini-redis-data:/data \
  redis:7-alpine redis-server --appendonly yes
```

Если такой контейнер уже есть, сначала проверьте его через `docker ps -a`; остановленный
подходящий контейнер запускается `docker start gf-mini-redis`. Не удаляйте чужой контейнер
или volume ради освобождения имени/порта. При другом Redis исправьте URL в `.env`.

Запустите валидатор и процессы из обычного терминала. Для всех команд управления ниже
используется одинаковая временная зона: она влияет на проверку времени запуска PID.
Можно выбрать свою зону, но не менять её между start/status/stop.

```sh
sh scripts/validator-start.sh
TZ=Europe/Moscow .venv/bin/python scripts/dev.py start
TZ=Europe/Moscow .venv/bin/python scripts/dev.py status
curl --fail --show-error http://127.0.0.1:8000/api/health/
```

`start` сам выполняет миграции и bootstrap, затем запускает app, preview, Celery worker
и beat. Приложение — **http://127.0.0.1:8000/**, preview — **http://localhost:8001/**.
Корень preview также отвечает 404. Нативная и Compose-установки используют разные
БД и порты: их чаты не появляются друг у друга автоматически.

Логи находятся в `.data/app.log`, `preview.log`, `worker.log`, `beat.log`;
запись принадлежащих менеджеру процессов — `.data/local-processes.json`.

```sh
tail -f .data/app.log .data/worker.log .data/beat.log
.venv/bin/python manage.py diagnose_invocation
```

### Локальный Codex остаётся доступен

В нативном `.env` выберите:

```dotenv
GAMEFORGE_PROVIDER=codex
GAMEFORGE_MODEL=gpt-6-luna
```

Нужен уже установленный Codex CLI с существующим локальным входом доверенного оператора.
Текущий адаптер проверен строго для **`codex-cli 0.163.0-alpha.10.2`**; другая версия
отклоняется до модельного вызова. Это зафиксированный контракт изоляции инструментов,
а не рекомендация устанавливать произвольную последнюю версию. Модели выбираются из
доступного локального каталога; default — `gpt-6-luna`, effort low.

Не копируйте авторизацию Codex в архив, репозиторий, Compose, CI или публичный сервис.
Подробности профиля: [адаптер генерации](generation/README.md). После смены провайдера
нужен полный перезапуск нативных процессов; настройки не переключаются отдельной кнопкой
для каждого сообщения. Прямой `vllm` также сохранён, но является отдельным режимом:
его URL с `/v1` и ключ описаны в той же документации, а не в командном relay-шаблоне.

## Остановка, перезапуск и обновление

Перед остановкой worker или обновлением дождитесь завершения активных заданий либо
явно отмените их в интерфейсе. Сохранение истории не делает безопасным произвольное
прерывание запроса к провайдеру. Не удаляйте Invocation, очередь или неизвестный расход
для «разблокировки» повторной генерации.

Для Compose:

```sh
docker compose stop
docker compose up -d
```

После изменения `.env` используйте `docker compose up -d`, чтобы Compose применил
изменившуюся конфигурацию контейнеров; один `restart` новые environment не подставляет.
После перезапуска Docker также выполните `up -d`: у edge и validator сейчас нет
автоматической restart policy. БД и Redis живут в именованных volumes.
`docker compose down` сохраняет volumes; **не добавляйте `--volumes`/`-v`**, если данные нужны.
Не используйте общие `docker system prune`/`volume prune` для обслуживания проекта.

Нативные процессы:

```sh
TZ=Europe/Moscow .venv/bin/python scripts/dev.py stop
TZ=Europe/Moscow .venv/bin/python scripts/dev.py status
TZ=Europe/Moscow .venv/bin/python scripts/dev.py start
```

Если менеджер сообщает, что worker ещё завершает работу, дождитесь остановки и повторите
status/stop. Не удаляйте PID-файл вручную при живых процессах: это допускает второй worker.
Redis и валидатор отдельные; `dev.py stop` их не останавливает. При необходимости и после
остановки заданий: `docker stop gf-mini-redis gf-mini-validator`.

Перед обновлением сделайте резервную копию PostgreSQL и приватной конфигурации. Например,
для Compose из текущей установки:

```sh
(
  set -e
  umask 077
  mkdir -p .data/backups
  stamp=$(date -u +%Y%m%dT%H%M%SZ)
  docker compose exec -T db pg_dump -U gameforge -d gameforge -Fc \
    > ".data/backups/gameforge-$stamp.dump"
  cp -p .env ".data/backups/env-$stamp"
)
```

Для поставки ZIP получите новый архив и распакуйте в другой каталог, перенесите свой
приватный `.env`, сравните его с новым шаблоном. Старую папку и backup сохраните до проверки.
Используйте **то же имя Compose-проекта**: в `compose.yaml` задано `gameforge-mini`;
если вы задавали `COMPOSE_PROJECT_NAME` или `-p`, сохраните прежнее значение, иначе получите
новые пустые volumes. Не запускайте старую и новую копии одновременно. Пароль существующей
PostgreSQL-БД не меняется от редактирования `POSTGRES_PASSWORD` в `.env`.

После остановки старого приложения в новой папке:

```sh
docker compose config --quiet
docker compose build
docker compose run --rm init
docker compose up -d
docker compose ps -a
curl --fail --show-error http://127.0.0.1:8080/api/health/
```

Для Git-копии после опубликованного обновления сначала сохраните свои изменения и получите
согласованную ревизию; остальные действия те же. Для нативной установки после обновления
кода повторите установку `requirements-dev.lock`, `npm ci`/build, пересоберите валидатор
через `scripts/validator-start.sh` и запустите `dev.py start`: миграции применятся при запуске.
Код app/worker и версия валидатора должны совпадать. При переносе в новый путь нативного
проекта пересоздайте `.venv` и проверьте абсолютный путь файла relay-токена, если он используется.

## Если запуск или генерация не работают

| Симптом | Что проверить |
| --- | --- |
| Ошибка `.env`, пустой secret или bootstrap | Заполнены ли секрет и `DJANGO_SUPERUSER_*`; `docker compose logs init`. Пароль существующего пользователя bootstrap не меняет. |
| Порты 8080/8081 или 8000/8001 заняты | Остановите свою прежнюю установку либо согласуйте другие порты вместе с origins/CSRF. Не завершайте неизвестный процесс. |
| Вместо модели fixture/fake | `CONTAINER_PROVIDER=relay` для Compose, `GAMEFORGE_PROVIDER=relay` для нативного режима; после изменения пересоздать/перезапустить процессы. |
| 401/403 от реле, «ожидание администратора» | Нужен действующий client-токен очереди и origin без `/v1`; `LLM_API_KEY` не заменяет relay-токен. |
| Долгое «ожидание модели» | Проверьте worker/beat и `diagnose_invocation`; очередь ограничена. Повторное чтение состояния не запускает новую генерацию. |
| `validator_unavailable` или устаревшая среда | Пересоберите именно валидатор текущей версии; проверьте его логи. Ошибка среды не является ошибкой игрового кода. |
| `invalid_schema`, `javascript_syntax`, неуспешные игровые проверки | Это отказ обработки/проверки кандидата. Читайте сохранённый отчёт; доступность API сама по себе не означает готовность игры. |
| `unknown` | Результат внешнего вызова неизвестен. Не отправляйте его повторно вслепую; нужны сохранённый receipt или сверка оператором. |
| Preview `/` отвечает 404 | Ожидаемо. Открывайте игру через чат и выданную ссылку `/preview/…`. |
| «Frontend is not built yet» | Нативно выполните `npm ci --prefix web` и `npm run build --prefix web`; в Compose пересоберите image. |
| База недоступна после смены пароля | `.env` не обновляет пароль роли в существующем PostgreSQL volume; не удаляйте volume, восстановите согласованные credentials. |

Запрос сохраняется в PostgreSQL до выполнения. Закрытие вкладки или обрыв связи пользователя
не отменяют его: после восстановления связи откройте тот же чат. Явная кнопка отмены,
напротив, записывает отмену задания. Relay хранит доставку результата; авария исполнителя
во время inference всё ещё может дать неизвестный исход. Подробнее:
[диагностика LLM](docs/llm-diagnostics.md), [протокол relay](docs/relay-deployment.md).

## Восстановление сохранённого ответа без генерации

Для завершённого `invalid_schema` оператор может использовать Invocation UUID:

```sh
.venv/bin/python manage.py recover_saved_response INVOCATION_UUID
.venv/bin/python manage.py recover_saved_response INVOCATION_UUID --apply
```

В Compose замените `.venv/bin/python` на `docker compose exec worker python`.
Первая команда только проверяет сохранённый JSON и упаковку. Вторая создаёт отдельный
запуск с кандидатом и обычной браузерной проверкой, которому постоянно запрещены вызовы
модели, в том числе после перезапуска. Повтор команды возвращает тот же запуск. Исходный
ответ, ошибка и расход не перезаписываются; неподходящий статус или изменившаяся база
блокируют восстановление. Ошибка игры остаётся ошибкой, не превращается в успешный статус.

`manage.py reconcile_invocation --help` предназначена для сверки неизвестного расхода
по независимым данным провайдера и не вызывает модель. Не подставляйте выдуманный нулевой
usage. `GAMEFORGE_BUDGET_USD` задаёт начальный бюджет новой БД; изменение `.env` не
обнуляет существующий журнал, резерв или неизвестные обязательства. Для Codex стоимость
в журнале — API-эквивалент, а не банковское списание за подписку.

## Проверки и измерения

```sh
.venv/bin/ruff check gameforge studio generation validation scripts tests
.venv/bin/mypy generation validation --ignore-missing-imports
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/pytest -m 'not browser and not live'
VALIDATOR_CONTAINER=gf-mini-validator-tests sh scripts/validator-start.sh
VALIDATOR_CONTAINER=gf-mini-validator-tests .venv/bin/pytest tests/test_validation.py -m browser
npm run lint --prefix web
npm test --prefix web
npm run build --prefix web
```

Браузерные тесты используют отдельный `gf-mini-validator-tests`, чтобы не конкурировать
с текущей генерацией за память одного браузерного контейнера; backend-тесты — PostgreSQL с правом
создать тестовую БД. CI выполняет эти проверки, сборку контейнеров и не делает платных вызовов.
Ручной пилот вызывает настоящую модель. Запускайте его только при согласованной нагрузке
и бюджете; пример ниже рассчитан на нативный стенд с relay/qwen38. Для Codex явно
выберите доступную модель через --model:

```sh
.venv/bin/python scripts/live_eval.py --model qwen38 --output .data/pilot.json --prefix my-unique-pilot
```

Скрипт сохраняет ID каждой операции до ожидания, продолжает наблюдение после перезапуска,
не повторяет ошибку скрыто и не засчитывает ручное подтверждение как автоматический успех.
Пять разных запросов и две правки на успешную игру — пилот, недостаточный для устойчивого p95.
Прежние цели времени были внутренними ориентирами и не являются обещанием для Qwen.
Полное время включает очередь, все ответы модели, исправления и проверки; полезный
ответ не обрывается по целевому времени. Публикуйте измерения вместе с неудачами.
