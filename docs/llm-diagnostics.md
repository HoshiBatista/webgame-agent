# Диагностика обрывов LLM

Расширение от 22 октября 2026 года. Архитектура, модель и тайм-ауты не меняются.
GPU-сервер и его контейнеры не администрируются этими средствами.

## GameForge

Для каждого прямого вызова vLLM UUID записи Invocation используется как `trace_id`
(32 шестнадцатеричных символа) и сохраняется в БД **до** отправки. HTTP-заголовки
`X-GameForge-Trace-ID` и `X-Request-ID` несут этот ID; Caddy возвращает независимый
`X-Proxy-Request-ID`. Это корреляция, не ключ идемпотентности и не разрешение повтора.

Журнал `generation.transport` записывает начало, заголовки, прогресс раз в 10 секунд
и завершение. Сохраняются UTC, длительность, время первого/последнего байта, пауза
без данных, объём запроса/ответа, количество SSE-сообщений, `[DONE]`, HTTP-статус,
фазы DNS/TCP/TLS/HTTP из HTTPX и ограниченная цепочка типов исключений с errno.
Встроенный TCP trace не выделяет DNS отдельно от `connect_tcp`.
Промпты, код, токены, URL, HTTP-заголовки и тексты исключений не записываются.
Подробный итог также хранится в приватном `Invocation.provider_metadata.transport`.

По умолчанию JSONL идёт в stderr worker. Для локальной установки задан
`GAMEFORGE_TRANSPORT_LOG` с путём `.data/llm-transport.jsonl`: 5 МиБ + 5 архивов.
Для Docker можно оставить stderr и использовать ротацию журналов контейнера.

Безопасная сводка последнего вызова, без нового обращения к модели:

```sh
.venv/bin/python manage.py diagnose_invocation
# Либо конкретный Invocation UUID (это не Run UUID):
.venv/bin/python manage.py diagnose_invocation INVOCATION_UUID
```

`ReadTimeout` означает отсутствие новых сетевых данных дольше настроенного read timeout,
а не превышение общего времени генерации. `RemoteProtocolError` — нарушение/обрыв HTTP;
`provider_protocol_error` — повреждённое JSON-сообщение API. EOF без `[DONE]`, отмена
и неверный конечный JSON различаются. Ни одно из этих наблюдений само по себе не доказывает
вину VPN. Автоматического повторного inference нет.

## Облачный VPS

Файлы установки находятся в `deploy/diagnostics/`. `install_caddy_logging.py` рассчитан
на существующую установку `/etc/llm-proxy` с менеджером `llm-proxy-token`. Он проверяет
соответствие действующей конфигурации шаблону, отсутствие активного upstream-соединения,
сохраняет резервный шаблон и применяет проверенное изменение с откатом при ошибке.
Все существующие токены, маршруты и тайм-ауты сохраняются. Глобальный debug выключен.

- `/var/log/caddy/llm-access.jsonl`: trace_id, proxy_request_id, метод/протокол,
  длительность, объём ответа, статус, endpoint и задержки upstream. Заголовки, query string
  и тело запроса/ответа исключены. Ротация: 5 МиБ, до 6 архивов, 7 дней для архивов.
- `journalctl -u caddy`: ошибки reverse proxy; сопоставлять со временем access-записи.
  HTTP 200 сам по себе не означает полного ответа: заголовки могли уйти до обрыва SSE.
- `/var/log/llm-diagnostics/network.jsonl`: локальные TCP-сокеты к порту 8000 GPU и
  клиентам HTTPS, retransmits/RTT/очереди из `ss`, счётчики/handshake WireGuard,
  RAM/нагрузка и PID/restarts Caddy. Период 10 секунд, суммарно до 20 МиБ с архивами.

Сборщик `llm-network-diagnostics.service` **пассивный**: не выполняет curl, ping, SSH
или другие подключения к GPU. Процесс ограничен 64 МиБ RAM и 5% CPU. Логи приватные.
`wg` требует CAP_NET_ADMIN для чтения; IP-сокеты для процесса запрещены systemd,
разрешены только локальные UNIX/NETLINK. Управление:

```sh
sudo systemctl status llm-network-diagnostics
sudo systemctl stop llm-network-diagnostics
sudo systemctl start llm-network-diagnostics
```

## Разбор следующего сбоя

1. Получить Invocation/trace_id и UTC интервал через `diagnose_invocation`.
2. Найти тот же trace_id в access-журнале VPS. Проверить длительность/размер,
   ошибки Caddy и сетевые снимки за интервал, включая 30 секунд до/после.
3. Сравнить время последнего байта в приложении, TCP retransmits/очереди на обеих
   сторонах прокси и состояние VPN. Старый handshake сам по себе не доказывает обрыв.
4. Если сеть выглядит исправной, а upstream перестал отдавать данные, нужен журнал
   `qwen38` за тот же интервал. Его получает владелец GPU-сервера; эта диагностика
   не даёт агенту права подключаться к серверу или управлять соседними контейнерами.

Для старого вызова 21 октября 13:09:43–13:13:37 UTC исходный тип ошибки не был записан;
новые журналы не восстанавливают утраченную информацию. Проверки с заглушкой доказывают
различение ошибок, но не устанавливают причину того конкретного обрыва.
