# Улучшение генерации Lite и Pro: пересмотренный план

Статус 27.10: P0–P3 и P4–P5 реализованы локально с регрессиями и ревью.
[Отчёт P4–P5 / ревью B](generation-improvement-p4-p5-implementation.ru.md).
P6–P9 остаются следующими этапами; эксперимент Lite по умолчанию выключен.

Дата: 27.10.2026. Исходная точка: `mini-games@815f2b2af18059d8dcb8780ced405f7f0ea98f3c`.
Статус: **P0–P3 реализованы локально**, P4–P9 остаются планом.
Фактическая приёмка и ограничения: [отчёт первой поставки](generation-improvement-implementation.ru.md).
Код приложения и серверы при подготовке плана не менялись; модельных вызовов нет.

## 1. Решение

Сохранить универсальную генерацию игровых правил и разные стратегии Lite/Pro.
Приложение должно брать на себя техническую среду, понятный протокол проверки,
сохранение результата и управление ограниченными исправлениями. Модель придумывает
и реализует игру; проверяющий код не подменяет её каталогом заранее написанных механик.

Нужны три последовательные поставки:

1. **Достоверное завершение:** исправить семантику проверок, различать ошибки игры,
   сценария и среды, восстановить доступное пользователю подтверждение результата.
2. **Устойчивый Lite:** уменьшить объём технической работы модели, исправить compact
   runtime и испытать отдельное создание сценариев для уже сохранённого кода.
3. **Качественный Pro:** сохранить свободные HTML/CSS/JS, дать необязательные проверенные
   средства движения и добавить ограниченную обратную связь по реальным кадрам.

Содержательность игры оценивается отдельно от её запуска и красоты. План, число
механик, успешный JSON и слово `passed` не доказывают ни интерес, ни работоспособность.

## 2. Что пересмотрено и что действительно известно

решения игрока → различающиеся стратегии Lite/Pro. Основное направление сохраняется,
но порядок уточняется: пользовательское завершение и ложные результаты проверок
предшествуют визуальной полировке. Для Lite нужен отдельный эксперимент с формой задачи.

Не переносить FastAPI, новую систему очередей, обязательный Phaser, asset pipeline,
общую схему жанров и многоролевую цепочку. Эти изменения не объясняют текущие дефекты.
Наличие ADR не означает готовую реализацию: ML-MVP по-прежнему делает `specify`, затем
выдаёт полный HTML, в том числе при ремонте; заявленный файловый harness не подтверждён
его кодом и сопоставимым живым тестом.

Особенно не переносить `force_win`/`force_lose` из предложенного test bridge как
доказательство прохождения. Такие команды могут проверять отдельный обработчик в
fixture, но не достижимость исхода реальным игроком. Обязательные `score/lives/phase`
также не нужны всем играм.

## 4. Уроки реальных harness

- **SWE-agent:** удобство ограниченных операций и ранняя проверка изменений влияют
  на результат. Здесь это короткие схемы операций и точная диагностика до дорогого
  браузерного прогона. Его редактор и shell целиком не переносим.
  [ACI](https://github.com/SWE-agent/SWE-agent/blob/main/docs/background/aci.md).
- **Aider:** разделение решения задачи и оформления правки может помогать, но требует
  дополнительного запроса. Для Lite раздельные code/scenarios — проверяемая гипотеза,
  а не обещание, что любая декомпозиция улучшает результат.
  [Architect/editor](https://aider.chat/docs/usage/modes.html#architect-mode-and-the-editor-model).
- **Anthropic:** полезны фиксированные критерии качества и оценка работающего
  приложения. Их эксперименты с визуальным улучшением использовали 5–15 итераций
  и могли длиться до четырёх часов. Для наших коротких игр проверяем максимум один
  цикл review → patch; перенос результата исследования на такой бюджет не доказан.
  [Исследование](https://www.anthropic.com/research/harness-design-long-running-apps).
- **Phaser:** переход числового свойства во времени — общая техническая операция,
  пригодная для разных игр. Это обоснование небольшого API движения, а не обязательной
  миграции движка. [Tweens](https://docs.phaser.io/phaser/concepts/tweens).

Дальнейшие архитектурные решения — наши выводы из кода и пилотов, а не результаты
перечисленных внешних исследований на нашей модели 27B.

## 5. Целевая граница и контракты

### 5.1 Замысел, требования и сценарии

Сохранить три разных сущности:

1. `GameBrief`: идея, действия игрока, развитие ситуации, оформление; создаёт модель.
2. `RequirementManifest`: ID, текст условия, происхождение, важность, способ проверки.
3. `CheckProgram`: исполнимый план конкретной проверки, ссылающийся на requirement ID.

Происхождение: `user_explicit`, `model_design`, `platform`, `operator_test`.
Для `user_explicit` хранить точную цитату/диапазон из исходного запроса. Проверка
диапазона подтверждает происхождение текста, но не правильность его интерпретации.
Извлечённое моделью условие всё равно может быть ошибочным. Не поднимать его в
доверенный контракт только из-за поля `origin` в её ответе.

Не требовать универсальной схемы игровых правил. ID связывает утверждение и
свидетельство; код механики остаётся обычным JavaScript. Неизмеримое/непокрытое
условие помечается явно. «Стало красивее» не компилируется в `score > 0`.

### 5.2 Компиляция сценария

Один компилятор обслуживает full/compact, create/checks_create/check_repair/recheck,
native и Docker. Он возвращает либо ограниченный `CheckProgram`, либо структурную
ошибку с `check_id`, полем и допустимыми вариантами. Проверки формы, типов и
стоимости не должны независимо реализовываться в нескольких местах.

Внутренний формат отделяет:

```text
setup                 подготовка через реальный ввод
actions               измеряемый ввод
observation           разрешённое наблюдение
assertion             абсолютное/относительное сравнение
settle                ограниченное ожидание результата
requirement_id        утверждение, которое проверяется
```

Один checkpoint существующего формата задаёт границу setup/actions. При `eq` или
`contains` он сохраняет эту границу, но не требует baseline-наблюдения. При относительном
сравнении baseline считывается после setup. **Удалять checkpoint без сохранения
границы нельзя:** это меняет контрольный прогон без измеряемого ввода.

Несколько checkpoint, ввод только до границы, нечисловое increased, неоднозначный
wait_for и неизвестный state-path дают ошибку сценария. Последний случай разрешается
по фактическому каталогу наблюдений, а не догадкой компилятора о JavaScript.
Одинаковая семантика применяется и при создании, и после ремонта.

Некорректный сценарий не запрещает независимые syntax/load/module/surface проверки
комплектного кандидата. Ограничения размера входа и ресурсов остаются жёсткими.

### 5.3 Решение о результате

Внутренняя классификация должна отдельно хранить:

| Причина | Действие | Что не должно происходить |
| --- | --- | --- |
| Ошибка среды/устаревший валидатор | Ограниченный recheck после восстановления | Новый модельный вызов и ремонт исходников |
| Некорректный сценарий | Компиляция/один ограниченный check repair | Перегенерация работающей игры |
| Недостаточно свидетельств | Сохранение кандидата, точное объяснение, допустимое ручное подтверждение | Автоматический pass |
| Доказанный syntax/runtime/geometry/module дефект | Патч или разрешённая замена малого модуля | Переписывание прочих файлов |
| Невыполненное модельное ожидание | Разбор происхождения и повторяемости | Автоматическое признание игры сломанной по одному effect_mismatch |
| Конкретный визуальный дефект | Отдельный ограниченный патч после допуска | Снижение требований или отказ от анимации ради pass |
| Повтор без прогресса/исчерпанный бюджет/unknown | Сохранение лучшего доказанного кандидата и stop | Бесконечные повторы или скрытый новый расход |

В UI показать соответствующую следующую операцию: повторить проверку, проверить
неподтверждённые условия лично, исправить обнаруженный дефект либо продолжить создание.
Ручное принятие всегда остаётся ручным и не увеличивает автоматическую успешность.
Разрешение берётся с сервера и связано с revision/hash/report/validator identity.

### 5.4 Разные стратегии при общей приёмке

**Lite, кандидат на новую стратегию:** короткий замысел → небольшой модуль правил и
рисования на compact runtime → локальные обязательные проверки → короткий вызов,
который составляет сценарии по замороженным требованиям и точному исходнику →
браузер → адресный repair. Подробный запрос может идти без отдельного plan, как сейчас.

`checks_create` не имеет прав изменять файлы/требования. К этому моменту код уже
сохранён, поэтому неправильные проверки не уничтожают игру. После нового кода
неизбежна актуализация привязок отчётов; автоматически переносить pass нельзя.
Неполный код не надо отправлять составителю сценариев: сначала syntax/module ремонт.

Это **эксперимент** против существующего compact с кодом и probes в одном ответе.
Он расходует дополнительный вызов. Не дробить автоматически каждую игру на множество
модулей: сохраняются проблемы стыков и теряется бюджет на исправления. Формат `lines`
тоже сравнить, а не объявлять победителем: модель уже умела складывать всю программу
в одну строку. Запрещены эвристическое восстановление переносов и удаление комментариев.

**Pro:** существующий plan → свободная реализация full с предложенными сценариями →
общая проверка → при наличии бюджета один визуальный review → при допуске один патч →
повторная проверка. Compact остаётся отдельным явно выбранным профилем, не ограничением Pro.
Review может завершиться `no_change`; необязательно изменять хороший результат.

Pro не участвует скрыто в обычной работе Lite. Не менять модель автоматически после
ошибки и не обещать слабой модели качество сильной только за счёт обвязки.

## 6. План исполнения

Исполнять этапы последовательно в текущей ветке. Перед каждым этапом сверять фактический
код: новые пользовательские изменения не перезаписывать по этому документу.
Все проверки до живого пилота используют fixtures/заглушки/сохранённые артефакты.

### P0. Зафиксировать исходную точку и корпус

**Результат:** `docs/generation-improvement-implementation.ru.md`, приватный снимок
исходников/хешей и воспроизводимый набор отрицательных/исправленных fixtures.
Секреты, авторизация и пользовательские исходники не попадают в публичный отчёт.
В P0 также записать таблицу версий из P8 и зависимости этапов. Новые схемы/операции
должны вводиться вместе со своими потребителями; P8 проверяет интеграцию, а не
откладывает версионирование до конца работ.

В корпус включить:

- checkpoint+eq/contains; неправильный числовой тип; wait_for посреди сценария;
- два неверных сценария рядом с исправной игрой; recheck без Invocation;
- check_suite_revised с разрешённым и запрещённым ручным принятием;
- ложный outcome на промежуточном достижении, фальшивый state при неподвижной игре;
- эффект таймера/RNG в контрольном прогоне, настоящая разница от ввода;
- `//` поглощает программу; корректная минифицированная программа; текст пути вместо кода;
- обрезанный второй ряд карточек; невидимая карточка; сломанный ввод после restart;
- compact без update с изменением состояния из callback; правильная пошаговая игра;
- ошибка длительности сноса, ошибка скругления, restart посреди анимации;
- полноценный и пустой/отказывающий план, явно запрошенная простая/статичная игра.

Использовать существующие тесты и очищенные минимальные примеры. Если точные приватные
артефакты отсутствуют, явно указать воспроизведение класса дефекта вместо replay исходных байтов.
Для каждого отрицательного примера зафиксировать нынешний результат до исправления.

### P1. Закрыть пользовательский путь завершения

**Файлы:** `studio/acceptance.py`, `serialization.py`, `replies.py`, `views.py`,
`web/src/Studio.tsx`, `api.ts`, `types.ts`, тесты API и Studio.

1. Использовать существующий `can_confirm` и confirmation payload в UI. Показать
   конкретные непроверенные условия и действие личного подтверждения.
2. Передать в существующий POST точные hash/report и `confirmed=true`; повторно
   проверить владельца, разрешение и отсутствие смены рабочей базы на сервере.
3. Для hard failure/нет gates/пустых checks/unknown/cancelled/stale report кнопки нет.
   Ответ 409 обновляет состояние, не повторяет подтверждение автоматически.
4. Различать текстом «игра сохранена, проверка требует внимания», «найден дефект»
   и «проверка временно недоступна». Сообщение модели не перекрывает состояние сервера.
5. Recheck обозначить как проверку без изменения игры. Сохранить доступ к прежнему
   кандидату и истории, не обещать, что recheck исправит сценарий.

**Приёмка:** браузерный сценарий с тестовым API и API-регрессии подтверждают manual
acceptance, отсутствие LLM и новых исходников, защиту от устаревшего отчёта и чужого
чата. Выбранная историческая версия не подтверждается как другая версия.

### P2. Единый компилятор и ранний допуск сценариев

**Файлы:** `generation/schema.py`, `compact.py`, `check_repair.py`, новый небольшой
`validation/check_program.py`, `checks.py`, `contracts.py`, `runner.py`,
`service.py`, `native.py`, `daemon.py`, тесты check semantics и browser.

1. Вынести независимые от браузера правила в общий компилятор; строить неизменяемый

3. Возвращать короткую структурную причину в check repair. Его ответ проверять тем

   Не менять requirement/expect/действия по эвристике.

**Приёмка:** паритет full/compact и native/Docker; checkpoint+eq/contains работает

**Ревью A:** P0–P2. Особое внимание: не исчезли ли ограничения приёмки ради процента

### P3. Проверять нужный эффект, честно учитывать неполное покрытие

**Файлы:** `validation/runner.py`, `diagnostics.py`, `evidence.py`, `checks.py`,
`studio/acceptance.py`, `check_repair.py`, `tasks.py`, существующие тесты R2/R3.

1. Разделить обычный запуск с естественным временем/RNG и диагностическую пару.
   В паре одинаковы начальные условия и setup; различается только измеряемый ввод.
   Нельзя сравнивать две разные случайные партии и объявлять разницу причинностью.
2. Таймерный исход не обязан зависеть от нажатия в последнюю секунду. Для такого
   критерия нужна отдельная явно заданная семантика и источник требования; само поле
   от модели не разрешает пропустить проверку управления.
3. Собирать ограниченную трассу действий: цель, проверка доступности, до/после,
   причина остановки. Каталог наблюдений читает доступные data properties, не getters.
   Отсутствие наблюдения остаётся unverified; обход Proxy не объявлять безопасным безусловно.
4. Сопоставлять сценарии с требованиями, отмечать непокрытые условия. Контроль
   промежуточного события не закрывает автоматически требование финала.
   В первой поставке использовать имеющиеся ID/requirement и доверенные критерии
   корпуса; новый RequirementManifest подключается в P4. Не строить эвристический
   «пониматель финала» по словам winner/score и не блокировать игру только по ним.
5. Не обещать универсального машинного доказательства соответствия естественному
   запросу. В независимом корпусе требования задаёт оператор; в обычной генерации
   модельные сценарии остаются предложениями, а спорная семантика видна пользователю.
6. Допуск ремонта механики требует воспроизводимого дефекта на точной базе и
   происхождения критерия. Один model-authored effect_mismatch недостаточен.

**Приёмка:** отрицательные fixtures для ложного state, случайного эффекта без ввода,
раннего outcome и подменённого критерия не проходят. Настоящий ввод и честный таймерный
исход не отвергаются по заведомо неправильному контрольному эксперименту. При потере
изоляции времени/RNG результат unverified, а не доказанный дефект игры.

Перед отдельным выпуском P0–P3 провести ревью всей этой поставки и replay корпуса.
Ревью A в середине не заменяет итоговую проверку изменений P3.

### P4. Усилить замысел без разрастания объёма

   до четырёх связанных механик, без требования обязательно заполнить четыре.
3. Явная просьба о простой, статичной игре или конкретных правилах сильнее наших

**Приёмка:** точный запрос не расширяется по обязательной схеме; простой пример не
отклоняется за отсутствие нескольких механик; редактирование не перепланирует игру;
модельный отказ не становится комплектным планом только из-за `status=ok` и длины строк.
Последний пункт проверять на корпусе, не выдавая это за доказательство для любого текста.

### P6. Небольшой проверенный набор технических средств

**Файлы:** новый модуль внутри `generation/runtime/`, `compact.py`, `artifacts.py`,
`prompts.py`, `presentation.py`, модульные и browser-тесты runtime.

Начальный объём ограничить переходами числовых свойств: from/to/duration/elapsed,
sample/advance/cancel/reset и режим уменьшенного движения. Нормализованное время
ограничено 0..1; разрешённый easing может намеренно выходить за диапазон значения.
Не запрещать отскоки и телепортации, не навязывать одну скорость/кривую всем играм.

Принимаемый dt использует одну единицу — секунды. Проверить нулевую длительность,
длинную паузу вкладки, новый ввод во время движения, смену перехода, restart,
однократность completion и очистку callbacks. Уменьшенное движение не меняет правила.
Для скругления использовать стандартный Canvas primitive; fallback нужен только
при подтверждённой необходимости в поддерживаемом WebView и с собственными тестами.

Compact получает средство через стабильный API; full может подключить его явно.
Список helpers и их версия фиксируются до упаковки; bundler встраивает локальные байты
в offline HTML. Модель не может заменить доверенный helper. Существующий сохранённый
HTML не меняется при чтении или recheck. Общая библиотека не рисует готовую игру.

**Приёмка:** числовые и пиксельные регрессии сноса/скругления, отрицательная исходная
fixture и исправленная; импорт/сеть не нужны. Тесты показывают исправность инструмента,
но не гарантируют, что произвольный сгенерированный код использует его верно.

### P7. Пакет кадров и один цикл визуального улучшения Pro

**Файлы:** `validation/runner.py`, `evidence.py`, `generation/feedback_image.py`,
`presentation.py`, `schema.py`, `studio/tasks.py`, models/migrations; Pro provider tests.

1. После игровых gates собирать ограниченный пакет: начало mobile, четыре кадра
   вокруг одного существенного действия и desktop-кадр. Хранить реальные времена,
   viewport, действие, artifact hash и report identity. Нет маршрута — нет выдуманной трассы.
2. Использовать уже выполненный доверенный маршрут или ограниченный повтор. Добавить
   его стоимость в watchdog. Детерминированный диагностический повтор не заменяет
   обычное проигрывание; не считать интервалы снимков доказательством FPS.
3. Для первого транспорта использовать одну контактную таблицу не более 512 КиБ
   с ограниченными размерами и подписями. Исходные кадры остаются приватными.
   Декодирование проверяет реальный формат/размеры; одна сигнатура PNG не защищает
   от огромного изображения. Повреждённый/устаревший пакет не отправлять модели.
4. Операция `visual_review` возвращает структурные замечания: воспроизводимый дефект,
   предполагаемый дефект, вкусовое предложение или no_change. Указать кадр, наблюдение,
   затронутое требование и минимальное исправление; не разрешать менять исходники этим ответом.
5. Приложение допускает один `visual_patch` только для конкретного дефекта с достаточной
   привязкой к версии. Чистое предпочтение палитры, неясность кадра и общий низкий балл
   не запускают автоматическую переделку. Замечания оценщика — гипотезы, не hard gates.
6. После патча повторить неизменные игровые критерии и соответствующие кадры.
   При регрессии оставить прежний более надёжный кандидат. Не запускать новый
   review → patch цикл автоматически. Без бюджета отметить review_skipped и сохранить игру.

Доступ Codex ограничивается данными и картинкой; shell, сеть и произвольный браузер
модели не выдаются. Существующие CLI/API используют один формат данных, без изменения GPU.

**Приёмка:** no_change, stale image, поддельный report ID, чужая ревизия, повреждённый
кадр, исчерпанный бюджет, отмена, unknown, повтор receipt, отказ и регрессия патча.
Тесты качества опираются на размеченные дефекты; отзывы vision-модели калибруются
живым пилотом и человеком. Один цикл остаётся экспериментом.

### P8. Сквозные версии, бюджеты и сохранность

**Файлы:** `studio/models.py`, `tasks.py`, `services.py`, `capacity.py`, `acceptance.py`,
`generation/schema.py`, providers, migrations, все identities и deployment documentation.

P1–P3 допускают отдельную поставку с существующим внешним v8 envelope, но новой
версией семантики/валидатора. Для полного изменения планов и операций P4–P7 целевой
pipeline **9**, check policy **3**, compact runtime **2**, planning policy **2**.
Если номера заняты к началу работ — выбрать следующие и записать соответствие.
Это одна новая поддерживаемая линия, без параллельной реализации старого генератора.

Перед новым контрактом остановить допуск и дождаться отправленных запросов; старые
receipt/UUID/usage/unknown сохранить. Не переписывать старые hashes и версии строк БД.
Несовместимые игровые артефакты можно удалить по прежнему решению владельца, но не
финансовый журнал. Миграция сначала делает inventory и резервную копию; при отсутствии
реальной несовместимости удалять игры ради номера версии не нужно. Публикации и ссылки
на удалённый формат получают явное состояние недоступности, не скрытую подмену игры.

Общий потолок остаётся **пять модельных вызовов с планом, четыре без**, максимум три
исправления. Новый этап не увеличивает эти пределы автоматически. Примеры распределения:

- Lite: plan + code + checks_create + до двух исправлений = до пяти.
- Pro: plan + create + visual_review + visual_patch = четыре; ещё одно место возможно
  для функционального ремонта. Если он потребовал больше, визуальный этап пропускается.
- check_repair расходует тот же бюджет исправлений; никакого отдельного бесплатного
  пула. recheck без изменения кода расходует браузерные ресурсы, но не Invocation модели.

На каждом шаге проверяются admission, отмена, лимит и оставшееся время. Получение
ответа на уже отправленный запрос не запрещается сроком новых отправок. Unknown
не повторяется вслепую. Операции review/checks_create учитываются как настоящие вызовы.

Сохранить remote Pro concurrency=2 суммарно на Codex Worker и лимиты приложения,
изоляцию клиентов Mac/облако, локальный CLI и Lite=1. Новые шаги не должны удерживать
место модели во время браузерной проверки. Расширение модели workflow не требует
увеличения конкурентности или доступа к GPU.

**Ревью C:** полный diff от P0, оба транспорта Codex, queue redelivery/cancellation,
неизвестный расход, hash-bound приёмка, границы публикации, недопустимость снижения
требований ради успеха. Итоговый отчёт включает все находки и их исправления.

### P9. Replay, сравнение и включение

Сначала проиграть сохранённые артефакты без inference. Измерять отдельно изменения
классификации, восстановление сценариев и результат реального ввода. Новый pass должен
объясняться исправленным свидетельством, а не исчезнувшим требованием. Нельзя приписывать
улучшение существующей игры новому промпту: он на её исходник не влиял.

Затем предложить **новый** живой бюджет. Прежние бюджеты закрыты. Предварительный
диагностический дизайн: до 48 вызовов / 180 минут, 12 игр, не более четырёх вызовов
на игру. Три разных запроса × две стратегии × два класса модели. Для Lite сравнивать
compact inline и code_then_checks; для Pro — общий новый путь без и с visual review.
Это один повтор на ячейку, поэтому результат только диагностический. При лимите четыре
вызова функциональный ремонт имеет приоритет, а visual review может быть пропущен.

В общий offline-корпус заранее включить восемь разных типов задач: дискретная головоломка,
память, перемещение/лабиринт, непрерывная аркада, таймерное выживание, физическая задача,
игра на реакцию, взаимодействие нескольких систем. Держать отдельные новые запросы,
не использованные для настройки промптов. Не превращать названия типов в шаблоны генерации.

Для живого опыта заморозить prompts/versions/лимиты, чередовать порядок веток опыта,
сохранять все исходы, включая отказ/unknown/пропущенный этап. Full/compact не смешивать
в одной цифре. В каждой паре Lite зафиксировать одинаковый source format: сравнение
string/lines — следующий отдельный опыт, его нельзя смешивать с эффектом разделения
code/scenarios в этих 48 вызовах. Отдельно сравнить с прежними пилотами, указав изменения моделей,
транспорта, политик и несопоставимость бюджетов. Для вывода об устойчивом эффекте нужен
следующий опыт с повторами, его объём и бюджет согласуются отдельно.

Метрики:

- доля запускающихся и независимо играбельных игр;
- автоматическое завершение и ручное подтверждение отдельно;
- ложный pass, ложный fail и доля непроверенных требований;
- полный требуемый исход и restart, а не только первое игровое действие;
- число/тяжесть визуальных дефектов и слепая попарная оценка оформления человеком;
- реализация обещанного выбора/прогрессии, а не количество полей плана;
- время до первого кандидата, первого играбельного и окончательного результата;
- вызовы/токены, известный и неизвестный расход, вызовы после появления играбельной версии;
- пропуск review по бюджету и доля улучшений/регрессий от visual_patch.

Условия включения: все отрицательные offline-регрессии сохранены; нет новых ложных
принятий на корпусе; соответствующая стратегия улучшает целевой эффект при том же
потолке, не ухудшая сохранность/управление. Малый пилот не даёт статистической гарантии.
Если отдельные checks увеличивают расход без выигрыша — не делать их Lite-default.
Если визуальный проход чаще портит игру/не помещается в бюджет — оставить его явной
доработкой пользователя. Если Lite остаётся слабым, честно показывать различие
качества; не прятать его автоматическим обращением к Pro.

## 7. Команды и отчётность

Использовать действующие команды README и изолированную тестовую БД; не запускать
тесты на рабочей базе. Минимальный набор по соответствующим этапам:

```sh
.venv/bin/ruff check gameforge studio generation validation scripts tests
.venv/bin/pytest -m 'not browser and not live'
npm test --prefix web
npm run lint --prefix web
npm run build --prefix web
```

Browser-проверки выполнить через существующие native/Docker инструкции README на
затронутом корпусе; проверить одинаковую семантику обоих backend. Проверка настоящего
телефона/WebView отдельная и не подменяется viewport или эмуляцией Chromium.

Для каждого P-этапа в отчёте: baseline, изменённые контракты, отрицательный пример до
исправления, результат после, проверки и границы доказательства. Не включать сырые
пользовательские запросы/игры, ключи и авторизацию. Отдельно отмечать mock/replay/live.

Код и локальная приёмка сначала; обновление облака — отдельная операция после ревью.
GPU не менять и не опрашивать. Подключение к Codex API/CLI сохраняется, но обычные
регрессии не отправляют запросы модели.

## 8. Рекомендуемый старт

Первая конкретная поставка — **P0–P3**. Она устраняет проверяемые причины «игра есть,
но генерация не завершена» и повышает достоверность проверки без нового inference.
Затем P4–P5 для Lite, P6–P7 для Pro, сквозная приёмка P8 и эксперимент P9.
P6 можно реализовать после первой поставки независимо от Lite, но включение новых
стратегий всё равно требует общей приёмки. Полный rewrite приложения не нужен.
