### Изменение поведения

Сейчас `_execute` восстанавливает pending-кандидата, оценивает старый отчёт и может
закончить Run раньше блока обработки reserved/sent. Наличие уже отправленного
check_repair при этом делает `can_repair=false`. Устранить зависимость порядка от
локальной переменной pending: до принятия решения по кандидату определить незавершённую
операцию и обработать её сохранённый запрос.

| Состояние Invocation | Действие при повторном входе |
| --- | --- |
| reserved, ещё не отправлена | Проверить отмену, fence и срок новой отправки; использовать тот же запрос и UUID |
| sent | Получить исход существующего задания; Pending откладывает Run; не создавать новую попытку |
| returned, результат не применён | Применить к базе из сохранённого request один раз, проверить результат |
| settled/failed | Перейти к оценке актуального кандидата и следующему действию |
| unknown | Сохранить неопределённость расхода и существующий порядок явного разрешения повтора |

Вынести небольшой общий путь обработки существующего вызова, если он сокращает
дублирование; не переписывать весь orchestration и не создавать новый workflow engine.
После применения ответа заново получить кандидат/отчёт; старое решение не использовать.

Соблюдать существующие ограничения `pending_invocations`: точная база, цепочка только
этого чата, барьер source_restart и запрет заимствования чужого ответа в model-free Run.
Для текущего Run не терять незавершённую Invocation только потому, что текущий кандидат
уже отличается от исходной базы запроса. Не обходить это снятием проверки base/hash:
применимость ответа и необходимость завершить его учёт — разные условия.

Завершение в succeeded/unverified/needs_attention не должно скрывать действующую
reserved/sent Invocation или неприменённый подходящий returned. Проверять инвариант
в общей точке завершения, учитывая транзакции и fence. Если защита блокирует завершение,
Run должен реально ожидать/восстанавливаться, а не остаться без outbox и lease.

Отмена, удаление чата и истёкший срок могут остановить пользовательскую работу.
Получение квитанции и usage после этого разрешено, применение кода/принятие — нет.
Истёкший срок новой отправки не запрещает получить уже оплаченный ответ.
Нельзя бесконечно считать вызов активным, если транспорт уже сообщил unknown/failed.

## S2 Разделить проверку артефакта и игровых сценариев

### Независимые обязательные проверки

Не возвращаться по incomplete_checks до проверки кода. Порядок:
проверка hash/структуры входа → синтаксис → загрузка и поверхность игры в изоляции →
сценарии, которые допустимо исполнять → общая классификация.

Структурно опасный/чрезмерный payload по-прежнему отклонять до браузера. Семантически
неполный набор checks — допустимый вход для проверки самого артефакта. Синтаксическая
ошибка прекращает последующие этапы, но возвращает точное свидетельство syntax.

Ввести отдельное версионируемое свидетельство обязательных проверок, например
`artifact_evidence`: hash артефакта, environment/версия, этапы и результаты по mobile
390×844 и desktop 1280×800. В нём нужны реальные результаты загрузки, ошибки/network
и геометрия Canvas; одних булевых флагов недостаточно. Проверка — короткая, с лимитом
времени, без придуманного нажатия Start и без объявления игровой победы.
Canvas, появляющийся только после корректного запуска, требует сценарного свидетельства;
его отсутствие на заставке само по себе не доказывает сломанную игру.

Обычный режим с полными checks может переиспользовать уже полученные свидетельства
сценарных контекстов. Не добавлять без необходимости два дополнительных запуска браузера
к каждой успешной игре. Для неполного набора обязательное свидетельство всё равно должно
быть получено независимо. Ошибки после реального ввода также остаются блокирующими.

Согласовать `gates_verified`, `_validated_report`, `assess`, `confirmation_report`,
`check_identity`, watchdog и cache. Сейчас gates_verified требует facts на каждый check
и непустой checks; нельзя просто заменить его на `all(gates.values())`.
Положительные обязательные gates не означают проверенные игровые требования.
Старый отчёт после смены валидатора не считается актуальным: recheck без модели,
без изменения исходников и исходных checks. Если добавлен исполняемый модуль валидатора,
включить его в `implementation_hash` и упаковку native/Docker.

### Таблица выбора действия

| Наблюдение | Следующее действие |
| --- | --- |
| Среда/браузер не завершили проверку | recheck без модели; исходники сохранены |
| Доказанная ошибка syntax/runtime или подтверждённая ошибка поверхности | Ограниченный repair кода при доступном бюджете |
| Код загрузился, checks неполны/недоступны/имеют несовместимый тип | check_repair в разрешённом лимите либо ручной разбор |
| Поверхность пока не удалось наблюдать, настоящего дефекта не установлено | Сохранение и диагностика; нет source repair и нет разрешения ручного принятия без gates |
| Только effect_mismatch или timeout с сомнительным маршрутом | Не считать это автоматически доказательством ошибки кода |
| Пересмотренные моделью checks прошли | Явное подтверждение по актуальному hash и отчёту |
| Исходные полные checks прошли все требуемые проверки | Существующий путь автоматического принятия |

Исчерпание попыток check_repair не превращает неопределённость в доказанный дефект игры.
Проверить смешанные результаты: настоящая syntax/runtime ошибка приоритетнее плохого
селектора; инфраструктурный сбой не выдаёт разрешение на изменение исходников.
Ручной разбор не равен доступной кнопке подтверждения: для подтверждения нужны
обязательные свидетельства и явный сохранённый список непроверенных требований.
Пустой checks не должен приводить к подтверждению пустого списка условий.

### Ремонт кода при неполном исходном checks

**Критическая зависимость:** сейчас `request_for` и `materialize` отклоняют repair
через invalid_baseline_checks, а итоговая `validate_checks` отклоняет его повторно.
После перестановки gates этот путь также нужно исправить.

Ввести узкое поведение контракта **v7** для новых запусков. Приложение выдаёт сохранённое
разрешение `code_repair_basis` только по актуальному отчёту доказанного дефекта артефакта.
Связать его с base_revision, artifact_hash, checks_hash, report_id/identity и кодом
дефекта. Разрешение формирует контроллер; модель не может прислать его в ответе.
Не включать в разрешающие причины один лишь effect_mismatch, timeout, invalid_check,
пустую/однотонную картинку или отсутствие свидетельства.

В этом режиме ответ repair сохраняет `checks=[]` в транспортном смысле «не менять
сценарии», а результат наследует исходный список **полностью и в прежнем порядке**.
Не собирать его через словарь ID: неполный набор может содержать повторяющиеся ID,
и молчаливое устранение дублей изменило бы базу. Design/title/требования также сохраняются.
Схема ответа, квоты, source_policy, точная база и правила patch/replace_module остаются строгими.
Отложить только семантическую полноту унаследованного checks; проверять допустимость
структуры и размера данных, не принимать произвольный повреждённый JSON.

После ремонта снова выполнить обязательные проверки. Исправленный синтаксис с
по-прежнему неполными сценариями ведёт к отдельной проверке сценариев/ручному разбору,
а не к succeeded. Разрешение нельзя переиспользовать на другом hash или более новом отчёте.
Материализатор получает сохранённое разрешение и проверяет его привязки, не читает БД.

Сохранить поддержку v2–v6 явным списком: сейчас `response_schema` использует
`{2,3,4,5,CONTRACT_VERSION}` — простое увеличение константы потеряет v6.
Существующие Invocation продолжаются по сохранённой версии. V6 с неполными checks
не получает разрешение v7 задним числом; если его ремонт невозможен по старому контракту,
результат сохраняется с понятным ограничением. Исправление доставки S1 применимо к старым
вызовам и не меняет их запросы. Новые обычные Run могут использовать v7 после локальной
проверки; live-включение и смена процессов пользователя в эту поставку не входят.

## S3 Дать ремонту ограниченную диагностику браузера

Файлы: `validation/runner.py`, при необходимости новый небольшой модуль внутри validation;
`generation/feedback.py`, `generation/prompts.py`, `studio/tasks.py` и тесты feedback/validation.

На неудачном сценарии сохранять: check_id, индекс и вид шага, requested observation,
фактический тип, ограниченные before/after/expected, viewport, размеры Canvas и
доступные элементы управления. Собирает браузер; модель не может сообщить эти факты
сама. Не включать полный DOM, outerHTML страницы, дамп window и данные хоста.

Для поиска исправимого селектора — до 16 видимых элементов управления с короткими
id/role/aria-label/текстом и координатами. Помечать усечение и не утверждать отсутствие
элемента, если список усечён. Не генерировать «точный селектор» без проверки, что он
действительно указывает на нужный элемент. Координаты соотносить с viewport и Canvas.

Для state наблюдать только явно запрошенный путь и допустимые собственные данные.
Сохранять защиту от getters, циклов, неподдерживаемых прототипов и чрезмерного объёма.
Не исполнять переданный моделью код для поиска состояния. Недоступное closed-local
