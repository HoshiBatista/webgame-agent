# Подключение независимых служб доставки LLM

GameForge взаимодействует с моделью через обычный интерфейс провайдера. Адаптер relay
скрывает повторную передачу, ожидание и получение сохранённого ответа. Реле и GPU-исполнитель
не знают схемы игр, не получают Django/исходники GameForge и не управляют моделями.

## Репозитории и порядок

Локальные Git-репозитории лежат рядом, но не являются зависимостями сборки:

- `../llm-relay` — сервис для облачного VPS; собственные Dockerfile, Compose, CI и README.
- `../llm-gpu-worker` — исходящий исполнитель рядом с vLLM; свой образ/Compose/CI/README.
- этот репозиторий — GameForge; `generation/relay_api` содержит только HTTP-клиент и codec v1.

В каждого свой release, dependencies lock и Git-история. На GitHub они пока не опубликованы.
Общий формат закреплён в docs/PROTOCOL.md обоих сервисов и тестовой fixture relay-v1.json.
Runtime-импортов из соседних каталогов, pip-зависимостей на соседние репозитории и git submodules нет.

1. Установить реле на VPS по его README; добавить маршрут /bridge/v1/* в существующий Caddy.
2. Создать отдельные client и worker токены. Ключ GameForge не подходит исполнителю и наоборот.
3. Оператор GPU устанавливает исполнитель по его README, проверяет исходящий HTTPS к VPS
   и локальный vLLM. Он не меняет модель/чужие контейнеры и не открывает входящих портов.
4. После готовности служб настроить GameForge, перезапустить его и сделать согласованный пробный запрос.

Изначальный единый архив `.data/llm-bridge.tar.gz` устарел; не использовать его для установки.
Актуальные комплекты: `dist/*-deploy.tar.gz` и `dist/*-0.2.0-linux-amd64.tar.gz` в каждом новом репозитории.
Проверить SHA256SUMS, docker load, заполнить deploy/.env, затем Compose up --no-build.
Для будущего GHCR-деплоя предусмотрена публикация образа по Git-тегу; сейчас не требуется registry.

## Настройки приложения

Для локального запуска:

```dotenv
GAMEFORGE_PROVIDER=relay
GAMEFORGE_MODEL=qwen38
GAMEFORGE_RELAY_URL=https://129.101.114.59
GAMEFORGE_RELAY_API_KEY=NEW_CLIENT_TOKEN
```

Вместо значения токена локальный процесс поддерживает `GAMEFORGE_RELAY_API_KEY_FILE` с путём
к закрытому файлу. Старый LLM_API_KEY остаётся для прямого vLLM и не используется вместо
отдельного ключа реле. Не добавляйте токены в frontend/Git.
На текущем стенде GAMEFORGE_PRICES_JSON задаёт qwen38/context_window=32768/max_output_tokens=16384,
GAMEFORGE_VLLM_CONTEXT_CHECK=server. URL — origin, без /v1 или /bridge/v1.

Для Compose задайте `CONTAINER_PROVIDER=relay`, `CONTAINER_MODEL=qwen38` и те же
GAMEFORGE_RELAY_URL/GAMEFORGE_RELAY_API_KEY. Только worker получает ключ; app/preview/beat — нет.
Для другой установки сначала подготовьте обе службы, затем переключайте её рабочую .env.

Дождитесь окончания старых запусков. Для текущего локального менеджера процессов:

```sh
TZ=Europe/Moscow .venv/bin/python scripts/dev.py stop
TZ=Europe/Moscow .venv/bin/python scripts/dev.py start
```

Временная зона должна совпадать с той, в которой менеджер записал время старта PID.
Для Compose — `docker compose up -d --build` после проверки config.
Режим Codex сохраняется (`GAMEFORGE_PROVIDER=codex`, `GAMEFORGE_MODEL=gpt-6-luna`);
прямой vLLM сохраняется (`GAMEFORGE_PROVIDER=vllm`). Browser API/логика игр прежние.
Не меняйте URL/principal реле при незавершённых заданиях: нужны прежний адрес и владелец.

## Что проверить до переключения

- Без Bearer ключа HTTPS /bridge/v1/health возвращает 401; с новым ключом — 200/protocol=1.
- На GPU есть исходящая связь с VPS, локальный vLLM доступен, executor работает без ошибок.
- У реле и исполнителя постоянные volumes и резервные копии, runtime-файлы закрыты.
- Один согласованный тест: GameForge ставит задание и получает сохранённый результат.
- Нет второго исполнителя с тем же principal и отдельным spool.

## Локальная проверка двух независимых образов

После сборки образов в соответствующих репозиториях:

```sh
.venv/bin/python scripts/verify_relay_stack.py \
  --relay-image llm-relay:0.2.0 --worker-image llm-gpu-worker:0.2.0
```

Тест использует только Docker на текущем компьютере, без внешней сети. Настоящий WSGI-сервис,
отдельный образ исполнителя, локальная HTTP/SSE-модель-заглушка: роли/авторизация, один вызов,
сохранение, обрыв доставки, перезапуск обоих процессов, потеря ACK и повторная доставка.
В GameForge отдельно проверяется разбор стандартного envelope в JSON игры и восстановление Invocation.
Это проверка протокола, не качества настоящей модели и не доступности реальной сети GPU.

## Границы надёжности

При обрыве внешней связи генерация продолжается, готовый ответ хранится рядом с vLLM.
Если аварийно завершится сам исполнитель во время вызова, результат может остаться unknown.
Такие вызовы не повторяются автоматически. После cancel поздний результат сохраняется
для учёта, но новая версия игры не применяется. Перед обновлением исполнителя используйте drain.
GPU-сервер устанавливает и обслуживает его оператор; прямой доступ агента к нему запрещён.

## Исправления готовности — 23.10.2026

Версия служб 0.2.0 сохраняет HTTP v1. История сжимается без удаления UUID/ответов;
лимит 512 относится к активным заданиям. Добавлены пороги размера БД/свободного места,
предупреждение и локальный archive для старых записей. После backup обновляйте обе службы;
образы 0.1 не умеют читать сжатые записи. Смотрите README соответствующего репозитория.

GameForge показывает waiting_admin при 401/403/507 с отдельной причиной в run.error и
invocation.provider_metadata.relay_wait. UUID, запрос и резерв сохраняются; после исправления
автоматическая проверка раз в 5 минут продолжает то же задание, не создавая новое.
429 означает занятую очередь, повтор через 30 секунд; обычное ожидание — 5 секунд.
Отмена сохраняется отдельно; плохой токен не превращает её в доказательство отсутствия расхода.
Неразрешённое задание продолжает занимать слот: это защита от незаметного повторного вызова.

`manage.py diagnose_invocation UUID` показывает также relay_job_id, relay_wait/cancel_wait
и статистику локального обращения к модели. Транспортные JSON-логи GameForge попадают в
тот же GAMEFORGE_TRANSPORT_LOG с ротацией; обе службы пишут безопасные метаданные в Docker logs.
Содержимое и ключи не журналируются. Счётчики попыток HTTP локальны процессу/клиенту,
число опросов GameForge сохраняется в Invocation. Продолжающаяся работа модели не имеет
общего таймера; 60 секунд — ограничение бездействия HTTP-операции к реле.

Перед запуском оператор всё ещё должен проверить выход GPU → HTTPS VPS и локальный vLLM.
Передача ответа пока целиком с повтором, без дозагрузки с места обрыва. Авария исполнителя
во время inference остаётся unknown; обновление выполняют после drain/idle.
