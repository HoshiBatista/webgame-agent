**Полный отзыв, 3000 символов и фоновые пожелания, 28.10.2026 — `ed35431` в облаке.**

Отзыв выбранной версии возвращает рейтинг, галочки и отдельный свободный текст;
старые объединённые причины также восстанавливаются. Повторное сохранение не создаёт
дубль, изменение только звёзд не вызывает модель. Общие пожелания увеличены до 3000
Unicode code points на клиенте/сервере с учётом LF и пробелов; шаблоны остаются до 2500.

Новый FeedbackProcessing сохраняется вместе с отзывом без сетевого вызова в HTTP.
Существующий dispatcher Celery подбирает задания; модель из настроек закрепляется
в момент сохранения отзыва. Один запрос с компактным контекстом выделяет новые общие
пожелания; исходный текст отзыва сохраняется независимо от результата. Существующие
пожелания имеют приоритет и не переписываются. Сервер проверяет структуру ответа,
цитату из отзыва, однострочность, буквальные повторы и свободное место; семантический
отбор/противоречия относятся к модели и без реальных испытаний не объявляются доказанными.
Задания аккаунта идут последовательно; ручная правка/сброс/возврат старого текста
делают прежний ответ stale, новая редакция отзыва — superseded. Повторного вызова
для таких ответов нет. Неопределённый расход, резервы и известный usage учитываются
в общем бюджете; слоты провайдера общие с генерацией игр. Durable-получение использует
прежний UUID/запрос; потерянный прямой вызов не отправляется заново. Игровые Run и
сообщения при обработке отзыва не создаются.

**Следующая поставка по результатам этого пилота — без нового inference:**

1. Отдельный надёжный формат исходников Lite. Проверить full/lines с явным массивом
   строк для каждого файла, детерминированным LF join и закреплением формата до
   отправки. Регрессии на комментарии, скобки, кавычки и Unicode; запрещено угадывать
   границы строк в уже повреждённом JS. У Pro сохранить полный формат и возможность
   реализовать связанный замысел. Это изменение выдачи кода, а не ещё одна роль модели.
2. Приёмка плана в `generation/planning.py` и `studio/tasks.py`: отказ должен иметь
   отдельную форму без обязательного заполнения всех полей фиктивным планом.
   Формально корректный capability refusal со status=ok не должен показываться как
   пригодный замысел. Необходимы сохранение исходного ответа, явное решение о fallback
   к исходному запросу и тот же общий бюджет. Проверить приоритет требований
   пользователя над ошибочными assumptions вроде «пользователь хочет текстовую RPG».
3. Семантическая компиляция проверок до браузера: одинаковые ограничения для create
   и check_repair, в том числе checkpoint/expect, тип наблюдения и доступность пути.
   Модель не должна владеть смыслом приёмки; полный финал и повтор происходят из
   закреплённых требований, а не подменяются первым промежуточным успехом.

   действий, с конечным бюджетом событий и времени. Регрессия — три фонаря и выход,

4. Разделить транспортный сбой Codex и дефект игры в результате и UI. При отсутствии
   кандидата нельзя сообщать «сохранённая игра осталась на месте»: в этом случае

| Было в расширенном процессе / предложениях | Будет здесь | Зачем |
| --- | --- | --- |

Точечные проверки и качественный интерфейс сохраняются. Скорость не достигается
выдачей шаблона, пропуском безопасности или маркировкой непроверенного кода как готового.

## 2. Скорость как критерий разработки

Предварительные внутренние цели на прогретом стенде, одном активном запросе и выбранной
модели. Не являются требованиями организаторов. Измерения приведены в отчёте;
реализация функций не означает автоматического выполнения этих целей.
Для текущей локальной модели прежние секундные ориентиры не подтверждены: последний
пользовательский запуск занял около 15 минут. По запросу 23.10.2026 приоритет следующего
пилота — доля работающих игр и полное время ограниченного поэтапного цикла.

| Метрика | Первичный ориентир |
| --- | --- |
| Принятие запроса и понятный статус | до 1 секунды |
| Создание: отправка → проверенная playable-версия | p50 ≤ 30 с, p95 ≤ 60 с |
| Малая правка: отправка → проверенная новая версия | p50 ≤ 10 с, p95 ≤ 20 с |
| Накладное время приложения без модели и очереди | до 5 с для обычного smoke-сценария |
| Вызовы модели без ошибки | 1 создание / 1 доработка |
| Автоматические корректирующие вызовы | до 3 исправлений после основного вызова; настройка 2–3, фиксируется в Run |
| Перезапуск при повторном открытии готовой игры | 0 модельных запросов |

Считать отдельно очередь, ожидание модели, первый токен, конец ответа, упаковку,
проверку и доставку preview. Основное время включает **все** эти этапы; нельзя выдать
анимацию загрузки за playable-результат. Холодный запуск, прогретый и нагрузочный режимы
публикуются раздельно. Внутренние ходы Codex не прячутся за одним вызовом адаптера.

Цель 60 секунд не является обрывом на 60-й секунде. Если ответ идёт, показать задержку
и отмену. Ошибки/отказы не перезапускаются бесконечно: сохранённый результат и явное
продолжение доступны пользователю. Общее время, output size и число внутренних запросов
используются для выбора модели и упрощения процесса, а не для сокрытия ошибок.

Пилот — пять разных коротких запросов и по две небольшие правки. Сначала показа
индивидуальных результатов достаточно; для устойчивых перцентилей нужен более широкий
согласованный по бюджету набор (ориентир ≥20 наблюдений на тип операции, с оговоркой
об ограниченной выборке). Не обещать точный p95 по двум удачным играм.

### Этап 3 — точечные правки, восстановление и история: реализован

**Сделать.** Edit-контракт с base revision/hash, точными заменами и необязательными

фиксированных примерах; не достраивать молча десятиступенчатого агента.

**Проверить.** Смена адаптера без изменения чатов/публикаций; edit игры, созданной другим
поддерживаемым адаптером; ошибочный schema output; медленный/оборванный stream;
раздельные latency/usage. Отсутствие API-цены у локальной модели не равно отсутствию работы.

**Выход.** Реальный API локальной модели работает в том же продукте и имеет отдельный отчёт.
Если сервер пока не выдан, протокольная часть завершена, живое испытание честно остаётся открытым.

### Этап 7 — проверка всей поставки, скорости и WebView: проверки и измерения

**Сделать.** CI по мотивам ML-ветки, но под новую реализацию: backend lint/types/tests,
frontend lint/types/tests/build, PostgreSQL 18+/Redis integration, browser, security,
сборка и запуск контейнеров. Нет неработающих заданий от удалённых модулей. Live evals
запускаются отдельно с явным бюджетом, не на каждый commit и не по старому расписанию.

Воспроизводимый прогретый стенд, пять разных запросов + малые правки, сохранённые
prompt/model/version/latency/usage/качество. Сначала функциональный прогон, затем
достаточная для выбранной метрики серия в пределах бюджета. Не смешивать фикстуры,
кеш повторной выдачи и новые генерации. Не скрывать ошибки из знаменателя успешности.

Проверить очередь на 1/3/10 конкурирующих заданиях с fake provider и ограничения
настоящего провайдера отдельно. Число одновременно исполняемых запросов настраивается:
для Codex начать с одного, для vLLM — по замерам. Десять поставленных в очередь заданий
не объявляются десятью одновременными inference. Оценка пропускной способности ML-ветки
не переносится без нового измерения.

Проверить offline HTML в мобильном браузере и доступной настоящей Android WebView /
WKWebView-оболочке. Конкретный хост Билайна неизвестен; если устройства нет, это остаётся
ограничением, а не закрытым тестом по скриншоту телефона.

Подготовить локальную демонстрацию 3–5 минут, README/runbook с фактическими командами,
чистую установку и восстановление. Размещение на `digsy.ru` — после готовности и доступа
к инфраструктуре; план не означает автоматическую публикацию сейчас.

**Выход.** Все обязательные и согласованные продуктовые сценарии подтверждены, известны
фактические скорость и ограничения обеих конфигураций. Есть короткая демонстрация и история Git.

### Этап 8 — дополнительные баллы: демонстрационная аналитика реализована

В настройках доступны явно обозначенные синтетические метрики и объяснимая
рекомендация. Только по нажатию пользователя она добавляется в редактируемые предпочтения

первую playable-версию и не превращают мини-игру в исследовательский проект.

## 4. Матрица ключевых проверок

| Область | Позитивный сценарий | Обязательная отрицательная проверка |
| --- | --- | --- |
| Генерация | Разные короткие запросы дают работающие новые игры | Заглушка/зашитая игра не считается живой генерацией |
| Ввод | Touch, keyboard, hold/release где применимо | Неработающая стрелка/кнопка, потерянный pointer, залипание после blur |
| Механики | Смысловой эффект и игровой исход | Счётчик меняется, но действие не работает; запрещённый ход правильно не меняет состояние |
| Изображение | Читаемость, цель, элементы управления, состояние победы/поражения | Пустая сцена, мелкие элементы, обрезанные кнопки, ложный успех по одному pixel diff |
| Патч | Цвет/размер/темп/уровни меняются локально | Stale hash, неоднозначная замена, выход пути, перезапись всей игры при перекраске |
| Восстановление | Сохранённые ответы и рабочая версия доступны после перезапуска | Повторная доставка, потеря подтверждения, поздний ответ после cancel |
| Секреты/preview | Изолированный запуск и offline экспорт | Доступ к cookies/БД/внутренней сети/хосту, popups/top-navigation |
| Аккаунты | Case-insensitive уникальность и права | Дубль регистра в гонке, чужой chat/revision, CSRF |
| Публикация | Явный снимок, обновление, независимый ремикс | Неопубликованная правка попадает в ленту, delete chat удаляет игру |
| Лента/feedback | Идемпотентный лайк, управляемые предпочтения | Рост лайков от дублей, скрытый запуск LLM при оценке, десятки live iframe |
| Провайдер | Одинаковая схема create/edit | Неверная schema, обрыв, отказ, неучтённый внутренний retry |
| Скорость | Измеренный путь от отправки до игры | Очередь исключена из времени, непроверенный preview засчитан как готовность |

Базовые проверочные игры: пошаговая сетка, непрерывное управление, головоломка,
кликер с конечной целью, короткий runner. Это набор испытаний, не каталог готовых игр.
Добавить вариант после фиксации prompt, чтобы не подгонять продукт только под известные случаи.

## 5. Организация работы и ограничения

Сначала этапы 1–3: рабочий путь, реальные замеры и точечное редактирование.
Далее 4–5: весь согласованный продукт; 6: реальный второй провайдер; 7: итоговая приёмка.
Разработка протокола vLLM и UI на согласованных fixtures может идти независимо, если
транспорт или бюджет временно недоступны. Не ждать полного frontend polish для первой LLM-пробы.

Предлагаемая ответственность: backend — состояния/права/патчи/версии/очередь; ML —
prompt/provider/evals/скорость; frontend — F01–F14 и общий API-контракт. Это распределение
для команды, не поручение рассылать сообщения или запускать дополнительных агентов.

Для выполнения пользователь разрешил **$50 суммарно** API-эквивалента. Живые
испытания проходят через общий журнал приложения; расход и неизвестная ответственность
не сбрасываются между пилотами. Реальный vLLM пока исключён из испытаний пользователем.

После изменений обновлять статус, README и `game-creation-model.ru.md`, указывать
сделанное, команды проверки и доказательства. Изменения продукта делать маленькими
осмысленными коммитами; не force-push и не переписывать историю ML-инженера.
