# План новой конкурсной версии GameForge

**18 октября 2026 года.** Выполнена только подготовка и очистка (этап 0).
Прикладная реализация начинается с этапа 1. Основная цель — быстро получить хорошую
мини-игру и быстро менять её небольшими запросами. Это отдельный продукт от GamesForgeEx.

Основания: [матрица требований](requirements.ru.md), [анализ ML-ветки](source-review.ru.md),
[архитектура](architecture.md), [исходные документы](sources/README.md).
Источники не заменяют настоящий прогон: старые отчёты не засчитываются новой реализации.

## 1. Что меняется принципиально

| Было в расширенном процессе / предложениях | Будет здесь | Зачем |
| --- | --- | --- |
| Несколько модельных ролей до первого результата | Один ответ: короткий замысел + игра + проверки | Убрать последовательную задержку |
| Длительные исследования и исправление общей платформы внутри задания | Короткая генерация, одна автоправка, понятное продолжение | Не расходовать десятки минут на мини-игру |
| Полный новый HTML при любой правке в ML MVP | Патч к точному снимку; локальная пересборка экспорта | Сохранить игру и уменьшить выход модели |
| Универсальная схема всех механик/обязательный runtime | Обычные HTML/CSS/JS, правила и проверки конкретной игры | Не создавать ложные ошибки из-за чужого шаблона |
| Проверки и ревью одних байтов несколькими ролями | Один сохранённый отчёт на версию/среду | Не делать повторную работу |
| Огромный исторический контекст | Текущая игра, запрос и релевантные результаты | Снизить задержку и путаницу |
| Бесконечное расширение игры | Цвет/размер/темп/пара уровней/простая механика | Выполнить уточнённый объём кейса |
| Старые данные, контроллеры и конвертеры | Чистые таблицы и один новый процесс | Не воспроизводить легаси |

Точечные проверки и качественный интерфейс сохраняются. Скорость не достигается
выдачей шаблона, пропуском безопасности или маркировкой непроверенного кода как готового.

## 2. Скорость как критерий разработки

Предварительные внутренние цели на прогретом стенде, одном активном запросе и выбранной
модели. Не являются требованиями организаторов и пока **не измерены**.

| Метрика | Первичный ориентир |
| --- | --- |
| Принятие запроса и понятный статус | до 1 секунды |
| Создание: отправка → проверенная playable-версия | p50 ≤ 30 с, p95 ≤ 60 с |
| Малая правка: отправка → проверенная новая версия | p50 ≤ 10 с, p95 ≤ 20 с |
| Накладное время приложения без модели и очереди | до 5 с для обычного smoke-сценария |
| Вызовы модели без ошибки | 1 создание / 1 доработка |
| Автоматические корректирующие вызовы | максимум 1 на пользовательскую операцию по умолчанию |
| Перезапуск при повторном открытии готовой игры | 0 модельных запросов |

Считать отдельно очередь, ожидание модели, первый токен, конец ответа, упаковку,
проверку и доставку preview. Основное время включает **все** эти этапы; нельзя выдать
анимацию загрузки за playable-результат. Холодный запуск, прогретый и нагрузочный режимы
публикуются раздельно. Внутренние ходы Codex не прячутся за одним вызовом адаптера.

Цель 60 секунд не является обрывом на 60-й секунде. Если ответ идёт, показать задержку
и отмену. Ошибки/отказы не перезапускаются бесконечно: сохранённый результат и явное
продолжение доступны пользователю. Общее время, output size и число внутренних запросов
используются для выбора модели и упрощения процесса, а не для сокрытия ошибок.

Пилот — пять разных коротких запросов и по две небольшие правки. Сначала показа
индивидуальных результатов достаточно; для устойчивых перцентилей нужен более широкий
согласованный по бюджету набор (ориентир ≥20 наблюдений на тип операции, с оговоркой
об ограниченной выборке). Не обещать точный p95 по двум удачным играм.

### Этап 1 — минимальная рабочая оболочка и контракты

**Сделать.** Новый Django/DRF-проект, PostgreSQL 18+, Celery/Redis, React/TS/SCSS и Compose.
Один репозиторий, модули по назначению; конкретные пути появляются вместе с кодом,
а не заранее как десятки пустых пакетов. Зафиксировать зависимости lock-файлами.

Реализовать сессии/CSRF, login/logout, init после миграций, уникальность username без
учёта регистра. Начальные сущности Chat, Message, Run, Revision, Invocation; простой
экран чата и истории. Разделить приложение и origin для игры уже на локальном стенде.
Обозначить статус ошибки, отмены и восстановления. Согласовать API с фронтендом до
детальной вёрстки: поля, ошибки, состояния и reconnect событий, mock fixtures по тем же схемам.

Ввести минимальный outbox, idempotency запроса, lease/fence для записи результата и
сохранение ответа перед переходом. SSE с ID события и восстановлением после разрыва;
Redis не хранит единственную копию истории. Отдельный тестовый провайдер отдаёт явно
помеченный fixture: он проверяет проводку, а не качество генерации.

**Проверить.** Чистый запуск; повторный bootstrap без смены пароля; гонка username;
вход/выход/CSRF; чужой chat ID; запрос→сохранённый fixture→preview; повторная доставка
Celery не создаёт вторую версию; перезапуск сохраняет историю и прогресс.

**Выход.** Один воспроизводимый локальный сценарий с заглушкой и задокументированные
команды запуска. Начальная архитектура изоляции проверена; ложного статуса «LLM работает» нет.

### Этап 2 — первая быстрая генерация через локальный Codex

**Сделать.** Прототип адаптера на фактически установленном интерфейсе Codex. Проверить
штатный вход, доступные модели, события, schema/JSON, usage и отмену. Не переносить
авторизацию пользователя в контейнеры/CI и не менять глобальную конфигурацию ради приложения.
Ограничить инструментальные возможности и файловый доступ реальными средствами среды.
Если это невозможно, зафиксировать блокер транспорта, не включать небезопасный режим.

Один ответ содержит компактный дизайн, файлы игры и короткие сценарии. Модель генерирует
код игры, а не адаптирует готовый жанровый шаблон. Небольшие красивые Canvas-ассеты,
читаемость, композиция и обратная связь входят в prompt; отдельный model reviewer не обязателен.

Добавить локальную упаковку HTML, неизменяемое сохранение, static checks и настоящий
изолированный браузер. Проверять запуск, реальный touch/keyboard input, основной эффект,
исход, отсутствие сетевых ресурсов и работу при компактном viewport. Кнопки и состояние
определяет игра; проверка не ищет обязательный текст «Restart».

**Проверить.** Фикстуры исправной и сломанной игры, запрет сети/escape, запрет самозачёта,
реальная модель хотя бы для трёх разных механик в согласованном бюджете. Проверить отмену
во время ответа, отказ модели, битый ответ и недоступность браузера — это разные причины.
Снять первые времена и число вызовов **до** расширения функций продукта.

**Выход.** Можно лично ввести короткий запрос, получить первую настоящую мини-игру,
сыграть и скачать HTML. Это первая точка пользовательского тестирования, не финал проекта.
Если время неприемлемо, сначала исправить этот путь, не добавлять новые роли и функции.

### Этап 3 — точечные правки, восстановление и история

**Сделать.** Edit-контракт с base revision/hash, точными заменами и необязательными
typed config patches. Применение атомарное, вне допустимых путей невозможно. При
конфликте модель получает конкретное объяснение, полного rewrite fallback нет.
Перекраска не пересоздаёт механику; новое название не требует повторной генерации игры.

Сохранять prompt/answer, кандидат, diff, usage и отчёт до подтверждения результата.
На ошибку — одна локальная автоправка; затем отдельное продолжение с кандидата по решению
пользователя. Последняя рабочая версия остаётся доступна. Ошибка соединения с неизвестным
результатом не вызывает слепой оплаченный повтор. Один writer на чат, независимые чаты.

Каждая правка наследует обязательные эффекты, проверяет затронутый и короткий базовый
набор. Коррекция неправильного теста разрешена, незаметное удаление эффекта — нет.
Подтверждённый отчёт неизменившихся байтов используется повторно.

**Проверить.** Цвет, размер кнопки, скорость, два уровня; совпадение hash нетронутых файлов;
игра после каждого изменения; stale/неоднозначный patch; двойной клик; отмена и поздний
ответ; worker crash после ответа; два чата с похожими именами; новая сессия браузера.

**Выход.** Полный путь «создать → сыграть → изменить локально → снова открыть ту же игру».
Нет полного перепланирования или перегенерации для простого изменения.

### Этап 4 — публикации, лента и ремиксы

**Сделать.** Publication владеет ссылкой на точный прошедший проверку артефакт отдельно
от Chat. «Поделиться», название, «Обновить», «Мои публикации», удаление, сортировки.
Лайки с уникальностью и идемпотентным повтором. Карточки автора и игры.

«Доработать» копирует опубликованную Revision в новый личный чат; сообщения исходного
чата не копируются. Источник ремикса фиксируется отдельно как происхождение.
Удаление чата не уничтожает публикацию/ремикс и не оставляет активного задания.
Новая правка автора не обновляет ленту до явного действия.

**Проверить.** Два аккаунта, закрытость черновиков, опубликованный hash после правки,
явное обновление, удаление чата/публикации отдельно, копия именно публичной версии,
пустая история ремикса, гонка лайков, отсутствие повторной LLM-проверки при публикации.

**Выход.** Все функции F09–F13 работают на стабильных снимках и правах доступа.

### Этап 5 — полный согласованный интерфейс и обратная связь

**Сделать.** Лендинг и login в светлой теме; авторизованный интерфейс с двумя темами.
HTML/SCSS/TS-декор, читаемость, игровые детали без избыточного усложнения.
На ПК — сворачиваемая панель чатов, чат и телефонный preview ≥ половины экрана.
На mobile — удобный переход в fullscreen и обратно. Клавиатура не должна оставаться
зажатой при уходе фокуса; fullscreen не захватывает управление оболочкой.

Кнопки аудитории меняют контекст LLM. Карточки ленты дают лёгкое hover-preview, не
запускают десятки игр одновременно. На телефоне есть явное «Попробовать».
Показать реальные стадии, ошибки и сохранённый результат; не рисовать фиктивный процент.

Оценка 1–5; при <5 необязательные причины. Хранить короткий набор предпочтений и
добавлять в следующие запросы. Пользователь может их сбросить/изменить; оценка сама
не отправляет запрос модели. Историю чата не превращать в бесконечный системный prompt.

**Проверить.** Полная F01–F14 матрица на ПК и телефоне, обе темы, две точки входа,
без регистрации, focus/keyboard/fullscreen, 20 карточек без 20 работающих игр,
влияние feedback на следующий prompt без утечки чужих данных.

**Выход.** Продукт соответствует согласованному файлу фронтендера, а не только техническому демо.

### Этап 6 — переход на API локальной LLM

**Сделать.** Второй provider adapter к vLLM. Сначала probe реального endpoint: модель,
chat template, схема ответа, streaming, usage, лимиты контекста и отмена. Настройки
API и модель — серверная конфигурация; UI обычного создателя не просит API key.
Не переносить обязательные Codex/Responses-функции в общий контракт.

Два адаптера имеют общие тесты create, patch, partial output, refusal/error, cancel и
идемпотентной записи результата. Fake API-сервер проверяет протокол, но не качество LLM.
После выдачи endpoint повторить часть того же набора игр и правок настоящей моделью.
Если она не справляется с одним ответом/патчем, исследовать настройки и prompt на
фиксированных примерах; не достраивать молча десятиступенчатого агента.

**Проверить.** Смена адаптера без изменения чатов/публикаций; edit игры, созданной другим
поддерживаемым адаптером; ошибочный schema output; медленный/оборванный stream;
раздельные latency/usage. Отсутствие API-цены у локальной модели не равно отсутствию работы.

**Выход.** Реальный API локальной модели работает в том же продукте и имеет отдельный отчёт.
Если сервер пока не выдан, протокольная часть завершена, живое испытание честно остаётся открытым.

### Этап 7 — проверка всей поставки, скорости и WebView

**Сделать.** CI по мотивам ML-ветки, но под новую реализацию: backend lint/types/tests,
frontend lint/types/tests/build, PostgreSQL 18+/Redis integration, browser, security,
сборка и запуск контейнеров. Нет неработающих заданий от удалённых модулей. Live evals
запускаются отдельно с явным бюджетом, не на каждый commit и не по старому расписанию.

Воспроизводимый прогретый стенд, пять разных запросов + малые правки, сохранённые
prompt/model/version/latency/usage/качество. Сначала функциональный прогон, затем
достаточная для выбранной метрики серия в пределах бюджета. Не смешивать фикстуры,
кеш повторной выдачи и новые генерации. Не скрывать ошибки из знаменателя успешности.

Проверить очередь на 1/3/10 конкурирующих заданиях с fake provider и ограничения
настоящего провайдера отдельно. Число одновременно исполняемых запросов настраивается:
для Codex начать с одного, для vLLM — по замерам. Десять поставленных в очередь заданий
не объявляются десятью одновременными inference. Оценка пропускной способности ML-ветки
не переносится без нового измерения.

Проверить offline HTML в мобильном браузере и доступной настоящей Android WebView /
WKWebView-оболочке. Конкретный хост Билайна неизвестен; если устройства нет, это остаётся
ограничением, а не закрытым тестом по скриншоту телефона.

Подготовить локальную демонстрацию 3–5 минут, README/runbook с фактическими командами,
чистую установку и восстановление. Размещение на `digsy.ru` — после готовности и доступа
к инфраструктуре; план не означает автоматическую публикацию сейчас.

**Выход.** Все обязательные и согласованные продуктовые сценарии подтверждены, известны
фактические скорость и ограничения обеих конфигураций. Есть короткая демонстрация и история Git.

### Этап 8 — дополнительные баллы, вне базового выпуска

Учёт прошлой аналитики на явно обозначенных синтетических данных, одна объяснимая
рекомендация для следующей игры. Отдельные image/audio инструменты — только если
подтверждена ценность и они не задерживают базовую генерацию. Эти функции не блокируют
первую playable-версию и не превращают мини-игру в исследовательский проект.

## 4. Матрица ключевых проверок

| Область | Позитивный сценарий | Обязательная отрицательная проверка |
| --- | --- | --- |
| Генерация | Разные короткие запросы дают работающие новые игры | Заглушка/зашитая игра не считается живой генерацией |
| Ввод | Touch, keyboard, hold/release где применимо | Неработающая стрелка/кнопка, потерянный pointer, залипание после blur |
| Механики | Смысловой эффект и игровой исход | Счётчик меняется, но действие не работает; запрещённый ход правильно не меняет состояние |
| Изображение | Читаемость, цель, элементы управления, состояние победы/поражения | Пустая сцена, мелкие элементы, обрезанные кнопки, ложный успех по одному pixel diff |
| Патч | Цвет/размер/темп/уровни меняются локально | Stale hash, неоднозначная замена, выход пути, перезапись всей игры при перекраске |
| Восстановление | Сохранённые ответы и рабочая версия доступны после перезапуска | Повторная доставка, потеря подтверждения, поздний ответ после cancel |
| Секреты/preview | Изолированный запуск и offline экспорт | Доступ к cookies/БД/внутренней сети/хосту, popups/top-navigation |
| Аккаунты | Case-insensitive уникальность и права | Дубль регистра в гонке, чужой chat/revision, CSRF |
| Публикация | Явный снимок, обновление, независимый ремикс | Неопубликованная правка попадает в ленту, delete chat удаляет игру |
| Лента/feedback | Идемпотентный лайк, управляемые предпочтения | Рост лайков от дублей, скрытый запуск LLM при оценке, десятки live iframe |
| Провайдер | Одинаковая схема create/edit | Неверная schema, обрыв, отказ, неучтённый внутренний retry |
| Скорость | Измеренный путь от отправки до игры | Очередь исключена из времени, непроверенный preview засчитан как готовность |

Базовые проверочные игры: пошаговая сетка, непрерывное управление, головоломка,
кликер с конечной целью, короткий runner. Это набор испытаний, не каталог готовых игр.
Добавить вариант после фиксации prompt, чтобы не подгонять продукт только под известные случаи.

## 5. Организация работы и ограничения

Сначала этапы 1–3: рабочий путь, реальные замеры и точечное редактирование.
Далее 4–5: весь согласованный продукт; 6: реальный второй провайдер; 7: итоговая приёмка.
Разработка протокола vLLM и UI на согласованных fixtures может идти независимо, если
транспорт или бюджет временно недоступны. Не ждать полного frontend polish для первой LLM-пробы.

Предлагаемая ответственность: backend — состояния/права/патчи/версии/очередь; ML —
prompt/provider/evals/скорость; frontend — F01–F14 и общий API-контракт. Это распределение
для команды, не поручение рассылать сообщения или запускать дополнительных агентов.

Перед платными испытаниями установить новый доступный бюджет. Текущая задача очистки
и планирования его не расходует. Отсутствие бюджета не мешает бесплатным проверкам,
но не позволяет отметить реальную генерацию как испытанную.

После каждого этапа обновить его статус, README и `game-creation-model.ru.md`, указать
сделанное, команды проверки и доказательства. Изменения продукта делать маленькими
осмысленными коммитами; не force-push и не переписывать историю ML-инженера.

## 6. Готовность

- [ ] Реальная мини-игра создаётся по короткому запросу и проверяется без обязательной цепочки ролей.
- [ ] Небольшие правки применяются патчами и сохраняют незатронутую механику.
- [ ] Есть история, отмена, продолжение после ошибки и последняя рабочая версия.
- [ ] Весь согласованный frontend-сценарий F01–F15 реализован и проверен.
- [ ] Публикации, обновления, лайки, удаление чата и ремиксы имеют правильную независимость.
- [ ] Codex испытан локально; vLLM испытан на реальном endpoint либо явно указан внешний блокер.
- [ ] HTML работает offline; реальные браузерные и доступные WebView-проверки перечислены честно.
- [ ] Скорость, число вызовов и доля успехов измерены; провал цели не замаскирован формальным pass.
- [ ] Нет исполняемого легаси, старых миграторов и зависимости от GamesForgeEx.
- [ ] Документация, установка, CI и демо соответствуют работающей версии.
- [ ] Команда подтверждает 2–4 участников и готова к презентации 3–5 минут; точные сроки сверены с регламентом.
