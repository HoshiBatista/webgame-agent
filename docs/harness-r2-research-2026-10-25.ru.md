# Исследование причин сбоев Lite и пересмотр следующей поставки

25 октября 2026 года. Основа — закрытый повторный пилот v8, исходники его 14 ревизий,
точные запросы и ответы, текущий контроллер и первичные источники пяти харнессов.

**Главный приоритет — довести цикл до ремонта игровой логики с достоверной обратной
связью.** В основной серии было 12 вызовов create, 6 check_repair и 3 source repair.
Все три source repair исправляли синтаксис. Попыток ремонта логики memory или движения
snake не было. Поэтому этот прогон показывает слабое качество создания и проверки,
но ещё не измеряет способность 27B исправлять механику по корректному воспроизведению.

Нужны исправления валидатора, короткая трасса реальных действий и разделение требований
пользователя со сценариями модели. Новый универсальный язык сценариев и обязательная
цепочка planner → coder → critic пока не обоснованы.

[Данные исследования](evidence/harness-r2-research-2026-10-25.json),
[исходный пилот](lite-v8-r2-pilot-2026-10-25.ru.md),
[предыдущая архитектурная гипотеза](lite-27b-research-and-plan-2026-10-25.ru.md).

## Что фактически препятствует готовности

В девяти созданиях все Run завершились; базовая играбельность — 3/9, автоматическое
принятие — 0/9. Full + compact string повторили прежние 2/6. Эти числа не доказывают
преимущество нового профиля или предел возможностей модели: по каждой комбинации
запроса и профиля есть только одна попытка.

| Наблюдение | Подтверждение | Следствие для следующей поставки |
| --- | --- | --- |
| Ошибки сценариев препятствуют выполнению игровых действий | Запрет checkpoint перед eq затронул grid lines, snake lines и memory string; в других играх были неверные координаты, недоступные наблюдения и wait_for посреди сценария | Сначала упростить интерпретацию существующих сценариев и показать фактически выполненные действия |
| Ремонт получает несовпадение, которое само по себе не различает ошибку теста и игры | Рабочий full-grid и сломанный snake имеют effect_mismatch | Нужна воспроизводимая диагностика до выбора check_repair или source repair |
| Исходное требование может быть искажено уже первым ответом | Пользователь: победа после обеих пар. Memory string: «При совпадении пары — победа» | Не считать requirement из первого ответа независимой спецификацией |
| Возможность заменить малый модуль уже есть | Все три source repair получили разрешение на game.js; два устраняли обрыв full-memory | Повторное введение замены модуля ничего не добавит; важны правильная задача и формат входа |
| Compact repair получил исходник, но заявил, что его нет | В prompt было 5041 байт source, одновременно files={} | Разделить compact-промпты по операции; проверить эффект на том же сохранённом кандидате |
| Наблюдения могут теряться или устаревать | Lines-memory экспортирует копии скалярных полей; небезопасное поле cards мешает каталогу перечислить безопасные соседние поля | Исправить диагностику свойств; объяснить контракт живого состояния без тестовых флагов |
| Формат JSON тоже расходует попытки | Два lines-create пропустили обязательные поля; два check_repair вернули unchanged с непустыми сценариями | Проверять форму отдельно от качества механики; сохранить строгий допуск, уменьшить неоднозначность операции |

Источник маршрутизации — [needs_check_repair](../generation/check_repair.py),
[выбор операции](../studio/tasks.py), [политика принятия](../studio/acceptance.py).
`effect_mismatch` входит в CHECK_FINDINGS и при выполненных artifact gates сначала
ведёт в check_repair. После одной попытки на hash новые сценарии требуют человека;
смешанный failed/unverified результат также может завершиться review. Это защищает
рабочий код от ремонта по плохому тесту, но оставляет мало возможностей исправить
семантический дефект. Простое удаление этой защиты опасно: full-grid пришлось бы
портить ради ошибочной последовательности ходов.

Ноль автоматических принятий нельзя использовать как единственную метрику качества:
оба контролируемых check_repair прошли 3/3 и всё равно требуют подтверждения по текущей
политике. Отдельно измеряются реальная играбельность, покрытие требований, достоверность
проверки и возможность автоматического принятия.

## Проверки гипотез без модели

Шесть успешных запусков изолированного Chromium использовали сохранённые артефакты
или маленькую отрицательную fixture. Исходники приложения не менялись: все 47 hashes
совпали с manifest пилота. Отчёты экспериментов не записывались в CheckReport, игры
не принимались и не публиковались. GPU, облачный сервер и Codex не изменялись.
Новых модельных вызовов — 0; прежний бюджет остаётся закрытым.

### Разрешение checkpoint перед конечным сравнением

Во временной копии валидатора убран только запрет одного checkpoint перед абсолютным
сравнением. Ограничение числа checkpoint, граница подготовки, требование игрового ввода,
ожидания, контрольный запуск и код игры сохранены. Проверены последние ревизии трёх игр.

| Игра | Результат опыта |
| --- | --- |
| Grid lines | Начало и управление проходят; исход становится effect_mismatch, status остаётся playing. Сценарий расставляет X в клетках 0, 6, 4, а O в 8, 2: заявленной диагонали X нет |
| Snake lines | Начало проходит; три проверки управления и столкновение дают effect_mismatch. Известный дефект dt остаётся |
| Memory string | Начало проходит; остальные сценарии по-прежнему недопустимы из-за нескольких checkpoint, включая checkpoint после ввода |

Это подтверждает лишний барьер в интерпретации теста, но не рост играбельности.
Нельзя просто удалить все checkpoint: они задают измеряемый участок, и удаление
последнего checkpoint может принять подготовку за проверяемое управление.
Нельзя автоматически заменить changed на eq или выдумать выигрышную последовательность.

### Случайность между основным и контрольным запуском

Текущий runner проверяет причинность на двух отдельных страницах. Без test_profile
каждая получает независимый Math.random. Отрицательная fixture выставляет одно
случайное булево поле при загрузке и вообще не обрабатывает ввод. Двенадцать сценариев
нажимают ArrowUp и проверяют это поле.

**Две из двенадцати проверок ошибочно получили passed**, потому что значение случайно
совпало с ожиданием в основном запуске и не совпало в контрольном. При том же HTML
и существующем test_profile с seed=1 все двенадцать стали unverified: одинаковое
значение в обоих запусках перестало выглядеть эффектом ввода.

Общий отчёт отрицательной fixture был failed; полноценную игру этот опыт не принял.
Доказан дефект отдельного свидетельства причинности. Это не доказательство, что именно
он испортил девять игр пилота. Одинаковый seed устраняет показанный источник расхождения,
но не гарантирует равенство времени, внешних событий и всей предыстории.

Нужно сравнивать воспроизводимые условия пары запусков, хранить профиль в идентичности
свидетельства и не объявлять причинность установленной при неизвестной сопоставимости.
Обычное прохождение с естественными временем и случайностью остаётся отдельной проверкой.

### Причина игрового исхода не всегда последнее действие

Дополнительная положительная fixture — короткий раунд со счётом: ArrowUp увеличивает
счёт, через 1500 мс раунд заканчивается и рисует результат, дальнейшие нажатия уже
не меняют счёт. Начало и управление прошли проверку. Сценарий нажатие → ожидание
1700 мс → over=true тоже фактически выполнился, но стал unverified, потому что
без последнего нажатия время также истекает.

Это показывает избыточность универсального правила «любой исход должен исчезнуть
без последнего ввода». Для истечения времени или столкновения при непрерывном
движении событие может быть корректным в обоих запусках. Контроль направления требует
своего свидетельства, а завершение раунда — свидетельства своего условия.

Проверку причинности нужно выбирать по проверяемому эффекту. Нельзя просто выключить
её для всех outcome: тогда вернутся постоянные флаги победы и декоративные счётчики.
Вместо этого задаётся подходящая контрольная ситуация либо явное свидетельство
временного/игрового условия, а неоднозначность остаётся видимой. В оценочном корпусе
обязательно иметь как положительную таймерную игру, так и отрицательную имитацию исхода.

### Подтверждённые ранее дефекты приложения

Ожидание 10 100 мс в сценарии превращается в validator_unavailable ещё до запуска
браузера. Следует вернуть invalid_check и выполнить обязательные artifact gates
в пределах безопасного watchdog. Recheck должен сохранять код и делать 0 inference.

В compact runtime paint находится внутри условия game.update. Разрешённый контрактом
модуль без update не перерисовывает изменения setTimeout до следующего ввода.
Нужна отрисовка в общем цикле и регрессия на реальный пиксель после таймера. При этом
необходимо проверить существующие модули: чаще вызываемый render не должен менять
механику или состояние. Исправление runtime не исправляет правила сопоставления пар.

## Какие прежние предложения меняются

**Новый формат setup → action → expectation отложить.** Он облегчает часть ошибок,
но компилятор компактных probes уже существует, а выигрышная последовательность и
смысл ожидаемого результата остаются задачей модели. Сначала следует измерить более
простую семантику текущего checkpoint и добавить наблюдения между шагами.

**Одного живого state и чистого render недостаточно.** Это полезная дисциплина compact,
но runtime не может автоматически доказать, что любое объявленное поле связано с
правильной механикой. Требуется проверка через действия и видимый результат. Не нужно
запрещать все локальные переменные или принуждать full к универсальному state/HUD.

**Сокращение prompt — гипотеза, а не найденная причина всех неудач.** Учтённые входы
основной серии — 898–6829 tokens; переполнение контекста этим прогоном не установлено.
Установлена конкретная неоднозначность source/files и общий compact PROMPT для разных
операций. Их стоит устранить и сравнить на одинаковых базах.

**Compact не включать всем.** Lines устранил наблюдавшуюся потерю скобок и дал читаемые
исходники, но качество правил остаётся низким. Full сохраняется как рабочий контроль,
compact lines — как экспериментальная ветка текущего контроллера. Codex остаётся
доступным провайдером, без автоматического расходования его вызовов.

**Ремонт логики сначала испытать на сохранённых кандидатах.** Очередной набор случайных
созданий смешает качество первого ответа, проверок и ремонта. Работающий grid с плохим
сценарием и сломанные snake/memory дают более информативные контрольные пары.

## Предлагаемая поставка

### R0 Исправность среды и свидетельств

Исправить watchdog и общий render loop. Добавить отрицательный тест случайного
состояния без обработки ввода и реализовать сопоставимые контрольные запуски с явной
идентичностью. Разделить доказательство управления и проверку условия завершения:
положительная игра с таймером не должна блокироваться лишь из-за того, что таймер
не зависит от последнего нажатия. Упростить единственный checkpoint перед конечным сравнением,
сохраняя границу подготовки; несколько неоднозначных checkpoint оставлять ошибкой.
Исправить каталог наблюдений: пропускать запрещённое свойство без выполнения getter
и без потери разрешённых соседей. Ограничения глубины, размера и времени сохраняются.

Файлы: validation/contracts.py, service.py, runner.py, checks.py, diagnostics.py;
generation/runtime/compact-v1.js. Приёмка: воспроизводимые положительные и отрицательные
браузерные тесты, повтор сохранённых артефактов, отсутствие ложных passed на известной
отрицательной fixture, новые receipts после изменения validator hash. Source bytes
неизменны во всех recheck. Без новых вызовов модели.

### R1 Наблюдаемая диагностика перед ремонтом

Дополнить существующий запуск короткой трассой: фактическая цель ввода, несколько
безопасных наблюдений перед действием и после него, первый расходящийся шаг, ошибки
выполнения. Для compact достаточно объявленных полей и небольшого каталога доступных
соседей; для full используются видимый DOM и разрешённые plain-state пути. Скриншот
полезен человеку, но доступность vision у нашего Lite не подтверждена.

Сначала выполнить это одним браузерным пакетом, без отдельной модели и постоянной
браузерной сессии. Сохранить полный ограниченный отчёт; в repair передавать один
воспроизводимый симптом, относящийся к актуальному source hash. Не менять ожидание
на фактически полученное значение.

Для неоднозначного результата отдельным экспериментом разрешить один ограниченный
диагностический запрос: модель предлагает реальные действия и поля для чтения,
приложение исполняет их и возвращает факты. Это данные для диагностики, не новый
acceptance suite и не разрешение изменять требования. Суммарный лимит вызовов остаётся
общим; модель не получает shell, произвольный evaluate или запись в состояние игры.

Файлы: validation/runner.py, diagnostics.py; generation/feedback.py, prompts.py,
compact.py; выбор следующего шага в studio/tasks.py и studio/check_repair.py.
Приёмка без inference: трасса показывает неверный маршрут рабочего grid, отсутствие
движения snake и неразрешённую пару memory; старые версии и checks сохраняются.
Проверить точный конечный prompt, включая усечение диагностики и выбранный формат repair.

### R2 Требования отдельно от предложенных тестов

Сохранённый game_request и явные пользовательские изменения остаются первичным
источником требований. Текст requirement в модельном probe — утверждение автора
сценария; его нельзя автоматически объявлять независимой спецификацией.

Для оценочного набора заранее закрепить требования вне генерируемого ответа. Для
свободного пользовательского запроса хранить связь предложенного условия с исходной
фразой и статус проверки покрытия. Совпадение цитаты само по себе не доказывает
правильность интерпретации. Автоматическое понимание произвольных правил остаётся
модельной задачей; сложные или непроверенные условия должны оставаться видимыми.

Раздельно хранить требование, способ его наблюдения и вердикт исполнения. Исправление
плохой привязки не должно переписывать историю исходного ответа. Смысловой пересмотр
требования или нового acceptance suite сохраняет явное подтверждение. Нельзя просто
снять check_suite_revised ради роста метрики готовности.

Добавить два разных основания продолжения: доказанный дефект исполнения и гипотеза
о дефекте механики. Гипотеза позволяет исследовать кандидат в экспериментальном
режиме; она не доказывает готовность. Для incomplete checks сохраняется действующее
правило: автоматический source repair только по актуальному независимому основанию.
Расширять это правило на механику можно после подтверждённых воспроизведений,
а не по одному effect_mismatch или мнению critic.

Приёмка: memory не теряет требование обеих пар; исправление сценария рабочей игры
не запускает переписывание её кода; ложный «успех» от тестового флага/случайного поля
не принимается; неоднозначный случай сохраняется как неподтверждённый.
Изменения контракта и политики следует описать вместе с реализацией в AGENTS.md
и архитектуре. В этом исследовании действующие правила не изменены.

### R3 Измерение полезности нового цикла

После локальных регрессий и ревью провести отдельный согласованный эксперимент
на фиксированных сохранённых базах. Сначала проверить ремонт; затем новые создания.

| Контроль | Что должен показать |
| --- | --- |
| Рабочий grid с плохими координатами/маршрутом | Тест исправляется, код остаётся прежним, исходное условие выигрыша сохраняется |
| Snake с дефектом dt | Исправляется движение и исход, сохраняется рабочее управление; проверяется также обычное время |
| Memory с незавершением пары | Обе реальные пары дают победу, mismatch закрывается; дополнительные независимые сценарии ловят частичный ремонт |
| Syntax error в малом модуле | Узкий repair получает реальный source и возвращает допустимую правку вместо ложного отказа |
| Дефект наблюдений при рабочем коде | Диагностика не вынуждает переписывать механику ради удобного тестового состояния |

Сравнивать текущий и изменённый контекст на одинаковых базах и одинаковом лимите,
с несколькими повторениями. Критерии оценки заранее фиксировать, часть проверок
не передавать в ремонт. Считать исправленные причины, регрессии, ложные принятия,
необоснованные изменения кода, вызовы/tokens/время. Не выбирать удачный seed постфактум.

Для новых созданий использовать несколько повторов и дополнительные запросы вне
grid/snake/memory, чтобы не настроить весь продукт на три известных примера. Отдельно
считать первый ответ и результат после ремонта. Повтор партии проверять, если он
заявлен/предоставлен или включён в заранее выбранную рубрику; не подменять этим
прежнее определение базовой играбельности. Автоматическая готовность требует полного
актуального набора подтверждённых условий.

Новый бюджет этим документом не открывается. Если ремонт по качественной диагностике
по-прежнему не работает, следующим контролируемым опытом сравнить генерацию кода
отдельно от сценариев. Только после такого сравнения решать об обязательном втором
вызове или более сильной модели. Алиас qwen38 не устанавливает точные веса,
квантование и server defaults; GPU-сервер для этой работы не требуется менять.

## Порядок решения

Начать с R0 и трассы из R1. Параллельно по смыслу работы, без дополнительных модельных
ролей, зафиксировать тестовый корпус и правила требований из R2. Затем выполнить R3
на сохранённых базах. Отдельный inference planner, новый DSL, жанровые шаблоны и
расширение числа бесконтрольных попыток в ближайшую поставку не входят.

Это более узкая и проверяемая гипотеза: модель должна получить настоящий дефект
механики и возможность исправить именно его, а решение о готовности должно опираться
на пользовательское требование и наблюдаемую игру.
