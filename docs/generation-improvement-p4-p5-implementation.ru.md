# Улучшение генерации: поставка P4–P5 и ревью B

Дата: 27.10.2026. Ветка `mini-games`; основание Git `815f2b2` плюс незакоммиченная
поставка P0–P3. Исполнены P4–P5 из
[плана](generation-improvement-plan-2026-10-27.ru.md). Это локальная реализация с
тестовыми провайдерами, не живое измерение качества 27B/Sol и не выкладка.

## Что изменено

### Замысел и обещания до кода

Planning v2 описывает действие игрока, выбор или ограничение, последствия,
развитие, достижимый исход и 3–8 наблюдаемых обещаний с постоянными ID. Lite:
одна основная и максимум одна вспомогательная механика; Pro: до четырёх,
без обязательного увеличения объёма. Простой или статичный запрос остаётся
допустимым. Отказ имеет `plan=null`, объяснение и `status=scope_refusal`.

Проверяются структура, уникальность ID, мобильные начало/управление, исход,
точная ссылка на запрос и происхождение каждого обещания. `origin=user` требует
цитаты запроса; модельные дополнения явно имеют `origin=design`.

`Run.requirement_manifest` сохраняется атомарно с планом, до первого исходника,
и копируется в Revision и ремикс. Реализация/ремонт не могут заменить обещания
своими названиями проверок. Проверяется совпадение ID/category/requirement/viewport;
недостающее или подменённое обещание не даёт автоматического или ручного принятия.
Исправление сценариев получает исходные обещания, а не переопределения из кода.
Manifest входит в identity отчёта, поэтому старый pass не переносится на другие обещания.

Для подробного Lite-запроса без plan сохраняются исходный текст и его hash с областью
`user_request_unmapped`: приложение не заявляет, что разобрало его смысл. Явная
пользовательская правка создаёт новый manifest с исходным запросом, историей поправок
и hash предшественника; область `user_amendment_unmapped`. Прежний план остаётся
контекстом, правка имеет приоритет и не запускает новое планирование. Без отдельного
разбора смысла нельзя утверждать, что все произвольные требования такого запроса покрыты.

Предпочтения и версии правил закреплены в Run до отправки. Снимок включает hashes
реализаций prompt/schema/repair/check policy и runtime; каждый Invocation по-прежнему
хранит hashes фактически отправленных инструкций и схемы. Изменение предпочтений
не меняет продолжение/ремонт. Изменение правил запрещает новый вызов, в том числе
после восстановления ранее зарезервированного, но ещё не отправленного Invocation.
Уже отправленный durable receipt при этом по-прежнему получают и учитывают.

### Compact runtime 2

Один requestAnimationFrame вызывает render и при отсутствии update. Render обязан
рисовать, правила изменяются через input/update/таймеры самой механики. API
`resetInput()` освобождает удержанные клавиши/указатели при рестарте; отпускание,
blur, pointercancel и потеря capture не оставляют удержанные действия. Координаты
`x/y` — логические единицы мира, `nx/ny` — ограниченные 0..1; resize сохраняет
состояние и пересчитывает отображение с учётом DPR.

Кнопки располагаются сеткой, длинные подписи занимают максимум две строки, полный
текст доступен через accessible name/title. Высота панели ограничена, предусмотрена
прокрутка на малой высоте; Canvas сохраняет ненулевое место. Жанровых шаблонов,
обязательного HUD, поля карточек или карты не добавлено.

### Эксперимент Lite: код, затем сценарии

Настройка `GAMEFORGE_LITE_CODE_THEN_CHECKS_ENABLED=1` выбирает стратегию
`lite_code_then_checks` только для новых Lite/compact Run. По умолчанию **выключена**.
Флаг не меняет уже созданный Run и не переключает профиль full на compact.

Последовательность: необязательный plan → create с модулем/controls/observations,
без probes → обязательные проверки артефакта → checks_create → исполнение сценариев.
При доказанном дефекте кода сначала разрешён ограниченный source repair.

`checks_create` получает точные base UUID, artifact/checks/manifest hashes, report ID,
identity и неизменяемые требования. Его схема не принимает исходники/патчи/новые
правила. Материализация повторно проверяет привязки и сохраняет все исходные байты.
Изменение отчёта/исходника/обещаний делает разрешение устаревшим. Составленные моделью
сценарии требуют проверки условий человеком даже после успешного браузерного прогона.

Общий предел остался 4 вызова без планирования / 5 с ним, либо меньший лимит
пользователя. Дополнительный этап занимает один из существующих слотов; скрытого
увеличения расхода нет. Неизвестный результат не повторяется. Отказ/некорректный ответ
останавливают составление сценариев, код остаётся кандидатом. После лимита между
кодом и сценариями можно явно продолжить со стадии сценариев. Без модели recheck
не превращается в checks_create.

Сохранённые ответы, атомарная привязка Invocation→Revision, lease/fence и cancellation
используются общие. Проверены аварии до и после сохранения кода, после gates, после
получения сценариев и после их сохранения; повторная доставка не удваивает кандидаты.
Durable relay проверен локальным HTTP-двойником. CLI/API Codex и их изоляция сохранены;
сервисы/очереди/разрешения инструментов не расширялись.

Ремонт выбранного малого модуля получает его исходник, ограниченный интерфейс,
неизменяемые обещания, основной дефект и последнюю ошибку применения. Остальные
исходники не включаются в модельный контекст. Замена и точные патчи ограничены этим
модулем. Исходные checks сохраняются; валидный минифицированный JS допустим,
поглощающий `//` диагностируется, границы кода не восстанавливаются по догадке.

## Ревью B

Повторно просмотрены границы P3–P5: происхождение критериев, сохранение обязательств,
разрешение source/check repair, бюджет, неизвестный исход и восстановление.
Исправлены обнаруженные при реализации/ревью проблемы:

1. Длинные подписи compact вытесняли кнопки за экран — сетка и ограничение строк;
   регрессия в реальном изолированном браузере.
2. При выборе малого модуля точный patch мог затронуть другой файл — проверяется
   область всех патчей, не только replace_module.
3. UI запрещал продолжение после лимита между кодом и сценариями — открывается
   только ещё не использованный этап checks_create с актуальными gates.
4. Восстановленный reserved вызов мог обойти проверку смены политики — добавлена
   проверка перед отправкой; уже отправленные receipt сохраняют приоритет.
5. Старый кандидат мог попасть в новый браузерный путь — unsupported pipeline
   останавливается до исполнения; учёт вызовов не удаляется.

Модельный manifest не превращается в независимый OperatorCriterion из P3. Он фиксирует
обещания, а не доказывает их смысл/реализацию. Структурно полноценный семантический
отказ под видом плана нельзя надёжно распознать одной схемой; отдельный негативный
пример явно фиксирует это ограничение. Аналогично текстовое совпадение обещаний не
доказывает соответствие естественному языку пользователя. Живой сравнительный пилот
остаётся необходимым до включения нового пути по умолчанию.

## Проверки

Итог: **792 backend-теста**, **113 frontend-тестов**, **17 native browser-тестов**.
Для Docker прошли все **27 различных browser-кейсов**: 25 в общем прогоне и
4 runtime-кейса в повторном (2 пересекаются). Две первоначально слишком строгие
проверки самого fixture уточнены: допуск округления дробной CSS-координаты и одного
кадра на границе интервала; удвоение цикла по-прежнему не проходит. Ruff, mypy,
Django check, проверка согласованности миграций, frontend lint/build и diff check проходят.

Результаты прогонов и hashes записаны в
[evidence](evidence/generation-improvement-p4-p5-2026-10-27.json).
Команды запускались последовательно для тестов, использующих PostgreSQL; браузерные
контейнерные запросы также выполнялись без конкурирующих pytest-процессов.

## Версии и выпуск

Текущая линия: pipeline **9**, planning **2**, checks policy **3**, runtime **2**,
manifest **1**, presentation **1**. Старый runtime 1 удалён из исходников; v8 не
поддерживается как исполняемый контракт. Миграция `0015` добавляет поля и новые
значения по умолчанию, не маркирует существующие записи как v9 и не переписывает
расход/receipt. Исторический тест фиксированных hashes старого planning заменён
проверкой отказа от старого контракта; протокольные гарантии Codex сохранены.

Миграция проверена на отдельной тестовой БД. Рабочая локальная БД, приложение,
облачный сервер, Codex Worker и GPU этим этапом не обновлялись. Перед выкладкой:
остановить новые задания, дождаться или сверить sent/unknown, сохранить резервную
копию, применить миграции, обновить валидатор/приложение, выполнить `retire_games`
сначала без `--apply`, затем удалить неподдерживаемые игровые артефакты. Команда
сохраняет пользователей и финансовый учёт и отказывается работать при активных
Run/reserved/sent. Это инструкция выпуска, а не выполненное удаление данных.

Далее P6–P8: средства анимации, отдельная оценка оформления и feedback; P9 — новый
согласованный живой пилот. P4–P5 не подтверждают улучшение реальных игр 27B.
