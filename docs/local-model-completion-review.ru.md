# Почему игра создана, но генерация не завершается

24 октября 2026. Ревью `mini-games@9a4bc9d` и уточнение
[основного плана](local-model-improvement-plan.ru.md). **Поставка B реализована, локально проверена и прошла ревью. Разделы ниже сохраняют основания и критерии.**

Повод: пользователь уточнил, что игра может быть полностью играбельной, но генерация
«не доходит до конца». Следующий приоритет — корректное завершение и приёмка результата.
Дополнительные модельные шаги до исправления этого места могут удорожить тот же тупик.

## Результат реализации B

Завершение отделено от степени проверки кандидата. Неопределённость больше не запускает
кодовый ремонт; recheck выполняет только проверку сохранённых байтов. Числовые источники,
checkpoint/wait_for, журнал коррекций, manual по hash/ID отчёта, остановка одинаковых
исправлений и сохранение кандидата при регрессии реализованы. Произвольная подмена
selector/ожидания автоматически не разрешается: непроверенный эффект остаётся для
ручной проверки после доказанных обязательных gates.

Прошли 360 backend-тестов, 21 браузерный сценарий в изоляции ОС и 73 теста интерфейса;
сборка и статические проверки успешны. Два браузерных сценария проходят полный путь
через Django, упаковку, настоящий Chromium и автоматическое/ручное принятие.
Модели в этих испытаниях заменены тестовыми ответами. GPU/облако не использовались.
Миграция 0008 проверена на тестовой БД; рабочее окружение не перезапускалось.
Подробности и замечания ревью — [в отчёте](verification.md#завершение-и-проверяющие-сценарии--24-октября-2026).
Следующая поставка C измеряет настоящую модель в отдельно согласованном лимите.

**Последующая диагностика C:** [пилот Lite 24.10](lite-completion-pilot-2026-10-24.ru.md)
завершён в пределах 10/24 вызовов. Все три задания получили конечный статус, но рабочей
игры не получилось. Отчёт не подменяет независимую оценку статусом приложения и не
объявляет законченным контролируемое сравнение C. Локальные процессы обновлены,
миграции 0008/0009 применены; GPU-сервер и облачная поставка не изменялись.

## Основания и ограничения

Проверены код генерации, схемы, упаковка, orchestration, браузерные проверки, API/UI
ручного подтверждения, прежний план и ADR ML-инженера. Прочитаны предыдущие обсуждения
«Создать SSH-ключи» и «Сравнить приложение с архитектурой», отчёты и локальная БД
в транзакциях READ ONLY. Облачная БД и GPU не опрашивались; новых вызовов моделей нет.
Это подтверждает дефекты процесса и исторические случаи, но не определяет причину
каждой новой облачной игры.

Поставка A действительно реализована: разделены схемы, сохраняются исходные дефекты,
защищены проверки ремонта, добавлена карта исходников. **Декомпозиция генерации пока
не реализована:** `generation/service.py` вызывает модель один раз, а ответ содержит
замысел, весь код и сценарии. Pro/Lite выбирает модель, не другой процесс разработки.

## Подтверждённые проблемы

| Приоритет | Факт и место | Почему мешает завершению |
| --- | --- | --- |
| P1 | `generation/schema.py::validate_checks` принимает `source=text` + `operator=increased`; `validation/runner.py::compare` принимает для increased только числа | DOM возвращает строки. Даже реальное изменение `"0"` → `"1"` получает False. Такой тест невозможно исправить изменением числового текста игры |
| P1 | `studio/tasks.py::_execute` завершает `unverified` только после исчерпания модельных вызовов либо при `allow_model_calls=false`; иначе запускает repair | Недостаток наблюдений или визуальная неопределённость расходуют исправления без доказанной ошибки игры |
| P1 | В v3 проверки ремонта заморожены; отдельного пути пересмотра ошибочного сценария нет | Защита от подгонки тестов необходима, но ошибку самого теста теперь нельзя разрешить внутри обычного цикла |
| P1 | `studio/serialization.py` и `views.py::confirm_view` разрешают ручное подтверждение только при `Run.status=unverified` | После `unchanged`, ошибки патча или `repair_exhausted` Run может стать `needs_attention`, хотя кандидат сохранился. Путь завершения зависит от последней ошибки процесса |
| P2 | `validation/runner.py` объединяет InvalidCheck и BrowserTimeout в `check_unverified`; любое несовпадение — в `effect_mismatch` | Неверный selector, недостигнутый исход и реальная ошибка управления требуют разных действий, но сейчас различаются недостаточно |
| P2 | Язык проверок не содержит drag/swipe/pointer move; waits ограничены 10 с; baseline для changed/increased берётся до всех действий | Для некоторых игр нельзя корректно выразить приёмку. Изменение при старте также может ошибочно засчитаться за эффект управления |
| P2 | При создании код и checks проходят единый контракт; при ремонте передаются все исходники, checks и общие инструкции | Ошибка сопроводительного сценария может заблокировать полезный код; слабая модель продолжает решать слишком большую совмещённую задачу |

Чистый пробник на текущем коде воспроизвёл первый дефект без браузера и LLM:

```python
validate_checks([check_with_text_source_and_increased], require_complete=False)  # принят
compare("0", "1", {"operator": "increased", "value": None})  # False
```

## Поставка B: исправить приёмку и завершение

### B1. Разделить причину отказа и решение о следующем действии

Жизненный цикл Run отделить от степени проверки конкретной Revision. Обработка может
быть завершена с сохранённым непроверенным результатом; это не автоматический успех.

| Причина | Действие приложения |
| --- | --- |
| Нарушение изоляции/ресурсов, синтаксис, подтверждённая runtime-ошибка | Блокировать принятие; исправлять конкретный код в пределах бюджета |
| Воспроизводимый дефект механики при корректном сценарии | Локальное исправление с трассой ввода и наблюдений |
| Неверный тип наблюдения, selector, противоречивый сценарий | Сохранить байты игры; отдельно исправлять способ проверки |
| Недостаточно доказательств: длинный исход, неподдерживаемый жест, визуальная неопределённость | Конечный статус с перечнем непроверенного; просмотр и подходящее ручное подтверждение после обязательных gates |
| Сбой среды или неподтверждённая доставка | Повторять проверку/получение сохранённого ответа по действующей политике, не переписывать игру |

Один timeout или `effect_mismatch` ещё не определяет виновника. При обоснованной гипотезе
нестабильности разрешить один ограниченный повтор проверки тех же байтов, с учётом
времени и сохранением обоих отчётов. Случайный второй pass не скрывает расхождение.
Сам по себе `unverified` больше не является основанием code repair.

Ручное подтверждение привязать к hash кандидата, актуальным обязательным проверкам и
списку непроверенных требований. Оно не зависит только от последнего статуса Run.
Известную синтаксическую ошибку или подтверждённую поломку управления нельзя принять
общей кнопкой «всё равно готово». Ручной результат остаётся `manual` и не увеличивает
метрику автоматического успеха. Ожидание решения человека завершает активную обработку;
API/UI показывают конечный результат, а не продолжающуюся генерацию.

### B2. Разделить требование и исполняемый тест

- Требование и исходный запрос сохраняются независимо от модельного пересказа.
  Сценарий получает собственную версию, происхождение и причину изменения.
- Проверять совместимость source/operator/value до ремонта кода. Для DOM-числа нужен
  явный строгий `parse=number` с отказом на неоднозначном тексте либо числовое состояние.
  Не извлекать число из произвольной строки «Счёт: 10» по эвристике.
- Разделить setup → baseline → действие → ожидание эффекта. Добавить ограниченное
  ожидание условия вместо единственного снимка после фиксированных 40 мс.
  Неподдерживаемый жест обозначать как ограничение проверки, не как дефект управления.
- Исправлять сценарий без изменения игровых байтов. Модель может предложить изменение,
  но принятие принадлежит приложению: неизменное требование, свидетельства ошибки теста,
  повторная независимая проверка, сохранённый старый отчёт. Второй вызов той же LLM сам
  по себе не является независимым доказательством. Неясный случай остаётся непроверенным.
- Не менять правила игры ради исхода за 10 секунд. Для короткой игры нужен достижимый
  сценарий; для долгой — проверка переходов из допустимых состояний и явное ограничение
  полного прохождения. `forceWin` запрещён. Контролируемые seed/time добавляются вместе
  с доверенной обвязкой, а не приписываются произвольному старому коду.

### B3. Прекращать бесполезные исправления и сохранять лучший кандидат

Сравнивать один и тот же набор требований: устранён ли целевой дефект, появились ли
регрессии, изменились ли код и сигнатура сбоя. Меньшее число findings не доказывает
улучшение. После двух одинаковых результатов выбрать другую разрешённую стратегию
или остановиться, сохранив понятную причину. Новая неудачная попытка не вытесняет
прежний лучший кандидат; принятая версия и публикация сохраняются.

Продолжение сначала классифицирует сохранённый отчёт, затем выбирает проверку, ремонт
или завершение. Не начинать новый полный лимит ремонтов только ради ошибочного теста.

Места реализации: `generation/schema.py`, `validation/runner.py`, компактная политика
рядом с `studio/tasks.py`, сериализация/API, `web/src/components.tsx`. Новым состояниям,
сценариям и решениям нужна версия политики; прежние Invocation/отчёты неизменяемы.
Это ограниченная поставка в существующем Django-процессе, без нового сервиса или движка.

**Критерии B:** рабочая игра с неверным числовым/selector-тестом не отправляется на
перегенерацию; сломанное управление не принимается; длинный исход даёт конечное решение;
исправление теста сохраняет требование и код; повторяющийся дефект останавливает цикл;
поздний/отменённый ответ не заменяет кандидат; API и UI показывают одинаковый результат.
Проверять на заранее размеченных рабочих и намеренно сломанных играх без LLM.

## Поставки C–E: измерить эффект и уменьшить нагрузку на 27B

**C. Сравнительный пилот после B.** Измерять время до кандидата и до конечного решения,
подтверждённую играбельность, ложные отказы и принятия, неопределённость, лишние вызовы
после первого рабочего кандидата, успешность малых правок, токены и полное время.
Играбельность определяет независимая оценка кандидата, не только `status=succeeded`.

Разведочный набор: три разные механики, по два создания и одной малой правке успешной
игры — максимум 12 операций на политику. Отдельно ограничить число вызовов, токены и
GPU-время. Сравнить текущий путь и B на одинаковых заданиях/настройках. Непроверенные
исходы не исключать из знаменателя; ручное принятие учитывать отдельно. Это разведка,
а не доказательство 80% успеха. Затем полный пилот из основного плана.

Существующий `scripts/live_eval.py` собирает преимущественно статусы и запускает правки
только после `succeeded`: ложный отказ рабочей игры им не измеряется. До пилота добавить
независимую разметку кандидатов, времена переходов и профиль модели. Replay старых
ответов проверяет приёмку, но не качество нового prompt. Новые inference требуют
отдельно согласованного бюджета; эта итерация их не запускает.

**D. Упростить работу модели, измеряя изменения по одному.**

1. Компактные схемы по задачам. Не повторять полный design при локальном ремонте.
   Если отказали только checks, сохранять безопасно разобранные исходники в карантинном
   черновике и отдельно исправлять контракт проверки. Неполный JSON не достраивать
   эвристически; карантинный черновик не считается принятой игрой.
2. Контролируемая замена одного небольшого повреждённого модуля по точному hash.
   Соседние файлы неизменны, применение атомарно, требования и регрессии обязательны.
   Целый монолит `game.js` не считать маленьким модулем автоматически. Перекраска рабочей
   игры остаётся точечной правкой.
3. Проверенная Canvas2D-обвязка: ввод, координаты, resize/DPR, время и наблюдения.
   Модель пишет правила, данные и отрисовку. Предварительный интерфейс — init/update/render
   и input; сначала закрепить его тестами. Нет готовой змейки или каталога жанров.
   Сравнить один модельный шаг с обвязкой и без неё до добавления планирования.

**E. Короткая спецификация → реализация.** План фиксирует требования, состояния,
ввод/исход и интерфейс. Второй вызов реализует компактный модуль, а не заново весь
HTML/CSS/движок/приёмку. При обычной малой правке нового планировщика нет. Дополнительные
модули — только при доказанной необходимости. Сначала сохранённые бюджеты/восстановление
шагов; планирование не расходует скрыто слоты ремонта. Результат оценивается по полному
пути до рабочей игры, а не по числу добавленных этапов. Pro и старые игры сохраняются.

Обязательный профиль измерений: точное имя/revision весов, квантование, vLLM/template,
reasoning, sampling, контекст/выход. Сейчас адаптер не задаёт temperature/top_p;
relay допускает эти два поля, но не произвольные seed/top_k/chat_template_kwargs.
Расширение протокола — отдельная работа. GPU агент не меняет; несекретный снимок
конфигурации предоставляет оператор.

vLLM может брать sampling defaults из `generation_config.json`
([официальная документация](https://github.com/vllm-project/vllm/blob/main/docs/serving/online_serving/openai_compatible_server.md));
совместимость structured output и reasoning зависит от конфигурации/модели
([официальная документация](https://docs.vllm.ai/en/latest/features/structured_outputs/)).
Это основания фиксировать настройки, а не доказательство неверной настройки нынешнего
сервера. Универсальную «правильную температуру для 27B» пока назначать нельзя.
