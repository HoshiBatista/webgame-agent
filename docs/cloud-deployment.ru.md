# Облачный стенд GameForge и реле

Целевой VPS: `212.57.126.215`, Ubuntu 24.04, 2 CPU / 4 ГБ RAM.
Рабочий вход: `https://212.57.126.215`; реле использует тот же origin и путь
`/bridge/v1/`. Preview использует отдельный origin `https://212.57.126.215:8443`.
Домен `noxlight7.fvds.ru` уже указывает на VPS, но его сертификат пока не выдан:
Let’s Encrypt возвращает общий лимит для `fvds.ru`. Для смены CA ожидается email владельца.
По IP установлен доверенный short-lived сертификат Let’s Encrypt с автоматическим
продлением Caddy; проверка TLS не отключается.
На этом порту разрешён только `/preview/*`, cookies и Authorization удаляются ingress.
Сам preview также задаёт CSP sandbox, запрещает сеть и не включает middleware сессий.

Конфигурация Compose: основной `compose.yaml` плюс `deploy/cloud.compose.yaml`.
Проверенная конфигурация Caddy: `deploy/Caddyfile.cloud`; её копия установлена
в `/etc/caddy/Caddyfile`. Домен временно перенаправляет приложение на рабочий IP,
когда сертификат домена станет доступен.
Облачный профиль использует только relay. Локальные Codex, vLLM и relay продолжают
работать как прежде; авторизация Codex на облачный сервер не переносится.

## Размещение и запуск

Исходники текущего выпуска: `/opt/gameforge/releases/20261023`.
Секреты находятся в его закрытом `.env`; не выводить `docker compose config` без
`--quiet`, поскольку полный вывод содержит их. Для просмотра состояния:

```sh
ssh -i ~/.ssh/id_ed25519_vps_proxy root@212.57.126.215
cd /opt/gameforge/releases/20261023
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml config --quiet
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml ps
```

Для нового выпуска нужны APP_IMAGE/VALIDATOR_IMAGE, CLOUD_HOST, случайные
DJANGO_SECRET_KEY/POSTGRES_PASSWORD и первоначальный администратор. Настройки модели
такие же, как в `.env.team.example`: qwen38, JSON schema, context check server,
потолок ответа 16384, максимум три автоматических исправления. У серверного приложения
должен быть отдельный **client** токен реле. Не копировать worker-токен GPU.

Перед запуском загрузить или собрать оба образа. Затем:

```sh
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml up -d --no-build
```

Приложение и preview опубликованы только на loopback через Nginx 8080/8081.
Хостовый Caddy завершает HTTPS на 443/8443 и удаляет доверяемые приложением заголовки
от внешних клиентов, формируя свои. В облачном Nginx X-Forwarded-Proto принудительно
равен https: его порты не должны публиковаться на внешнем интерфейсе.
80 используется для ACME и перенаправления на HTTPS. SSH доступен только по ключу.
Публичный `/admin/` закрыт; управление пользователями выполняет оператор через SSH.
Открытой регистрации нет; тестовый пользователь создаётся без staff/superuser прав.

Redis, PostgreSQL, Gunicorn и служебный Unix-сокет валидатора наружу не выставляются.
У валидатора `network_mode: none`, read-only filesystem и нет Docker socket.
Токен реле передаётся только сервису worker. Вход в приложение ограничен по частоте
на Nginx: общий для небольшого стенда лимит 10 запросов/минуту с burst 10.

## Ресурсы и ограничения

Один слот генерации; два потока Celery обслуживают задачи и доставку. Валидатор работает
последовательно. Контейнеры имеют лимиты памяти; активные постоянные сервисы GameForge
и реле суммарно ограничены примерно 3 ГБ. Это небольшой тестовый стенд, не подтверждение
большой конкурентной нагрузки. Контролировать `docker stats --no-stream`, память и диск.
Нельзя считать свободную память после старта доказательством запаса под любое число игр.

## Перенос реле без доступа агента к GPU

Переносится SQLite через backup API: UUID, владельцы, хеши токенов и receipts сохраняются.
Во время финального снимка старое реле должно прекратить приём, а активных заданий быть 0.
После переноса работает только одна база. Старый HTTPS `/bridge/v1/*` может временно
проксировать новый HTTPS origin с исходным Authorization, поэтому действующий исполнитель
на GPU и старые клиенты не требуют немедленного переключения.

Старый VPS нельзя удалять, пока оператор GPU не переведёт BRIDGE_RELAY_URL на новый origin
и все клиенты не перестанут использовать старый адрес. На GPU менять только executor,
через drain → idle → backup → изменение URL → пересоздание executor → resume.
Не менять его principal, токен, spool, UUID; не затрагивать qwen38 и blast4d.

**Откат старой базы поверх новых заданий запрещён.** Если новая очередь уже принимает
работу, откат требует согласованной остановки, актуального снимка и проверки исполнителя.
Для временной проблемы приложения можно остановить только GameForge: реле независимо.
Не выполнять `down -v`; постоянные volumes содержат историю, задания и данные приложения.

## Проверка без запроса к модели

Проверить TLS без `-k`, отсутствие доступа к реле без токена (401), health с client-токеном,
запрет клиенту worker-методов (403), сохранность старых receipts и вход тестового пользователя.
Гость не должен получать список чатов. Preview не должен обслуживать `/api/session/`
или выставлять cookies. Проверку браузера выполнять на доверенной тестовой игре без LLM.
Успех этих проверок подтверждает инфраструктуру, а не качество генерации настоящей модели.
