### Фактическая исходная точка до поставки A

- Уже есть сохранённые Invocation/Revision/CheckReport, повторное использование ответов,
  раздельные тексты prompts create/edit/repair, синтаксическая проверка перед игровыми,
  ограниченный цикл исправлений, Pro/Lite и независимый транспорт через реле.
- В отличие от текстов prompts, JSON Schema операций пока общая. `validate_response()`
  принимает полный `files` при repair, а `materialize()` затем отвергает его как
  `rewrite_disallowed`. Это воспроизведено на синтетическом ответе без LLM.
- На том же fixture `materialize()` принимает repair, который меняет только проверки
  на `contains ""`, сохраняя файлы, названия требований и категории. `compare()` принимает
  пустую строку даже при неизменном наблюдении. Это доказательство дыры в контракте,
  не новый браузерный прогон сломанной игры и не оценка качества модели.
- `validation/syntax.py` честно сообщает координаты собранного HTML, но карты к исходным
  файлам ещё нет. `generation_contract` записывает hashes и `pipeline_version=2`, однако
  сохранение номера само по себе ещё не обеспечивает исполнение прежнего контракта после обновления.
- Выполнено 72 существующих локальных теста: `test_generation_artifacts`,
  `test_generation_feedback`, `test_generation_prompts`, `test_response_normalization`.
  Они прошли; новые граничные случаи выше пока не являются регрессионными тестами проекта.
  Браузер, БД приложения, облако и настоящая модель в этом ревью не вызывались.
- По выводу оператора GPU-исполнитель 0.2.1 установлен и возобновлён, остальные контейнеры
  не перезапускались. Это завершённая работа над отменой транспорта; исправлением качества
  генерации она не является. GPU-сервер агент не посещал.

### Ближайшая поставка: закончить текущий ремонт

Один ограниченный набор изменений без нового runtime, смены модели или изменения реле:

1. Сохранить раздельно исходные незакрытые дефекты и ошибку последнего ответа. Сокращение
   контекста выбирает главный дефект, но не удаляет остальные из состояния процесса.
   При отклонённом патче базовая версия не меняется; после успешного патча новый отчёт
   обновляет состояние дефектов. Проверить оба пути ошибки: отказ упаковки и отказ схемы.
2. Выбирать контракт create/edit/repair на стороне приложения и передавать его через
   Codex, прямой API и relay. В этой поставке repair ещё не разрешает замену целого файла.
   Сохранённые ответы читаются по своей версии контракта, без новой генерации и изменения
   исходной квитанции. Повторная проверка старого кандидата использует актуальные правила
   приёмки и создаёт новый отчёт, сохраняя прежний.
3. Заморозить действующий проверочный набор для автоматического ремонта. Модель может
   предложить исправление теста отдельно, но оно не заменяет обязательный сценарий без
   решения приложения и независимого подтверждения эффекта. Одни проверки/метаданные
   не дают статуса «игра исправлена». Запретить пустые/тривиальные ожидания.
4. Добавить карту упаковки до исходного файла и строки, включая defer, несколько scripts,
   inline-код и экранирование. На неразрешимом месте сохранять честную координату экспорта,
   а не указывать предполагаемую строку. Не чинить сам исходник эвристикой переносов строк.
5. Регрессии: ошибка патча → следующий запрос и рестарт всё ещё знают исходный дефект;
   repair не получает create-формат; ослабление теста отвергается; честная коррекция
   ошибочного сценария не выдаётся за исправление кода; stale/cancelled результат не
   становится текущим; Codex и API проходят одинаковую проверку контракта.

Критерий выхода — воспроизводимые ошибки закрыты тестами, восстановление сохранённого
ответа проверено без модели, последняя рабочая версия сохранена. Тесты транспорта и
зелёный CI не заменяют отдельное измерение playable rate.

## Цель и границы

Главный результат — проверенная рабочая игра и сохраняющие её небольшие правки на Qwen.
Сначала повышаем долю успешных результатов, затем оптимизируем время и число вызовов.
Один неудачный ремонт старой змейки не доказывает общий предел возможностей модели.

Принимаем в план спецификацию, планирование, доверенные шаблоны исполнения, ограниченные
файловые операции, независимые проверки, разные стратегии ремонта, измерения и эксплуатационные
границы ML-проекта. Единственное исключённое архитектурное решение — FastAPI.
Другие идеи распределены по этапам, а не молча отброшены.

Сохраняются Codex, прямой vLLM и relay, история, публикации и локальный запуск с Docker/без него.
PostgreSQL/Celery остаются владельцами процесса. Реле и GPU-исполнитель доставляют запросы
и результаты; они не планируют игры и не выбирают следующую попытку.
GPU-сервер агент не подключает и не изменяет. Этот план не требует смены модели,
квантизации, контейнеров GPU или настройки VPN. Живые проверки позже выполняются через
GameForge и действующий API в отдельно определённом лимите нагрузки.

## Исторические причины до поставки A

Этот раздел описывает состояние до A. Потеря исходных findings, общая wire-схема,
ослабление checks при repair и отсутствие карты исходников уже исправлены.
Актуальные проблемы перечислены в [повторном ревью](local-model-completion-review.ru.md).

Сверены текущие `generation/prompts.py`, `schema.py`, `feedback.py`, `artifacts.py`,
`studio/tasks.py`, `validation/syntax.py` и предыдущий [разбор](source-review.ru.md).

- Один ответ всё ещё совмещает замысел, весь код и проверяющие его сценарии. Этапы в UI
  сейчас отражают преимущественно проверки, а не декомпозицию работы модели.
- Ошибка применения патча заменяет `findings`: исходный незакрытый дефект может исчезнуть
  из следующего запроса. Фильтр синтаксических ошибок дополнительно скрывает другие причины.
- JSON Schema общая для create/edit/repair. Она разрешает форму полного файла, который
  затем отвергается упаковщиком при ремонте. Структурно правильный JSON не означает допустимую операцию.
- Сохранение названия требования не мешает модели ослабить `expect`, наблюдение или действия.
  Независимой полноценной приёмки механики пока нет.
- Ошибка JavaScript адресуется в собранном HTML, хотя править нужно исходный файл.
- Системно повреждённый модуль приходится чинить через точные текстовые замены;
  отсутствует управляемый переход к структурному ремонту или новому кандидату.

В зафиксированном прогоне змейки было четыре вызова за 704,64 с, но рабочего исправления
не получено. Это исторический результат из отчёта, не новое испытание этой задачи.

## Целевой процесс

```text
Запрос → GameSpec + BuildPlan + профиль исполнения → подготовленные ассеты, если нужны
  → ограниченная попытка: небольшие модельные шаги + быстрые проверки черновика
  → один неизменяемый кандидат → независимые статические и браузерные проверки
  → рабочая версия ИЛИ решение о способе ремонта ИЛИ остановка с объяснением
```

Локальная проверка черновика помогает модели, но не даёт права объявить игру готовой.
Одна попытка может включать несколько модельных обращений; каждое сохраняется и учитывается.
Продолжительность сессии не означает передачу всей переписки в каждый запрос.
GameSpec и BuildPlan — разные проверяемые данные, но для простой Lite-игры они могут
появиться в одном коротком ответе. Отдельный вызов на каждый термин не обязателен.
Для небольшой правки используем сохранённую спецификацию; заново планируем только
затронутые требования при необходимости. Pro сохраняет текущий рабочий путь; новый
режим включается явно по версии политики, а не по одному только названию провайдера.

## Этап 0. Воспроизводимая исходная точка и актуальные правила

1. Из сохранённых неудачных ответов получить обезличенные fixtures: неверный патч,
   полный файл при repair, однострочный JS с `//`, изменение только теста, `unchanged`.
   Исходные пользовательские тексты/секреты не публиковать; факты и старые результаты сохранять.
2. Зафиксировать версию prompt/schema/validator/model profile и эталонные задания до правок.
   Включить исходный запрос и критерии, полные настройки модели и версии контракта,
   а не только отображаемый alias. Сохранённый ответ проверяет регрессию обработки;
   проверку качества нового prompt он не заменяет.
3. При начале реализации синхронизировать AGENTS, архитектуру, модель процесса и старый план:
   убрать прежний запрет на отдельное планирование, доверенный runtime и структурный ремонт.
   Это изменение подхода, а не утверждение, что перечисленные функции уже существуют.

**Готово, когда:** известные ошибки воспроизводятся без LLM и сетевых запросов;
каждому дефекту соответствует проверка, которая не считает неверную игру успешной.

## Этап 1. Исправить текущий ремонт до увеличения числа вызовов

1. Хранить отдельно `unresolved_findings` игры и `last_attempt_error` формата/патча.
   Исходное требование, точная база, уже проверенное поведение и оставшийся бюджет сохраняются
   в каждом запросе, включая продолжение после перезапуска.
2. Ввести схемы по разрешённым операциям: create, local patch, разрешённая замена модуля.
   Передавать выбранную схему всем адаптерам вместо неизменного общего RESPONSE_SCHEMA.
   Проверки прав, путей, base hash и размеров остаются на стороне приложения.
3. Сопоставлять ошибку компиляции и runtime с исходным файлом/строкой через карту упаковки;
   передавать точный небольшой фрагмент и hash. Не восстанавливать переносы строк по догадке.
4. Разделить требования приёмки и исполняемый тест. Требования фиксируются версией;
   модель не может поменять их во время ремонта. Исправление ошибочного теста — отдельное
   решение приложения с журналом причины и повторной независимой проверкой.
   До появления такого решения приложение не принимает изменения обязательного набора
   от автоматического repair. Не замораживать заведомо ошибочный сценарий навсегда:
   отделить дефект теста как `needs_attention`, сохранить кандидат и причину.
5. Запретить считать исправлением одни метаданные, пустое ожидание или тестовый обход.
   Отличать `no_changes`, `unchanged`, дефект игры и отказ инфраструктуры.

Основные места: `generation/{schema,prompts,feedback,artifacts}.py`, `studio/tasks.py`,
`validation/{syntax,runner,service}.py`, модели Run/Invocation/CheckReport.

**Готово, когда:** после ошибки патча следующий запрос всё ещё исправляет исходный дефект;
`contains ""` не превращает сломанную игру в принятую; координаты ведут к исходнику;
неверная операция отвергается до применения, а сохранённые ответы можно повторно обработать без inference.

## Этап 2. Доверенная игровая обвязка и компактные спецификации

1. Ввести версионируемые GameSpec, AcceptanceRubrics, BuildPlan, TemplateProfile и FeedbackSnapshot.
   Спецификация закрепляет цель, цикл, состояния, управление, правила, исход, аудиторию и ограничения.
   План связывает каждое требование с модулем/хуком и способом независимой проверки.
   Явные требования пользователя остаются отдельным неизменяемым входом: пропущенное
   требование отклоняет план, а не исчезает после модельного пересказа.
   Для первого среза это компактные схемы/снимки в существующей БД, без пяти новых сервисов.
   Автоматическая проверка ссылок rubric → проверка не доказывает полноту понимания
   произвольного текста. Для эталонных задач полнота задаётся независимыми критериями;
   неоднозначное или непроверенное требование явно отмечается, а не становится pass.
2. Первым реализовать `canvas2d-arcade-v1`: lifecycle, ввод с клавиатуры/pointer/touch,
   resize/DPR, pause/blur, управляемое время/random seed, audio opt-in, тестовый bridge.
   Модель пишет механику в разрешённых хуках, а не снова реализует эту инфраструктуру.
3. Проверять hash доверенных файлов до и после сборки. Шаблон не содержит готовую змейку,
   раннер или карточную игру: правила и игровой контент по-прежнему создаёт модель.
4. Начать с Canvas2D; grid/cards/narrative и локальный Phaser включать через ту же систему
   профилей после проверки набора игр. Число модулей определяется задачей, а не жёстким конвейером.
5. Подготовку ассетов выделить перед попыткой. Процедурные/локальные ресурсы — базовый путь;
   внешняя генерация изображений/аудио позднее использует manifest с происхождением,
   лицензией, hash и квотами. Не разрешать модели скачивать ресурсы из sandbox.

**Готово, когда:** fixture с новой обвязкой работает offline, на телефоне и ПК;
ввод, reset, resize и pause проверены без генерации; модель не может изменить доверенный runtime.
Профиль сначала применяется только к новым кандидатам нового процесса. Старые свободные
HTML/JS-игры продолжают открываться и правиться прежним контрактом, без скрытой миграции.
Bridge — средство наблюдения; сама игра не является доверенным источником вердикта.

## Этап 3. Поэтапная генерация внутри ограниченной попытки

Предпосылки: минимальная независимая приёмка из этапа 5 и сохранённые бюджеты/границы
шагов из этапа 4. До выполнения этих условий многошаговый режим не включаем.

1. Создать GenerationHarness и DraftWorkspace по ADR 0002. Harness обслуживает одну попытку
   и возвращает не более одного CandidateSubmission; решение о новом ремонте принадлежит workflow.
2. Для первого Lite-пилота: один короткий запрос спецификации + плана → реализация
   минимальной игры → проверка интеграции. Для простой игры код может быть одним модулем.
   Пофайловые вызовы добавлять для задачи, которая не помещается в этот срез, и только
   в пределах заранее сохранённого бюджета. Не вводить обязательную очередь ролей.
   Каждый шаг имеет узкую схему ответа и короткий специализированный prompt.
3. Сохранять состояние этапов и обращения, загружать только нужные файлы и allowlisted
   инструкции из версионированного registry. Не отправлять на каждый шаг весь чат и все старые исходники.
   При этом всегда сохранять обязательные требования, текущий главный дефект, точную
   базу, интерфейсы соседних модулей и остаток бюджета. Фильтрация контекста не означает
   слепую правку файла без его зависимостей.
4. Дать только ограниченные операции: list/read, create/patch/replace разрешённого файла,
   manifest/prepared assets, quick check, submit. Замена требует разрешения политики и base hash.
   Ни shell, ни пакетов, ни произвольных URL/путей, ни доступа к БД/платформе.
5. Не привязываться к наличию function calling: типизированная JSON-команда может выражать
   те же операции. ModelGateway принимает контракт текущего шага и возвращает ответ, usage,
   finish reason и идентификаторы. Codex остаётся отдельным адаптером с теми же ограничениями.
6. Quick и release используют общую библиотеку статических правил. Быстрая проверка —
   подмножество правил, не альтернативное определение успеха; исполняемый код остаётся в sandbox.

**Готово, когда:** fake-последовательность проходит весь путь и восстанавливается на каждом
шаге; повторная доставка ответа не запускает новый inference; отмена останавливает новые
операции; промежуточный черновик не становится опубликованной или рабочей версией.

## Этап 4. Разные способы ремонта и единый бюджет

| Ситуация | Решение приложения |
| --- | --- |
| Локальный дефект в конкретном участке | LOCAL_PATCH |
| Повреждён небольшой модуль или его внутреннее устройство | STRUCTURAL_REPAIR с ограниченной заменой/реорганизацией модулей |
| План не покрывает требование или неверно связывает модули | REPLAN с сохранением спецификации |
| Кандидат системно непригоден, бюджет позволяет | REGENERATE от доверенного шаблона, отдельная дочерняя версия |
| Нет прогресса, недопустимый запрос, бюджет исчерпан | STOP с последней рабочей версией и объяснением |

Модель может предложить способ, но не выбирает его и не запускает следующую попытку сама.
Сохраняем максимум 2–3 семантических исправления на Run. Replan/regenerate не обнуляют
счётчик. Внутренние ходы и quick checks ограничены отдельно и входят в общий потолок
вызовов, токенов, времени, файлов/байтов и стоимости. Лимиты сохраняются вместе с запуском.

Первым реализуется `LOCAL_PATCH → STRUCTURAL_REPAIR одного разрешённого файла → STOP`.
Выбор связан с классом дефекта и историей фактического прогресса. Замена требует точного
hash, области разрешённых файлов, сохранения интерфейсов и независимых регрессий.
Один большой `game.js`, содержащий всю игру, не становится «маленьким модулем» автоматически:
для него действуют отдельные ограничения. Запрос перекраски рабочей игры не даёт права
переписать её механику. REPLAN/REGENERATE принимаются как следующие возможности, но не
являются предпосылкой исправления сегодняшних патчей.

Для начального двухшагового пилота бюджет новой политики содержит 2 базовых вызова и
не более 2–3 корректирующих: максимум 4–5 внешних вызовов, а не старый счётчик `1 + repairs`.
Ошибки схемы и повтор плана расходуют тот же общий предел; дополнительные quick checks
также имеют лимит. Это стартовая конфигурация эксперимента, не обещание достаточности.
Токены, контекст и сроки задаются профилем каждого шага и платформенным потолком;
точные значения калибруются по измерениям. Любой новый шаг сначала резервирует бюджет.

Повтор того же дефекта после двух целевых патчей запрещает третий одинаковый путь:
политика меняет стратегию в оставшемся бюджете либо останавливается. No-op и повтор
идентичных запросов обнаруживаются по данным, а не только по тексту сообщения модели.
Неизвестный исход внешнего вызова требует сверки; сетевой retry не равен новому ремонту.

**Готово, когда:** повреждённый модуль можно восстановить без fuzzy replace и незаметной
перегенерации всей игры; простой запрос цвета сохраняет остальные модули; ни перезапуск,
ни смена стратегии, ни fallback-провайдер не расширяют бюджет скрыто.

## Этап 5. Независимая приёмка и надёжное сохранение кандидата

Пункты 1–4 в минимальном объёме начинаются вместе с этапом 1 и развиваются с каждым
профилем. Проверка отмены, fence и сохранения обязательна сразу при добавлении нового шага.
Номер этапа не означает, что эти свойства можно отложить до конца разработки генератора.

1. Проверять spec/rubrics независимо от предложенных моделью тестов. Добавить закрытые
   для генератора сценарии и метаморфные проверки: другие допустимые входы, seed,
   последовательности управления, reset и сохранение инвариантов.
2. Сопоставлять bridge-состояние с реальным pointer/touch/keyboard и видимым поведением.
   Bridge с нарисованным `passed` или внутренним `forceWin` не является доказательством.
3. Выполнять сначала затронутые проверки, затем весь обязательный набор перед продвижением.
   Визуальные проверки: пустая сцена, обрезанные элементы, доступность управления, layout;
   vision-оценка — дополнительный совет, не способ отменить детерминированный отказ.
4. Сохранять seed и версии runtime/bridge/prompt/schema/browser/validator/locale/timezone;
   ключ кеша учитывать и артефакт, и требования, и среду. Публиковать проверенные байты.
5. Ввести ArtifactStore/ArtifactCommitter: закрытый staging → проверка квот/путей/runtime →
   immutable bundle по digest. При файловом хранении нужен PENDING commit intent и reconciler
   для разрыва между rename и транзакцией PostgreSQL. Текущие JSON/Text артефакты в БД
   переносить только после проверки равенства digest, с сохранением прежних публикаций.
   Для первого среза остаёмся на JSON/Text в PostgreSQL: ограниченный DraftWorkspace
   может иметь ту же реализацию хранения, а принятие Revision — существующую транзакцию
   с дополнительными проверками. POSIX rename и двухфазное согласование пока не нужны.
   Файловая реализация остаётся в плане; условие перехода — измеренная потребность
   в объёме/ассетах, а не само появление класса ArtifactStore.
6. Использовать существующие outbox, leases и Invocation; расширить проверку fence на
   каждый новый шаг, submission и commit. Предусмотреть монотонный номер захвата этапа
   по ADR, миграцию существующих заданий и отказ от результата устаревшего исполнителя.

**Готово, когда:** намеренно обманные игры отвергаются; сбой после ответа/submit/rename
не теряет результат и не делает чужую попытку текущей; публикации и история не изменяются
от новой неудачной генерации.

## Этап 6. Доказать улучшение на настоящей модели

Сбор эталонного набора начинается на этапе 0. Первый небольшой сравнительный прогон
нужен после этапа 1, до полной обвязки/harness; следующий — после каждого нового среза.
Реальные вызовы запускаются отдельно через GameForge в согласованном лимите, не в этом ревью.

1. Отдельно сравнить исправленный текущий цикл и новый процесс на одинаковых заданиях,
   версии модели, настройках и условиях очереди. Сохранённые ответы использовать для
   регрессий, но не выдавать их за новый независимый модельный прогон.
2. Первый пилот: пять механик, включая змейку, runner, grid puzzle, cards и touch drag/drop;
   по три создания на механику, затем две малые правки для успешных игр. Скрытые варианты
   требований держать отдельно от заданий, на которых корректируются prompts.
   Перед полным пилотом допустим разведочный набор из трёх разных задач и по одной малой
   правке. Он помогает выбрать следующую работу, но не доказывает 80% успеха. Непроверенные
   профилем механики не исключать молча из знаменателя: отмечать область поддержки.
3. Измерять first-pass и post-repair playable rate, успех правок без регрессий, долю
   форматов/патчей с ошибками, результат каждой стратегии, повторяемость findings, токены,
   число вызовов, полное время с очередью и причины остановки. Ручной успех учитывать отдельно.
4. Предварительный порог ML-плана — ≥80% проверенно рабочих игр после ограниченного
   ремонта и отдельно ≥80% успешных малых правок, ноль нарушений границ/потерь истории.
   Пятнадцать созданий — пилот с опубликованными дробями, не точная оценка p95 или гарантия.
5. Проверить также полный новый путь на Codex при согласованном доступе/лимите. Если Qwen
   не достигает порога, разбирать типы ошибок; не подменять его автоматически более сильной
   моделью и не объявлять смену provider доказательством исправления Qwen.
   Сравнивать отдельно исправленный текущий путь, добавленный runtime и двухшаговую
   генерацию. По возможности менять один фактор за раз. Новую скачиваемую модель
   проверять отдельной строкой с фиксированными настройками; более быстрые токены не
   гарантируют меньшего полного времени до рабочей игры.

Секундные цели старого плана не обрывают полезный ответ. Явный hard budget остаётся,
но его значения калибруются по измерениям модели, а не копируются из capacity.md.
Нулевые цены собственного vLLM не означают неограниченную GPU-нагрузку.

## Этап 7. Остальные принятые идеи ML: качество и эксплуатация

- **Память отзывов:** одна оценка ревизии, вес `5-rating`, двойной вес текущего проекта,
  ограниченная история и очищенные комментарии; точный FeedbackSnapshot в спецификации
  и генерации. Это контекст предпочтений, не дообучение весов и не автоматическое доказательство качества.
- **Skills/debug registry, ассеты и vision:** версионированные проверенные материалы по
  типам механик/ошибок, подготовленные изображения/звук с происхождением; независимая
  визуальная оценка после базовой механики. Дообучение — только при накопленных данных.
- **ModelGateway/Responses:** предусмотреть адаптер Responses из ADR 0005 и контрактные
  проверки возможностей. Текущий Chat Completions/relay сохраняется на время перехода;
  совместимость API не является исправлением игровой логики. При необходимости менять
  GPU-исполнитель готовятся отдельные команды оператору, агент туда не подключается.
- **Разделение ролей:** общий Django-пакет с отдельными model/workflow/validation workers,
  секрет и egress только у model worker, CPU/RAM/PID-потолки и restart policies. Это не
  дополнительный внутренний HTTP-сервис. Native-режим сохраняется для локальной команды.
- **CI/security:** контрактные и adversarial fixtures, coverage, аудит зависимостей/секретов,
  закреплённые Actions, полный Compose e2e и проверка изоляции; имеющаяся Linux/macOS
  браузерная проверка сохраняется. Сценарии миграций адаптируются к Django и PostgreSQL 18.
- **Наблюдаемость и нагрузка:** трасса Run → этап → Invocation → candidate → report,
  квоты, backpressure и circuit breaker; без prompts/секретов в обычной телеметрии.
  Цель 10 активных пользовательских запусков проверяется очередью и нагрузочным тестом,
  а не трактуется как 10 одновременных inference на A100. SLO устанавливаются по измерениям.
- **Production:** сохранность файлов, retention/backup/restore, preview capabilities,
  rate limits/TLS и более сильная изоляция browser runner (gVisor/microVM). Это отдельный
  этап поставки; наличие защищённого реле само по себе не делает GameForge production-ready.
- **Продуктовые предложения `работа.md`:** память оценок, аудитория, публикации, ремиксы,
  управление чатами и интерфейс остаются в матрице соответствия. Уже работающие функции
  покрываются регрессиями; отличия UI выносятся в отдельные продуктовые задачи, а не
  переделываются попутно с ремонтом модели. Только FastAPI исключён из целевой архитектуры.

Обязательный второй модельный шаг не вводится: E становится сравнительным
экспериментом, если компактный один проход D остаётся недостаточным.

Каждая поставка — отдельный проверяемый набор изменений с тестами и ревью.
Прежний линейный порядок `0 → 1 → 2 → 3 → 4 → 5 → 6` заменён следующими срезами:

| Поставка | Состав из этапов | Критерий перехода |

| B. Исправить завершение и проверяющие сценарии | B1–B3 повторного ревью + части 1/4/5 | Ошибка теста не вызывает ремонт игры; неопределённость получает конечный статус; реальные дефекты не принимаются; лучший кандидат сохраняется. |
| C. Измерить текущий и исправленный пути | Начало 6 + метрики повторного ревью | Независимая оценка кандидатов, ложные отказы/принятия и времена; живой запуск отдельно согласован. |
| D. Упростить генерацию и ремонт | Узкая часть 4, компактный контракт, минимальная часть 2 + 5 | Замена небольшого модуля сохраняет требования и соседний код; один профиль runtime проверен без модели и с одним модельным шагом. Эффекты изменений измеряются отдельно. |
| E. При необходимости сравнить двухшаговую генерацию Lite | Бюджеты/восстановление 4 + 3 + повтор 6 | План+код сравниваются с компактным одним проходом; сбой между шагами не повторяет inference; оценены качество и полный расход до рабочей игры. |
| F. Расширить доказанную базу | Остальные 2/4/5/6/7 | Новые профили, replan/regenerate, ассеты, файловое хранение и эксплуатация добавляются по измерениям с сохранением принятых требований. |

Внутри D порядок структурного ремонта и runtime выбирается по результатам C:
ошибки патчей требуют первого, ошибки повторяемой инфраструктуры — второго.
Поставка B не откладывается ради расширения генерации. Проверка границ и восстановление не зависят от результатов пилота и
не откладываются. Конкретные идеи ML сохраняются; их адаптация к Django/БД и момент
поставки не означают исключение из цели. FastAPI остаётся единственным исключённым стеком.

Новый процесс включается отдельной версией политики. Уже начатые Run завершаются по
сохранённому контракту, старые ответы не интерпретируются новой схемой задним числом.
Rollback меняет выбор процесса для новых запусков и не удаляет историю/бюджет/артефакты.
Для пользователя сохраняются обычные API GameForge, чат и понятные этапы с отменой.
До включения нового процесса синхронизировать AGENTS, архитектуру и prompts: нынешние
формулировки «один вызов»/«без runtime» описывают текущий путь и не должны запрещать
одобренный новый профиль. Пока это план, не помечать новые сущности реализованными.

Итог принимается по работающим играм, независимым проверкам, отсутствию регрессий малых
правок и измеренному бюджету. Сам факт появления новых классов, prompts или зелёного CI
не засчитывается повышением качества модели.
