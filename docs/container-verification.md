# Проверка контейнерной поставки

Проверено 18 октября 2026 года на собственном Compose-проекте `gameforge-mini`.
Стенд `127.0.0.1:8080` / `localhost:8081` использует **бесплатный провайдер fake**,
реальные PostgreSQL 18, Redis, Celery, nginx и Chromium в изолированном контейнере.
Это проверка поставки и управления заданиями, а не измерение качества/скорости LLM.
Compose-проверки не перезапускали локальный Codex-стенд на портах 8000/8001;
GamesForgeEx не изменялся.

## Сквозной сценарий

Выполняется `scripts/verify_container.py` через настоящие HTTP endpoint. Скрипт до
создания запуска проверяет `capabilities.provider == fake`; с платным провайдером
отказывается работать. Пароль берёт из локального `.env`, не выводит его.

Проверено:

- вход без CSRF отклонён, с токеном и сессией работает;
- создание чата и задания проходит через очередь, сохраняется принятая версия;
- HTML скачивания, preview и сохранённый hash совпадают побайтно;
- preview на другом хосте, без session cookie; CSP содержит sandbox и запрет сети;
- preview URL на хосте приложения отклонён, API на хосте preview недоступен;
- локальная правка CSS сохраняет байты HTML и JS, создаёт новую версию;
- опубликованный снимок не меняется от приватной правки; обновление публикации явно;
- ремикс использует опубликованный снимок, а не приватный черновик, без чужих prompts;
- повторная установка like идемпотентна;
- SSE имеет сохранённые возрастающие ID, reconnect после последнего ID не дублирует события;
- удаление чата не удаляет публикацию; гость не читает приватные чаты/диагностику;
- fixture не создаёт расхода, зависших резервов или неизвестных обязательств.
- после перезапуска app/preview/worker публикация и ремикс сохранили исходные hash,
  preview снова доступен без повторного запроса модели.

Последняя пересборка включает защиту от no-op, trusted operation, исправленный
учёт неизвестного расхода, init-процесс и безопасный снимок state.
Сквозной HTTP-прогон: создание **2,468 с**, правка **2,166 с**; очередь — 0,143 и
0,059 с. Оба результата проверены настоящим Chromium в обновлённой среде:
`check_seconds` равен **2,083 с** и **1,766 с**. ID запусков:
`06274215-cb67-4eeb-b9e6-1442a5bbd9a7` и `7ccb9a33-4db8-4a9f-bf1a-0eaae3a7aaba`.
Это проверка бесплатной fixture; время LLM здесь не измеряется.

Предыдущий прогон той же fixture с действующим кешем браузерных доказательств
занял 1,393 с и 0,290 с (`check_seconds=0`). Кеш используется только при совпадении
HTML, suite и среды; новый fingerprint runner вызвал реальные проверки выше.
Актуальные показатели последнего HTTP-прогона сохранены в
`.data/container-verification.json`. Расход, резерв и неизвестные обязательства
контейнерного fixture-стенда после проверки равны нулю.

## Очередь и восстановление

При исследовании локального Codex-пилота обнаружена очередь из 26 служебных задач:
ежесекундный dispatcher с поздним ACK накапливался перед новыми пользовательскими
запусками. Последовательные запросы ждали 6–18 с при отсутствии полезной работы.
Дополнительно запись `dispatched_at` после отправки могла перетереть сброс от busy worker.

Теперь уведомление отправляется сразу после commit задания; durable outbox остаётся
страховкой при недоступном брокере. Уведомление помечается до отправки, при ошибке
метка возвращается только для того же claim. Завершившийся worker сразу будит
ожидающие задания. Служебные задачи используют ранний ACK и короткое время жизни;
сами генерации сохраняют поздний ACK, lease и fencing. Это не повторный запрос LLM:
дубли доставки всё ещё обрабатываются идемпотентно.

`scripts/verify_queue.py` проверяет пять последовательных запросов и пакеты 1/3/10
через настоящую Celery/Redis, ровно один fixture-вызов на задание, собственную версию
каждого чата и нулевой расход. Повторная fixture использует корректный кеш браузерных
доказательств: тест измеряет доставку, а не браузер/модель. Результат —
`.data/queue-verification.json`. В финальном прогоне пять отдельных запросов ждали
0,014–0,029 с. Пакет из 10 одновременно завершился без дублей и смешивания чатов,
но максимальное ожидание достигло 14,6 с при ограничении одного активного задания
провайдера. Производительность массовой одновременной нагрузки не заявляется как
мгновенная; строгий FIFO не обещан.

После остановки локальных процессов перед миграцией подтверждено отсутствие активных
запусков и пустая Redis-очередь проекта на порту 56379: удалено **0** сообщений,
`unacked=0`. Никакие чужие Redis/Docker-ресурсы не очищались.

49 backend-тестов на PostgreSQL покрывают гонки бюджетов/username, повторную доставку,
ошибку брокера, race метки outbox, восстановление receipt/кандидата, неизвестный расход,
поздний ответ, ровно одну автоправку, unverified и инфраструктурные ошибки, приватную
диагностику, метрики recheck и наследование выбранной модели при продолжении.
Сбой хранения кандидата или программная ошибка упаковщика не отправляются модели
как ошибка игры и не расходуют автоправку: receipt остаётся доступен для продолжения.
Дополнительно проверено, что пустая правка с сообщением об успехе не создаёт одинаковую
версию: `no_changes` получает одну штатную автокоррекцию. Явный ответ `unchanged`
завершается объяснением без новой версии, проверки и автоматического повторного запроса.
Точный сохранённый ответ проблемного реального запуска `aa2739d9-bb56-45a7-96a8-b59f6e7510d9`
проверен только чтением и теперь отклоняется `no_changes`; сама игра не исправлялась вручную.

При неизвестном исходе запроса промежуточный usage сохраняется только для диагностики:
`cost_usd=NULL`, весь резерв учитывается один раз в неизвестных обязательствах.
Окончательный receipt заменяет резерв известной стоимостью без двойного учёта;
достоверный отказ до исполнения по-прежнему освобождает резерв с нулевым расходом.
Оба случая покрыты регрессиями. Операция определяется сохранённой базой запроса:
без базы — `create`, до первого кандидата доработки — `edit`, после кандидата — `repair`.
Отказ контракта не переводит исходную пользовательскую правку в `repair` преждевременно.

После пересборки защиты от no-op **внутри app-контейнера** на отдельной временной
PostgreSQL test database повторены три интеграционных теста: пустое `ok` не принимается;
штатная единственная автоправка исправляет no-op; явное `unchanged` не создаёт версию,
не вызывает браузер и не повторяет модель. **3/3 прошли за 1,461 с**. В этих негативных
сценариях ответы контролируются тестом, используется настоящий `materialize` и
backend-оркестратор; браузер заменён наблюдаемой заглушкой, чтобы проверить отсутствие
лишних вызовов. Это отдельно от HTTP-проверки контейнерной поставки выше.

## Изоляция и конфигурация

Фактический Docker inspect подтверждает у validator:

- `network_mode: none`, read-only root, непривилегированный UID 10001;
- `init: true`: завершённые дочерние процессы Chromium собирает PID 1;
- `cap_drop: ALL`, `no-new-privileges`, лимиты памяти/CPU/PID;
- только служебный named volume Unix-сокета, без bind mount исходников/host socket;
- нет DB/Redis паролей, Django secret, Codex авторизации или ключа модели.

Приложение, БД и Redis находятся во внутренней сети. Только edge имеет ingress и
публикует порты на `127.0.0.1`; worker дополнительно имеет сеть для будущего API модели.
Авторизация Codex не помещается в образ или Compose-контейнеры.
Проверенные значения финального Docker inspect и конфигурационные результаты
записаны в `.data/container-security.json` без значений секретов.

Проверены два отрицательных/конфигурационных случая:

1. Пустой `DJANGO_SECRET_KEY` отклоняется при запуске Django, нет встроенного ключа.
2. При provider=vllm и пустом `CONTAINER_MODEL` используется явно заданный
   `GAMEFORGE_VLLM_MODEL`, а не `fixture`. Тариф и execution limits задаются оператором;
   реальный API локальной LLM в этой проверке не вызывался.

Найдены и исправлены ошибки поставки: edge только во внутренней сети не предоставлял
фактический published port в используемом Docker; отдельная ingress-сеть только для
edge решила доступ. nginx теперь разрешает имена app/preview через Docker DNS,
поэтому пересоздание контейнеров не оставляет старые IP upstream. Preview settings
не подключает admin/messages, которым требовались отсутствующие auth/session middleware.

## Длительная работа браузера

В длинном реальном пилоте обнаружено накопление примерно 140 zombie-процессов
Chromium/crashpad: прежний PID 1 (`sleep`) не собирал осиротевшие дочерние процессы.
Лимит в 256 процессов исчерпывался и приводил к `TargetClosed`, хотя OOM не было.
Локальный launcher теперь использует Docker `--init`, Compose validator — `init: true`.
Профиль локальной проверки отклоняет контейнер без init до выполнения игрового кода.
Лимит процессов не повышался.

`scripts/verify_validator_lifecycle.py` выполнил **40 последовательных настоящих
browser jobs**, каждый с тремя проверками fixture, в отдельном
`gf-mini-validator-tests`. Все 40 прошли за **97,450 с**; baseline и каждое измерение
после задания: **3 процесса, 0 zombies**. `pids_limit` оставался 256. Результат:
`.data/validator-lifecycle.json`. Ни модели, ни пользовательские игры в серии не участвовали.
Этот тест проверяет lifecycle; последующие изменения наблюдения state проверяются
отдельными браузерными регрессиями и не требуют повторения сорока одинаковых запусков.
После обновления безопасного snapshot state выполнены **10 настоящих browser
регрессий**, включая неизменность `sideEffects` при вложенных getters/toJSON и полный
путь через Unix-сокет. Затем локальный и Compose validator пересозданы с актуальным
runner; фактический Docker inspect подтверждает `init=true`, `network=none` и
`pids_limit=256` у обоих контейнеров. Финальный HTTP-прогон выше использует эту сборку.

## Воспроизведение

```sh
docker compose build app validator
docker compose up -d
.venv/bin/python scripts/verify_container.py
.venv/bin/python scripts/verify_queue.py
VALIDATOR_CONTAINER=gf-mini-validator-tests sh scripts/validator-start.sh
.venv/bin/python scripts/verify_validator_lifecycle.py
```

Перед изменением схемы остановить worker/app; затем применить миграции и запускать
все компоненты из одной версии. Тестовые JSON и приватные артефакты в `.data/`
исключены из Git. Проверка доступного macOS WebView описана отдельно:
[wkwebview-smoke.md](wkwebview-smoke.md).

Не проверены реальный vLLM-сервер, конкурсный WebView, внешний домен/TLS и физическое
мобильное устройство. Эти результаты нельзя выдавать за подтверждение такой среды.
