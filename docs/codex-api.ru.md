# Pro через отдельный Codex Worker

26.10.2026. Провайдер `codex_api` подключает GameForge к самостоятельному сервису
Codex Worker HTTP v1. Текущий адрес сервиса — `https://72.56.101.64`.
Одинаковое подключение поддерживается на локальном компьютере и облачном GameForge;
для каждой установки используется собственный client token и отдельный владелец очереди.
Авторизация ChatGPT остаётся на сервере Codex. GPU к этому пути отношения не имеет.

## Поведение

`GAMEFORGE_PRO_PROVIDER=codex_api` меняет транспорт режима Pro. Локальный вариант
`GAMEFORGE_PRO_PROVIDER=codex` продолжает работать через прежний CLI/login.
Выбор не передаётся из браузера произвольной строкой: клиент выбирает Pro/Lite,
а сервер закрепляет провайдера и модель в Run. Автоматического перехода между API и CLI нет.
Текущая модель Pro — `gpt-6-sol`.

Планирование, политика оформления и анимаций, reasoning effort, full/compact,
ограниченные кадры валидатора и ремонт остаются теми же. API получает инструкции,
текст, точную JSON-схему операции и допустимый кадр конкретного кандидата.
Сервис возвращает данные; доступа к файлам, shell или браузеру приложения у модели нет.

UUID Invocation, origin, точный payload и отпечаток клиентского ключа сохраняются
в PostgreSQL **до** сетевой отправки. Повторный обработчик сначала получает прежнее
задание; повторная доставка на тот же UUID не создаёт новое исполнение. Результат
забирается отдельным GET `/result`, проверяются UUID, hash запроса, модель и hash квитанции.
Ответ после дедлайна новых вызовов всё равно можно получить. Сбой сохранения результата
в приложении приводит к повторному GET, без нового UUID.

Отмена доставляется через сохраняемый в БД запрос, включая отмену до PUT. Поздний
результат учитывается, но не применяется к отменённой игре. Unknown сохраняет частичный
текст, известный usage и неизвестную стоимость; повторное исполнение автоматически
не запускается. Изменение URL/ключа при незавершённых запросах блокирует доставку до
восстановления прежнего подключения, чтобы случайно не отправить работу другому владельцу.

Клиент не использует proxy из окружения, не следует redirect и проверяет HTTPS.
HTTP разрешён только для loopback в тестах. Runtime-зависимости на соседний проект нет;
адаптер реализует его HTTP v1, тесты используют независимого протокольного двойника.

## Локальный запуск

Сохранить отдельный токен в закрытом файле (0600), создать каталог для публичного
снимка моделей и добавить в существующий `.env`, сохранив настройки Lite и Codex-login:

```dotenv
GAMEFORGE_PRO_ENABLED=1
GAMEFORGE_PRO_PROVIDER=codex_api
GAMEFORGE_CODEX_API_URL=https://72.56.101.64
GAMEFORGE_CODEX_API_KEY_FILE=/absolute/private/path/local-client.token
GAMEFORGE_CODEX_API_CATALOG=/absolute/path/codex-api-catalog/catalog.json
```

`GAMEFORGE_PROVIDER=relay` и параметры Lite можно оставить прежними. Если Pro должен
быть также провайдером запросов без явного профиля, выбрать
`GAMEFORGE_PROVIDER=codex_api`, `GAMEFORGE_MODEL=gpt-6-sol`; Lite настроить отдельно.

```sh
.venv/bin/python manage.py refresh_codex_api_catalog
.venv/bin/python scripts/dev.py stop
.venv/bin/python scripts/dev.py start
```

Останавливать процессы только после завершения активных запусков. Авторизацию локального
Codex не удалять. Для возврата к CLI дождаться окончания удалённых Invocation, затем
вернуть `GAMEFORGE_PRO_PROVIDER=codex` и перезапустить процессы. Если менялся общий
`GAMEFORGE_PROVIDER`, вернуть и его. Учёт старых API-запросов сохраняет прежний транспорт.

## Облачный запуск

Использовать третий Compose-файл `deploy/codex-api.cloud.compose.yaml` **вместо**
`deploy/codex.cloud.compose.yaml`. Дополнить закрытый `.env` выпуска:

```dotenv
GAMEFORGE_PRO_ENABLED=1
GAMEFORGE_PRO_USER_IDS=1,2
GAMEFORGE_CODEX_API_URL=https://72.56.101.64
GAMEFORGE_CODEX_API_KEY_HOST=/opt/gameforge/secrets/codex-api-cloud.token
GAMEFORGE_CODEX_API_CATALOG_HOST=/opt/gameforge/codex-api-catalog
```

ID 1,2 — ранее согласованные аккаунты текущего стенда; в другой установке указать
реальные разрешённые ID. Новые пользователи автоматически Pro не получают.
Файл ключа должен читаться UID 10001 (0600); каталог снимка должен быть доступен
на запись worker UID 10001 и на чтение app. Содержимое снимка не содержит секретов.

```sh
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml \
  -f deploy/codex-api.cloud.compose.yaml config --quiet
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml \
  -f deploy/codex-api.cloud.compose.yaml run --rm --no-deps -T worker \
  python manage.py refresh_codex_api_catalog
docker compose --env-file .env -f compose.yaml -f deploy/cloud.compose.yaml \
  -f deploy/codex-api.cloud.compose.yaml up -d --no-build
```

На существующем сервере применять штатный порядок обновления: нет активных вызовов,
резервная копия, миграции, переключение, проверка. Не удалять БД и не создавать
служебные чаты для проверки выпуска. Только worker получает ключ API; app читает
снимок каталога, preview/validator/beat не получают ключ. CLI и auth-home не монтируются.

## Проверка и диагностика

Worker обновляет снимок health/models раз в минуту. Снимок старше трёх минут,
остановленная очередь или отсутствующий исполнитель делают Pro недоступным для новых
запусков. Получение уже отправленных ответов от снимка не зависит. Обновление каталога
не вызывает модель и не доказывает доступ аккаунта к реальной генерации.

`manage.py diagnose_invocation UUID` показывает ID удалённого задания, причины ожидания,
ошибки доступа и hash квитанции без запроса/ответа/секретов. История вызовов и usage
сохраняются в GameForge и отдельно в сервисе. Квота подписки принадлежит одному аккаунту
на сервере Codex; два клиента не создают независимых квот.

Реальный пилот требует отдельного бюджета. Для этой поставки согласованы максимум
два коротких вызова Pro за 15 минут; время отсчитывается с первой отправки. Отдельные
задания проверки соединения не должны создавать Chat/Run в пользовательских аккаунтах.
