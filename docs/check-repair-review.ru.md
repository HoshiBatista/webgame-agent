# Сохранение кода и отдельное восстановление проверок

24 октября 2026. Продолжение [живого пилота v5](lite-v5-pilot-2026-10-24.ru.md).
Новых вызовов Lite/Codex нет; закрытый бюджет пилота не используется. GPU-сервер
и адаптеры Codex/relay/vLLM не изменялись.

## Изменение поведения

Контракт v6 разделяет комплектность исходников и пригодность сценариев. Если полный
структурно корректный create содержит исполняемую реализацию, но семантически неполные
проверки, приложение сохраняет кандидат с точными исходниками и исходным checks.
Повторный create ради исправления сценариев больше не нужен. Пустая реализация
по-прежнему остаётся incomplete_sources и не становится игровым кандидатом.

По отдельному решению приложения разрешён компактный шаг check_repair. Он не возвращает
исходники, патчи, название или дизайн. Ответ привязан к UUID базы, hash экспортируемого
HTML и hash исходного checks. Для всех существующих проверок неизменны ID, категория,
текст требования и viewport. Недостающие обязательные категории получают условия от
приложения на основе первоначального запроса/дизайна; каталог игровых механик не нужен.
Удаление условия, подмена базы или передача исходников отклоняются.

Меняться могут действия, наблюдение и ожидание сценария: ошибочный путь к закрытой
переменной или неверная последовательность победных ходов не должны менять правила
игры. Это предложение модели, **не независимое доказательство корректности проверки**.
Новая Revision хранит исправленный checks с теми же побайтовыми исходниками, HTML/hash,
названием и дизайном; предыдущая Revision и ответ модели остаются в истории.

Исправленный набор обязательно проходит обычный изолированный браузер. Даже если
сценарии прошли, checks_review_required не позволяет автоматическое принятие: сохраняется
unverified с перечнем всех условий и явным подтверждением по текущему hash/отчёту.
При ошибке игры или отсутствии обязательных gates подтверждение недоступно. Успешное
явное подтверждение отмечается как manual; последующие обычные правки могут снова
проходить стандартную автоматическую проверку. Публикация и последняя принятая игра
не меняются до принятия новой версии.

## Ограничения цикла и восстановление

- Нормальный ответ по-прежнему требует один модельный вызов. Новый шаг появляется
  только при проблеме проверки, в общем сохранённом лимите Run и с прежним deadline.
- Для одного hash исходников в цепочке продолжений сохраняется не более одной попытки
  check_repair. Неудачный JSON, нарушение контракта или отсутствие полезного изменения
  не запускают бесконечный ремонт. Кандидат остаётся доступен для разбора.
- При effect_mismatch полного набора нужны доказанные обязательные browser gates;
  неполный инфраструктурный отчёт не доказывает ошибку игрового сценария. Синтаксис,
  runtime/network, отсутствие Canvas и overflow сохраняют свой маршрут ремонта.
- Если модель отказалась менять сценарии, существующая допустимая ручная проверка
  остаётся доступной. Исходники ради этого отказа не переписываются.
- Сбой после receipt использует сохранённый точный ответ; отмена оставляет receipt,
  но не применяет его. Recheck не вызывает модель и не снимает отметку ручной проверки.
  Неизвестный usage/расход сохраняется отдельно и требует прежнего явного согласия.
- Начатые контракты v2–v5 и старая политика завершения сохраняют прежнее поведение.
  Новый явный запуск может использовать v6; текущий Invocation не переинтерпретируется.

Нужна миграция 0010_check_review_required, сборка интерфейса и перезапуск приложения.
Новый внутренний статус показывает «Уточняем проверки сохранённой игры».

## Проверки и ревью

Регрессии проходят полный путь provider → строгая схема → сохранённый receipt →
материализация → браузер/оценка → ручное подтверждение. Проверяются сохранение кода
при неполном checks, запрет подмены источников/условий/hash, общий лимит, отказ/ошибки
предложения, unknown, отмена, восстановление после аварии, model-free recheck,
запрет автоматического принятия и сохранённое поведение v5. RPC-имитатор Codex
получает отдельную схему check_repair через настоящий адаптер без inference.

Два новых сценария настоящего Chromium используют реальные касания: восстановление
недостающего outcome и исправление неверного числа действий до победы. На исправленной
версии весь набор проходит, исходники совпадают, автоматического принятия нет.

[Replay двух сохранённых случаев Lite](evidence/check-repair-replay-2026-10-24.json)
проверяет именно прежние байты: рабочий сырой grid, отклонённый с missing_effects,
теперь материализуется без изменений; сохранённый grid с неверными победными/ничейными
действиями получает отдельный набор. По 5/5 сценариев прошли в native sandbox, hashes
обеих игр совпали с пилотом. Сценарии replay написаны независимо вручную: это проверка
механизма на реальных артефактах, не доказательство способности Lite исправить проверки.

Итог: **463 backend**, **26 браузерных** сценариев, **75 UI**; Ruff, mypy,
Django check, проверка миграций, ESLint/Prettier, TypeScript/build и diff-check прошли.
После уточнения формулировок добавляемых условий отдельно перепроверены все 24 новые
backend-регрессии. Миграция 0010 применена локально, native-preflight успешен;
app/preview/worker/beat перезапущены и работают. Активных генераций перед перезапуском нет.

При собственном ревью отдельно проверены границы доверия: модель не меняет требования,
успешный отчёт пересмотренных сценариев не становится automatic, недостаточные gates
не запускают пересмотр полного набора, неизменённый ответ не уничтожает допустимую
ручную проверку. Известный и неизвестный расход не смешиваются. Финальные результаты
наборов и локальное применение миграции записаны в [журнале проверок](verification.md).

Ограничения: не восстанавливается произвольный испорченный JSON или неизвестная схема;
такие ответы по-прежнему сохраняются приватно для диагностики. Нельзя автоматически
доказать правильность новых игровых последовательностей по самоотчёту той же модели,
поэтому их принятие остаётся явным. Увеличение доли автоматических принятий реальной
Lite ещё не измерялось; эти тесты не заменяют новый согласованный живой пилот.
Неоднозначный effect_mismatch при невозможности надёжно исправить сценарий остаётся
на разборе, вместо автоматического изменения игровых правил. Доказанные ошибки
синтаксиса/выполнения сохраняют обычный ограниченный ремонт исходников.
