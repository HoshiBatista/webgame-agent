# План следующей поставки харнесса для Sol 6.1

25 октября 2026 года. Статус: **задание на реализацию, ещё не выполнено**.
Этот документ задаёт следующую поставку после повторного пилота v8. Он не продолжает
нумерацию S0–S5 из старого плана первой поставки v7.

Основания: [исследование R2](harness-r2-research-2026-10-25.ru.md),
[его проверяемые данные](evidence/harness-r2-research-2026-10-25.json),
[повторный пилот](lite-v8-r2-pilot-2026-10-25.ru.md),
[независимое ревью v8](v8-independent-review-2026-10-25.ru.md).

**Sol выполняет S0–S10 целиком без модельных вызовов**, с ревью после S3, S6 и S9.
Результат — исправленная реализация, воспроизводимые регрессии, работающий контрольный
путь ремонта механики с имитатором провайдера и пакет для независимого ревью.
S11 — отдельный живой эксперимент после ревью и нового разрешения на расход.

Цель поставки — получать достоверные браузерные сведения, сохранять пользовательскую
задачу и направлять ремонт на воспроизведённый дефект. Рост качества 27B устанавливает
только S11. Зелёные тесты приложения сами по себе его не доказывают.

## Границы исполнения

- Репозиторий: `/Users/noxlight7/study/GameForge/GameForge`, ветка `mini-games`.
  Перед работой проверить фактические cwd, HEAD и изменения. Незакоммиченный v8,
  исследование и правки фронтендера являются исходной точкой. Не применять reset/clean.
- Сохранить Django/DRF, PostgreSQL, Celery/Redis, Run/Invocation, точную адресацию
  source_revision, отмену, восстановление receipt, учёт known/unknown и Codex.
- Не обращаться к GPU-серверу, не менять relay deployment, веса, vLLM, sampling,
  credentials или `.env`. Не делать SSH, облачный deployment и обновление зависимостей.
- Не делать inference, включая Codex turn/start. Старые бюджеты закрыты. Разрешены
  имитаторы API, JSON-RPC doubles и изолированный native/Docker Chromium.
- Не перезапускать пользовательское приложение ради тестов. Использовать отдельные
  тестовые БД/контейнеры. Применение миграций к рабочей БД и rollout — отдельная операция.
- Старые игровые контракты не поддерживать. Изменение контракта допускает вывод старых
  игр из эксплуатации, но не удаление пользователей, Invocation и неизвестного расхода.
  Сейчас подготовить проверяемый переход; удаление рабочих данных для тестов не нужно.
- Не добавлять обязательные planner/critic, каталог готовых игр, новый workflow engine,
  произвольный shell/evaluate у генератора, скрытые повторные вызовы или новый DSL проверок.
- Full остаётся основным профилем. Compact lines — экспериментальный. Нельзя включать
  compact всем по результатам unit-тестов или менять закреплённый формат незавершённого Run.
- Не отправлять задачи другим чатам и не создавать агентов. Ревью в ходе исполнения
  выполняет Sol отдельными проходами; последующее независимое ревью выполняется отдельно.
- Не останавливаться после локальной правки, если остальные пункты поставки выполнимы.
  Недоступный тестовый backend описать точно и продолжить независимые проверки; не
  заменять изоляцию запуском сгенерированного кода на хосте.

## S2 Допуск сценариев и watchdog

Файлы: `validation/contracts.py`, `service.py`, `native.py`, `daemon.py`, `runner.py`,
`checks.py`; тесты `test_validation.py`, `test_check_semantics.py`, `test_artifact_evidence.py`.

1. Разделить ограничение стоимости браузера и корректность отдельного сценария.
   Чрезмерное суммарное ожидание получает invalid_check; оно не исполняется и не
   предотвращает syntax/load/surface/module проверки кандидата.
2. Общие ограничения входа остаются жёсткими: размер payload, максимум проверок,
   шагов и действий. Нельзя делать большой обход/запуск браузера по неограниченному
   списку. Повреждённый внешний envelope отличается от ошибки конкретного check.
3. План исполнения и расчёт watchdog должны совпадать во всех backend. Не исправлять
   только service: native.execute и daemon также используют лимиты. Watchdog считает
   реально допустимые маршруты, обязательные probes и нужные контрольные исполнения.
4. Неподходящий сценарий не даёт права вслепую нажать Start. Если сцена доступна только
   после достоверного маршрута, отсутствие такого маршрута остаётся surface_unverified.
5. Один checkpoint допустим с абсолютным оператором. Для eq/contains он не меняет
   конечное сравнение, но сохраняет границу setup/измеряемого ввода. Несколько checkpoint
   и отсутствие нужного действия после границы остаются ошибками.
6. Не преобразовывать wait_for посреди сценария в wait и не исправлять неоднозначные
   координаты/ожидания автоматически. Представление и смысл — разные изменения.

**Регрессии:** F01/F02/F09, смешанные valid/invalid сценарии, пустой suite, oversized
вход, настоящий browser timeout, обязательный receipt, stale validator, одинаковое
поведение native и Docker. API recheck делает 0 Invocation и сохраняет source/checks hashes.

## S3 Runtime и безопасные наблюдения

Файлы: `generation/runtime/`, `generation/compact.py`, `validation/diagnostics.py`,
`runner.py`, `evidence.py`; тесты compact, diagnostics и browser.

**Общий цикл.** Обновление механики вызывается только при наличии update; отрисовка
после успешной регистрации работает и без него. Сохранить dt в секундах, ограничение
шага времени, обработку исключений, DPR, геометрию и release/blur. Не добавлять второй
animation loop. Runtime v2 встраивается в новые экспорты; сохранённый HTML не перепаковывать
при чтении/recheck. Ошибка render/update остаётся блокирующей.

Проверить, не создаёт ли новый paint лишнюю частоту обновления механики и побочные
эффекты в render. Правило compact: render читает игровое состояние; изменения правил
идут через input/update/обычные callbacks. Это правило подсказки и тестов, а не обещание
автоматически доказать чистоту любого JavaScript. Не переписывать чужую игру эвристикой.

**Каталог.** Считывать только собственные data properties выбранного корня.
Неподходящее свойство пропускать с причиной, не теряя остальных разрешённых полей.
Не выполнять accessor/function; запрещённые paths и self-report остаются запрещёнными.
Циклы, глубина, число свойств, общий размер и время ограничены. Пропуски отражаются
структурно, например reason/truncated; не возвращать обрезанную JSON-строку вместо объекта.
Произвольные объекты могут быть Proxy: не заявлять отсутствия любых побочных эффектов
рефлексии; изоляция и watchdog остаются обязательны, недоступный snapshot не является pass.

**Регрессии:** F03/F04/F10, реальный пиксель после таймера, неисполненный getter-canary,
безопасный scalar рядом с unsafe полем, cycle/large/deep объект, закрытая переменная,
resize без сброса, удержание/отпускание, runtime exception, версия runtime в receipt.

**Ревью A:** проверить diff S0→S3, отрицательные fixtures и отсутствие изменения
игровых правил ради проверок. Исправить найденное до продолжения. Зафиксировать выводы
в отчёте; отдельное сообщение пользователя для перехода к S4 не требуется.

## S4 Свидетельства ввода и исхода

Это наиболее рискованный этап. Не ограничиваться seed=1 и удалением effect_not_causal.
Основные файлы: `validation/runner.py`, `checks.py`, `contracts.py`, `service.py`,
`evidence.py`, `studio/acceptance.py` и `tasks.py`. На S4 доверенный таймерный критерий
проверяется через тестовый вход валидатора; его производственный источник и запрет
подделки подключаются в S7–S8. До этой интеграции обычный поток его не использует.

**Два отдельных результата:** обычный сценарий с естественными временем/случайностью
и диагностическая пара для конкретного утверждения. Их условия, статусы и hashes
должны быть различимы. Успех искусственно ускоренного времени не заменяет обычную игру.

### Эффект ввода

- Основной и контрольный диагностические маршруты получают одинаковый объявленный
  seed, viewport и профиль времени. Использовать существующий test_profile, а не
  добавлять модели инструменты подмены игровых переменных.
- Seed выбирать воспроизводимо приложением из стабильного digest идентичности проверки,
  не из процессного Python hash; не перебирать до успешного результата. Для повторов
  corpus заранее закрепить как минимум два seed.
- Сохранять setup до измеряемого участка, полезное действие и связанные releases.
  Безуспешный/упавший контрольный запуск не доказывает причинность.
- Хранить precondition snapshots доступных наблюдений. При несовпадении существенных
  доступных начальных условий либо недостоверном времени возвращать inconclusive.
  Одинаковый seed не доказывает равенство всей скрытой игры; зафиксировать эту границу.
- `causal_evidence` содержит mode, profile/hash, removed action indices, результаты
  двух маршрутов и сравнение условий. Оно привязано к artifact/check hash и валидатору.
  Старый булевый comparison без сопоставимых условий больше не достаточен.
- Постоянный и случайный флаг без обработки клавиши не проходят F05/F08. Реальные
  нажатие и отпускание продолжают проходить F06. Не требовать изменения картинки при
  каждом корректном действии.

### Исход который наступает по времени

Сам факт, что сценарий помечен outcome, не требует удаления последней клавиши.
Но и модельный ярлык timed_outcome не разрешает обход проверки победы.

В первой поставке добавить альтернативное свидетельство **только для доверенного
критерия контрольного корпуса**: фиксированное условие завершения по времени,
границы допустимого ожидания, действительный переход из незавершённого состояния,
видимый результат и независимая проверка игрового управления. Проверить, что после
окончания раунда заявленное управление больше не продолжает раунд. Проверка использует
обычное время; clock-профиль допустим дополнительно для диагностики.

Положительная F07 проходит этот тип критерия. Константа won=true не имеет нужного
перехода. Декоративный таймерный флаг не покрывает критерий «обе пары найдены».
Переключатель режима не принимается из ответа модели или публичного HTTP-запроса.
Для свободного пользовательского запроса без проверенного основания сохраняется
явное неподтверждённое условие; не обещать, что эта поставка автоматически распознает
все таймерные игры. Это сознательная граница первой реализации, проверяемая тестом.

Распространение на произвольные timed/collision outcomes — решение после S11.
Не вводить сейчас универсальный язык причин и зависимостей.

**Приёмка S4:** F05–F08, stale/подложное/неполное свидетельство, разные seeds/profiles,
исключение в контрольном запуске и неподтверждённый public-mode дают корректные результаты.
Watchdog учитывает дополнительную работу, service проверяет обязательные поля, cache
не смешивает обычный сценарий и диагностический профиль.

## S5 Трасса реальных действий

Файлы: `validation/runner.py`, `diagnostics.py`, `service.py`, `generation/feedback.py`.
Использовать существующий язык действий и один ограниченный браузерный запуск.
Постоянную browser session между модельными вызовами не создавать.

Трасса содержит: индекс и действие, наблюдавшуюся цель ввода, относительное время,
значение проверяемого поля до/после, несколько связанных разрешённых наблюдений,
ошибку или отметку unavailable. Фиксировать факты, не модельные объяснения причины.
Для wait сохранять контрольные точки без покадрового лога. Текущее значение после
отменённого/неисполненного действия нельзя подписывать как эффект этого действия.

Рабочие пределы: до 30 шагов; до 8 дополнительных scalar-наблюдений на шаг;
не более 32 КиБ трассы на check и 128 КиБ на отчёт; фокусный пакет модели до 8 КиБ
в сумме с diagnostic. При измеренной необходимости корректировать эти числа один раз
с объяснением и тестами границы. Не менять текущий общий сетевой лимит без необходимости.
При усечении оставлять первый проблемный шаг и последнее состояние, исходные индексы
и явный truncated. Все размеры считать в UTF-8 байтах.

Каталог полей брать из разрешённых объявлений и безопасных соседей, не из всего window.
Трасса и сырые наблюдения доступны владельцу через приватную диагностику. В ленту,
публикации и обычные логи исходники/снимки не выводятся. Проверить существующую
serialization: нельзя автоматически добавить весь объём в публичный report.facts.

Фокусный вход ремонта объясняет: проверяемое условие, реальные действия, ожидаемый
и полученный эффект, границы достоверности. `first_divergence` обозначать только там,
где есть промежуточное ожидание; при одной конечной проверке писать «первое наблюдённое
отклонение/конечное несовпадение», не выдумывать точную причину на раннем шаге.

**Приёмка S5:** F11 показывает реальную последовательность без победы; F12 — ввод,
изменение nextDir и отсутствие движения; F13 — действия с картами и отсутствие
завершения. Нет изменений code/checks, getters и тестовых hooks. Передача данных
проверяется до конечного provider request, включая redaction и усечение.

## S6 Контекст и формат модельных операций

Файлы: `generation/prompts.py`, `compact.py`, `schema.py`, `studio/tasks.py`;
тесты prompts, wire_contract, repair_contract и generation_providers.

- Разделить compact create/edit/repair/check_repair на короткие operation-specific
  инструкции. Общая часть содержит только действующий runtime/input/state контракт.
- В compact wire-контексте один явный source game.js и его hash. Не отправлять рядом
  пустой files, пустые дублирующие checks и инструкции full-патча. Внутренний request
  может хранить files для provenance; исправление касается реального входа модели.
- Для replacement-repair сообщать единственный разрешённый формат: полный малый модуль.
  Для exact-edit — только точные замены. Не давать меню нескольких форматов, если
  выбранная схема принимает один. Full и Codex продолжают получать свой корректный формат.
- Передавать исходную пользовательскую задачу, актуальный source, один основной
  воспроизводимый симптом и необходимые регрессии. Ошибка последнего ответа хранится
  отдельно от нерешённой ошибки игры; прошлый синтаксис не заслоняет новый runtime-дефект.
- Примеры интерфейса показывают накопление dt и живое state. Это небольшие примеры
  API, а не готовые snake/memory. Нельзя обещать, что prompt гарантирует правильность.
- Для check_repair только неизменный код, исходные условия и реальные наблюдения;
  никакого приглашения подстроить expected под actual. Unchanged с непустыми изменениями
  остаётся отклонённым; не нормализовать его молча в ok.
- Сохранить ASCII-pattern исправленного lines, точный LF join, лимит модуля и запрет
  угадать формат ответа. Нельзя восстанавливать пропущенный код или world по эвристике.

**Приёмка S6:** table-driven проверки всех операций × full/compact × string/lines
для применимых сочетаний. Реальные сериализаторы relay/vLLM и Codex prompt/schema
проверяются на имитаторах. F15 содержит source в конечном сообщении, один разрешённый
формат и актуальный hash. Новые prompt/schema fingerprints сохраняются в Invocation.

**Ревью B:** прочитать конечные сообщения провайдеру, а не только промежуточный dict.
Проверить, что трасса не стала каналом доступа к хосту/секретам, seed не выдаётся за
полное доказательство причинности и не ослаблены требования для повышения pass-rate.

## S7 Требования и происхождение утверждений

Файлы: `studio/models.py`, `services.py`, `tasks.py`, `acceptance.py`, `serialization.py`,
`generation/check_repair.py`; по необходимости `web/src/types.ts`, `Studio.tsx`.

Ввести небольшой версионированный `requirements_context` — неизменяемый JSON-снимок
пользовательской задачи на Run и Revision с миграцией. Run получает его **до первой
отправки**, Revision наследует этот снимок. Не включать в него будущие ответы модели
или изменяющийся вердикт проверки. Распределение данных:

| Данные | Где хранятся и какое правило действует |
| --- | --- |
| Исходный текст задачи и hash | requirements_context: сохранённый game_request без модельного пересказа |
| Цепочка явных пользовательских изменений | requirements_context: связанные ID сообщений/Run и тексты; не собирать заново по последнему чату |
| Ссылка на критерии контрольного опыта | requirements_context: только утверждённый оператором immutable manifest, его hash и точная база |
| Предложения сценариев | Неизменяемые checks конкретной Revision и явное происхождение model_proposed; не переписывать ими context Run |
| Покрытие | CheckReport.assessment: not_assessed / partial / verified, критерии и свидетельства, привязанные к context/artifact/checks hashes; значение verified не назначает модель |

Покрытие вычисляется заново в новом отчёте, а не меняет исходную задачу задним числом.
Здесь verified означает подтверждённую полноту выбранных критериев, а не успех игры:
их результаты passed/failed/unverified хранятся отдельно. Игра с полным набором
проваленных критериев не готова; набор прошедших частичных критериев не доказывает
полноту задачи. Эти два отрицательных случая обязательны в тестах оценщика.
Один и тот же HTML с другой задачей или критериями не может получить чужой вердикт
из cache. Добавить context/criteria identity в check_identity и основание ручного
подтверждения; не считать UI-параметр или JSON модели источником этого доверия.

Не создавать граф требований, универсальный GameSpec или отдельный сервис. Проверка
цитаты/ссылки на исходный текст не доказывает семантическую полноту. Для свободного
запроса без независимой оценки использовать not_assessed, не выдумывать проверенный список.

Check_repair продолжает сохранять идентичность исходных сценарных утверждений.
Если само утверждение противоречит задаче, это отдельное `requirement_conflict`,
которое нельзя исправить сменой expected и объявить пройденным. В этой поставке
конфликт устанавливает доверенный корпус/оператор; не внедрять keyword-классификатор
для произвольного естественного языка. Семантическое исправление требует отдельного
решения с сохранением предыдущего снимка.

Не переименовывать все существующие статусы Run. `succeeded`/verification=automatic
продолжают означать выполнение принятого автоматического набора. В сообщении писать
«Автоматические проверки пройдены», не утверждать полноту пользовательской задачи,
если coverage=not_assessed. Метрика готовности в оценщике отдельно требует независимого
покрытия критериев. Не снимать check_suite_revised; ручное подтверждение связано с
актуальными artifact/report/context hashes и не становится автоматическим.

Новый edit наследует снимок выбранной source_revision и добавляет только явное
пользовательское изменение. Recheck/repair/check_repair не меняют задачу. Продолжение,
recovery, ремикс и конфликт принятой базы не должны потерять происхождение. Старым
записям миграция не выдаёт verified и не подделывает отсутствующую историю.

**Приёмка S7:** F14, source draft отличается от accepted base, две последовательные
правки, recheck без нового сообщения, подложный клиентский verified, stale context при
подтверждении, невозможность изменить исходный запрос ответом модели. В UI исходная
задача и модельные проверенные условия различимы без технических подробностей.

## S8 Контрольный путь ремонта механики

Основные файлы: `studio/tasks.py`, `acceptance.py`, `services.py`, `generation/code_repair.py`,
`source_policy.py`, `feedback.py`, `scripts/evaluation.py`; новая узкая операторская
команда в `studio/management/commands/`. Не создавать второй независимый цикл генерации.

Цель — проверить весь механизм выбора ремонта без изменения общей политики на основании
одного effect_mismatch. Добавить выключенный по умолчанию режим измерений; обычный
публичный API не принимает trusted=true, произвольные criteria, repair_basis или
переключатель обхода causal-проверки. Не полагаться только на staff из JSON-клиента.

Доверенный manifest загружается локальной операторской командой из подготовленного
корпуса. Он фиксирует критерии, сценарии, ожидаемый исход проверок, права изменения,
source/check hashes и профиль среды. При импорте создаётся отдельная контрольная копия;
старые Run/Invocation и результаты пилота не переписываются. Не подключать старый
декодер v8: переносить конкретный исходник как fixture текущего контракта и фиксировать
изменение упаковки/hash, если runtime был обновлён.

Операторские критерии настраиваются до вызова модели. Они должны быть проверены на
отрицательной и исправленной положительной версии. Требование полноты baseline checks
сохраняется; для контролируемого семантического repair использовать комплектную,
заранее проверенную suite. При incomplete checks остаётся прежний code_repair_basis
только для доказанного syntax/runtime/geometry/module дефекта.

Приложение формирует `semantic_repair_basis`, только если одновременно выполнены:
точная source_revision/artifact, полный проверенный набор условий, актуальный receipt,
валидный доверенный manifest и воспроизведённый failed критерий. В основании нужны
manifest/criteria/checks hashes, report ID/identity, validator/profile и список failed IDs.
Модель не может его создать или повысить уровень доверия своим ответом.

Manifest закрепляет исходную базу опыта; после repair новый basis относится уже к
новой Revision и её свежему отчёту. Принимать только доказанную цепочку потомков
этой базы с неизменными критериями и владельцем. Не переписывать manifest под новый
source hash и не переносить разрешение на постороннюю игру. Проверить повторный
repair допустимого потомка и отказ для чужой ветки отдельно.

| Наблюдение | Следующий шаг |
| --- | --- |
| Незавершённая Invocation | Сначала восстановить её исход; диагностика не создаёт новый вызов |
| Ошибка инфраструктуры | Recheck без inference, никакого source repair |
| Доказанный syntax/runtime/module дефект | Существующий ограниченный source repair |
| Дефект сценария при рабочем артефакте | Ограниченный check_repair либо review |
| Только effect_mismatch без доверенного основания | Диагностика/review; код сохраняется |
| Failed независимый критерий в контрольном режиме | Source repair по точному semantic_repair_basis, с неизменными критериями |
| Модельный check_repair прошёл | Сохранить явное подтверждение новых сценариев |
| Исчерпан лимит или нет прогресса | Конечный объяснимый результат с лучшим сопоставимым кандидатом |

Ремонт получает один выбранный модуль, один главный симптом и трассу, сохраняет
остальные исходники и весь набор проверок. После правки выполнить полный набор,
включая независимые проверки, не переданные модели. Исправление одного сценария
с регрессией остальных не становится успешным ремонтом.

Критерий «лучший кандидат» применяется только к одной базе и неизменным критериям:
сохранять последнюю подтверждённую версию, отдельно показывать текущий черновик.
Не ранжировать разные наборы проверок по числу passed. Повтор без изменения artifact
и свидетельства не открывает новый цикл; действующие лимиты и конечные состояния
сохраняются. Регрессии проверяют завершение при повторном дефекте и исчерпании бюджета.

Отдельный модельный запрос для предложения диагностических действий **не входит
в первую поставку**. S5 даёт автоматическую трассу. Если её недостаточно, S11 измеряет
этот предел; не добавлять новый тип Invocation и постоянную браузерную сессию заранее.

**Сквозные регрессии S8:**

- Имитатор создаёт дефектную memory → настоящий Chromium воспроизводит критерий →
  запрос repair содержит основание/трассу → имитатор возвращает малый модуль →
  браузер подтверждает обе пары и регрессии. Проверять реальные байты запроса.
- Рабочий grid с плохим модельным сценарием никогда не отправляется в source repair.
- Подложный/старый manifest, другой hash/checks/profile/owner и неполные checks
  не дают семантическое разрешение. Внешний API не позволяет включить доверенный режим.
- Повтор обработки receipt не удваивает правку/расход; сохраняются budget, deadline,
  cancel/fence и запрет повторять unknown. Recheck всё равно имеет 0 inference.
- Имитация «исправления» ожиданий или скрытого тестового флага отклоняется либо
  проваливает независимые проверки; хорошие проверки не заменяются модельными.

## S9 Сквозная совместимость и ревью C

Обязательные маршруты: create → validate; create → check_repair; create → syntax repair;
контрольный semantic repair; edit непринятого draft; recheck; продолжение после лимита;
Pending → восстановление receipt; cancel во время проверки; stale report при подтверждении.

Codex сохраняет существующую авторизацию, изоляцию и допуск версий. Проверить full
create/edit/repair/check_repair и редактирование compact через существующие RPC doubles,
без настоящего turn/start. Новый evidence/requirements context должен корректно доходить
до Codex prompt, а внутренние операторские разрешения не должны быть подделываемыми.
Новая модель/CLI и расширение allowlist для этой поставки не нужны.

Проверить pipeline/runtime/evidence/policy версии, fingerprints, миграции, serializer,
native/Docker packaging и invalidation cache. Нет маршрута, который молча считает
старый отчёт новым. Подготовить dry-run retire_games для перехода, сохраняя учёт и
объясняя, какие контракты будут несовместимы. Не выполнять удаление данных.

**Ревью C:** отдельный проход по собственному diff относительно S0. Проверить источник
каждого уровня доверия, все выходы в succeeded/manual, сохранность source_revision,
правила pending/unknown, бюджет и контрольные негативные случаи. Нельзя завершить
этап с известным P1/P2 в затронутом поведении. Исправить и повторить нужные проверки.

Нативные/контейнерные тесты запускать последовательно при общей тестовой БД. Наличие
зелёной имитации не заменяет браузер и наоборот. Полный набор повторять после итоговых
изменений; повторять уже прошедшие несвязанные проверки без причины не требуется.

## S11 Отдельный живой эксперимент

Начать только после независимого ревью S0–S10, готового оценщика и нового явно
согласованного бюджета. Не возобновлять остаток 25 вызовов последнего пилота.

Первая серия проверяет полезность трассы на одинаковых базах. Обе группы используют
исправленную платформу и одинаковые operation-specific prompts; единственное отличие
— наличие трассы в контексте. Так сравнение не смешивает исправление watchdog,
новый runtime и разные форматы ответа.

Пять заранее закреплённых случаев: рабочий grid с плохим сценарием, snake/dt,
memory/пары, синтаксическая ошибка малого модуля, рабочий код с дефектом наблюдения.
Для каждого до старта закрепить профиль, формат ответа, ожидаемую операцию и основание:
для рабочего кода — только check_repair, для доказанного дефекта — source repair.
Не принуждать рабочую игру к source repair ради равного количества вызовов.
Предлагаемый объём — 3 повтора × 2 группы × 5 случаев = **до 30 вызовов**, по одному
ремонтному вызову на опыт. Это предложение для согласования, не открытый лимит.
Число минут определяется новым разрешением; контроллер проверяет оба ограничения
перед каждой отправкой. Отказ/ошибка формата тоже расходуют попытку.

Группы получают одинаковые bytes баз и одинаковые критерии. Каждый опыт — отдельная
контрольная копия с новым ID; неизвестный старый запрос не пересылается. Порядок заранее
перемешать и сохранить. Оценщик получает заранее определённые критерии и дополнительные
проверки, которые не были переданы в repair. Историческую v8-статистику показывать
отдельно: она не является контрольной группой этого опыта.

Измерять исправление целевого дефекта, сохранение работающих условий, ошибочные
изменения кода, ложные подтверждения, невалидные ответы, calls/tokens/время. Проверять
каждый кандидат, включая неуспешные. Изменённый check_repair может оставаться unverified
по политике подтверждения — это не то же самое, что неработающая игра.

После этой серии принять отдельное решение о выпуске контрольной маршрутизации в
обычный продукт. До этого её флаг остаётся выключенным. Повторяемое преимущество
трассы полезно; три повтора не дают точной вероятности успеха. Если выигрыша нет,
разобрать точные ответы и следующим отдельным опытом сравнить код вместе со сценариями
против их раздельной генерации. Не включать новую обязательную модельную роль без опыта.

Новые создания full/compact lines и дополнительные жанры — следующая серия с отдельным
заранее зафиксированным планом/доступным остатком нового бюджета. Compact string не
объявлять снятым с поддержки только из-за трёх неудачных игр. Codex проверять живьём
только при отдельном разрешении; GPU-сервер по-прежнему не обследовать и не менять.
