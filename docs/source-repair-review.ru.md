# Неполные исходники и ремонт небольших модулей

24 октября 2026. Реализован первый срез D после
[диагностического пилота Lite](lite-completion-pilot-2026-10-24.ru.md): контракт v5
различает неполный первый ответ и игровой кандидат, а ремонт может заменить один
ограниченный файл без копирования старого текста. Это общий путь Codex, relay и vLLM.

## Новое поведение

При создании упаковщик обнаруживает отсутствующие локальные исходники, HTML-заглушки,
пустой/комментарийный JS и документы только с JSON-данными. Ответ получает
`incomplete_sources` **до создания Revision**. Исходный ответ, канонический JSON, usage,
стоимость и причина сохраняются в Invocation. Следующий вызов остаётся create без
выдуманной базы/патча и расходует прежний общий лимит Run. При исчерпании лимита
показана причина «модель не передала полную реализацию игры»; бесконечного повтора нет.

Проверка консервативная: наличие исполняемого кода — необходимый структурный признак,
а не доказательство полноты механики. Динамический Canvas, единственный HTML и inline
обработчики допустимы; конкретные имена файлов/состояния не навязываются. Непустой
синтаксически сломанный код остаётся задачей синтаксической проверки и ремонта.
Прежние правила неизвестной доставки/расхода не изменены.

Новое явное продолжение старой непринятой заглушки без рабочей базы может начать create.
Сначала используется уже полученный корректирующий ответ к точной базе: если он пригоден,
новый модельный вызов не нужен. Незавершённая доставка также не заменяется новой генерацией.
Событие `source_restart` содержит ID/hash прежнего кандидата; его исходники и история
не удаляются. После сбоя решение восстанавливается из этого аудита, и ожидающий патч
к прежней заглушке не применяется. Recheck без inference и уже начатые v2/v3/v4 Run
такой переход не выполняют.

Для настоящего кандидата repair v5 может получить `module_repair`: приложение выбирает
один существующий JS/CSS/JSON-файл по месту подтверждённого дефекта. При игровом дефекте
без координаты допустим единственный JS-файл игры; наличие одного маленького helper
среди нескольких JS не даёт такого разрешения. Если есть рабочая база, файл должен
уже отличаться от неё: косметический edit не разрешает переписать нетронутую механику.

Модель возвращает одну запись в patches:

```json
{"action":"replace_module","path":"game.js","file_hash":"<точный SHA256>","content":"<полный текст файла>"}
```

Размер **до и после — максимум 12 КиБ UTF-8**. Разрешение версии 1, список файлов и hash
сохраняются в запросе Invocation до отправки. HTML, новый/неразрешённый файл, чужая база,
неверный hash, превышение размера, смешивание с другими патчами и изменение checks
отвергаются до сохранения кандидата. Соседние файлы остаются побайтово прежними.
Обычный пользовательский edit и старые контракты сохраняют точные патчи. Последняя
принятая версия и публикация меняются только после обычной полной проверки нового кандидата.

## Регрессионные доказательства

- Заглушка → полноценный create даёт один кандидат и одну браузерную проверку;
  оба ответа и usage сохраняются. Повторные заглушки завершаются в том же лимите без Revision.
- Замена модуля сохраняет соседние исходники и весь проверочный набор. Неверный hash,
  путь, размер, смешанные операции и попытки ослабить проверки не меняют исходный артефакт.
- Сбой после сохранения неполного ответа или ответа replace_module восстанавливает
  сохранённый шаг: уже полученный модельный ответ не запрашивается второй раз.
- Отмена после получения замены сохраняет квитанцию, но не применяет модуль.
- Новое продолжение старой заглушки сохраняет её в истории. Сбой сразу после
  source_restart не возвращает процесс к старому ожидающему патчу.
- Публикация и рабочая версия остаются прежними после неудачного косметического edit;
  нетронутый JS не получает разрешение на замену.
- Сохранённые prompt/schema hashes v4 совпадают с паспортом реального пилота;
  v2/v3/v4 не принимают новый вид операции. Codex и API получают одну схему/контекст.

Два новых сквозных теста используют настоящий generation service, тестовый provider,
материализацию и Chromium в изоляции ОС. Они проходят пути неполный ответ → create →
автоматическое принятие и сломанное управление → replace_module → автоматическое принятие
после реальных pointer-сценариев. Это испытания процесса на тестовых играх, не свежий inference.

## Ревью

Проверены итоговые изменения, границы полномочий модели, сохранение бюджета/квитанций,
старые контракты, точная база, восстановление, отмена и неизменность рабочих версий.
В ходе ревью исправлены:

1. Передача сохранённой версии при materialize и локальном восстановлении ответа:
   старые исходники не проверяются новой политикой задним числом.
2. Недопустимое расширение ремонта на нетронутый рабочий JS после косметической правки.
3. Возврат к старому pending patch после сбоя между source_restart и новым вызовом.
   При этом пригодный сохранённый ответ используется до решения о повторном create.
4. Выбор маленького helper вместо большого игрового JS и использование устаревшей
   координаты с чужим hash.
5. Общие изменяемые объекты между возвращаемыми схемами и трактовка неизвестной
   версии как последней. Версия 99 теперь явно отклоняется.
6. Распознавание строковых комментариев при CR/Unicode-переносах без потери настоящего кода.

Дополнительно исправлена локальная идентификация процессов: start/status/stop сравнивают
время запуска в одном TZ=UTC/LC_ALL=C. Загрузка .env больше не делает собственный процесс
«остановленным» из-за часового пояса/локали. Проверка команды и защита от повторного
использования PID сохранены; добавлена регрессия. Проверка свободного порта допускает
завершённые соединения TIME_WAIT, но блокирует настоящий listener. Это дополнительно
проверено на реальных локальных TCP-сокетах без внешних соединений.

Финальная проверка: **420 backend-тестов** (419 общим набором и дополнительная регрессия
локальных TCP-сокетов), **23 браузерных сценария** в native sandbox,
Ruff, mypy, Django check и проверка миграций. UI и транспортные права не менялись.
Новых миграций для этого среза нет. Локальный app/preview/worker/beat перезапущен под v5;
GPU-сервер и облачная поставка не изменялись. Новых платных модельных вызовов нет;
закрытый бюджет прежнего пилота не возобновлялся.

## Повтор сохранённых ответов и границы результата

[Машиночитаемое свидетельство](evidence/source-repair-replay-2026-10-24.json) сравнивает
обработку одних и тех же трёх сохранённых ответов Lite. В v4 обе заглушки становились
кандидатами; v5 отклоняет их с incomplete_sources. Полная змейка материализуется в те же
байты, а по её настоящим findings приложение разрешает ремонт game.js. Её известная
игровая ошибка этим повтором не исправляется и не принимается.

Это подтверждает устранение тупика процесса, но не измеряет вероятность того, что
следующий ответ 27B будет качественным. Нового живого сравнения нет. Генерация ещё
одношаговая; runtime, AST-ремонт и двухшаговый Lite не включены. Дальнейшее уменьшение
единого ответа «замысел + код + сценарии» и измерение его эффекта остаются следующей работой.

## Исправления после дополнительного ревью — 24.10.2026

Дополнительное ревью обнаружило три воспроизводимых дефекта на границе этапов B/D:
после recheck терялось требование подтвердить неизвестный расход, уже полученный ответ
становился недоступным следующему продолжению, а одинаковая ошибка в другом модуле
ошибочно останавливала ремонт как `no_progress`.

Общий модуль `studio/continuations.py` восстанавливает цепочку только внутри одного чата.
Неизвестные вызовы учитываются через любое число промежуточных recheck. Новое явное
подтверждение сохраняет список конкретных Invocation ID в `explicit_retry`; оно не
сбрасывается при следующей проверке и не покрывает другую неопределённую попытку.
Старые события подтверждения сохраняют прежний смысл — вызовы указанного родителя.
API и доступные пользователю действия используют одну интерпретацию. Перед резервом
worker повторяет проверку; ожидающий ответ предка также не разрешает второй inference.
Для допуска используется один снимок доставки: переход sent → unknown не может
проскочить между проверкой неизвестного исхода и проверкой незавершённого вызова.
Финансовые записи и неизвестные суммы при этом не списываются и не обнуляются.

Поиск готового ответа идёт от ближайшего запуска к предкам, строго для текущей базы.
Recheck по-прежнему проверяет только исходный кандидат. Последующее явное продолжение
сначала применяет пригодный сохранённый ответ, включая поздний receipt; новый вызов
для этого не нужен. `source_restart` остаётся сохраняемой границей поиска старых ответов.
Ответ к другой базе не применяется. Сбой перед сохранением кандидата восстанавливает
тот же ответ без нового inference; отменённый предок не получает права менять новый Run.

Обнаружение повторного дефекта теперь учитывает подтверждённые путь/строку/столбец,
а при недоступной карте исходников — номер скрипта и координаты компилятора.
Исправление первого JS-модуля и обнаружение такой же ошибки во втором является
прогрессом. Одинаковая ошибка в прежнем месте и повторный неудачный игровой эффект
по-прежнему останавливают автоматические вызовы в сохранённом общем лимите.

Все три исходных воспроизведения проходят после исправления. Добавлены регрессии
HTTP → recheck → continue, нескольких recheck, старых/новых подтверждений, позднего
ответа, неизвестного исхода при ожидании в очереди, незавершённой отправки, другой базы
и аварии при применении ответа предка. Сквозной тест с настоящим generation service,
тестовым provider и изолированным Chromium исправляет `helper.js`, затем `game.js`
и автоматически принимает игру после реальных сценариев ввода. Это не живой inference.

Новых миграций и изменений адаптера Codex нет. GPU-сервер и облачная поставка не затронуты;
закрытый бюджет модельного пилота не возобновлялся.

Финальные проверки после повторного ревью: **438 backend-тестов** без browser/live,
**24 браузерных сценария** в native sandbox, **75 тестов интерфейса**, ESLint/Prettier,
TypeScript/production build, Ruff, mypy (generation/validation), Django check и отсутствие
новых миграций. Повторное ревью закрыло все три исходных замечания; дополнительно
проверены границы старого согласия, позднего receipt, исходной базы и очереди worker.
Новых блокирующих замечаний в проверенном объёме не выявлено. Результат относится
к процессу приложения и тестовым играм, не к свежему качеству 27B/Codex или физическому WebView.
Локальные app/preview/worker/beat обновлены после проверки отсутствия активных генераций;
все четыре процесса работают, HTTP health приложения возвращает 200.
