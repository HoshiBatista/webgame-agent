# Генерация мини-игр

`service.generate` делает **один** запрос к выбранному провайдеру. Решение об одной
автоправке, продолжении, отмене и сохранении результата принимает Django orchestration.
Модуль не подключает Django и не содержит каталог игровых шаблонов. `fake` — явно
помеченная тестовая сцена; использовать её как доказательство живой генерации нельзя.
`prompts.py` собирает стабильное общее ядро, правила проверок и инструкции только
для выбранной операции. `create` получает требования к полным исходникам;
`edit`/`repair` — правила точных патчей, затем соответственно изменение по запросу
или исправление без ослабления требований. `build_messages` используется обоими
адаптерами. Журнал сохраняет hash инструкций выбранной операции и отдельный hash
схемы ответа; vLLM без schema-режима дополнительно получает эту схему в тексте.
Компактность означает отсутствие лишних подсистем и объяснений: все запрошенные
механики, оформление, управление, исход и повторный раунд должны быть реализованы.
Промежуточная usage при обрыве или отмене до финального маркера — диагностические данные,
а не окончательный расход. Адаптер возвращает `outcome_unknown=True`; backend сохраняет
полный резерв как неизвестный до окончательного receipt. Известный отказ до отправки
не расходует резерв. У vLLM поток без `[DONE]` не считается завершённым даже при наличии
готового текста и промежуточной usage.

`schema.py` — единственный контракт ответа и браузерных сценариев. `materialize`
проверяет точную базовую версию и SHA256 каждого исходника, применяет непересекающиеся
точные замены атомарно, наследует предыдущие проверяемые эффекты, собирает автономный HTML.
Скачивание, preview и публикация должны использовать возвращённые байты `html`.
Отдельные JSON-настройки/уровни встраиваются через `<script type="application/json"
src="levels.json" id="levels"></script>`; игра читает textContent, а не делает fetch.
Добавление уровней может менять только JSON, сохраняя JS побайтово.

`status=ok` при правке должен менять итоговые исходники или проверки. Пустой патч,
замена текста самим собой, перестановка одинаковых сценариев, изменение только сообщения,
названия или карточки игры не считаются реализованной доработкой: `no_changes` допускает
одну обычную автоправку. Это проверка фактических изменений, без эвристик по тексту запроса.
Если запрос уже реализован, модель возвращает `status=unchanged`, объяснение, точный
`base_revision` и пустые files/patches/checks. `materialize` проверяет базу и возвращает
`{status: "unchanged", message}`; backend показывает нейтральный результат, сохраняя игру
без новой версии, браузерной проверки и автоматического модельного повтора.

## Проверки

Каждый сценарий имеет `id`, `category`, `requirement`, `viewport`, `steps`, `observation`
и `expect`. Категории: `start`, `control`, `outcome`, `restart`, `regression`; первые три обязательны.
Обычный ориентир — 4–6 содержательных сценариев; максимум 12 разрешён для нужного
покрытия. Это не новый жёсткий лимит: сокращать обязательные эффекты и унаследованные
регрессии ради количества запрещено. Требуются мобильный `start` и мобильный `control`
с касанием без клавиатуры. Для повтора используется `restart` с реальным вводом.
Проверка не навязывает названий кнопок или полей игры. В пользовательской доработке `edit`
можно обновить условие и категорию существующего ID, если пользователь меняет механику.
В автоматической коррекции `repair` уже сохранённого кандидата категория и формулировка
эффекта неизменны; ошибочные действия/наблюдения можно исправить. Вид операции берётся
из сохранённого запроса приложения и обязательно передаётся в `materialize(operation=...)`.
Модель не может объявить `edit` вместо `repair`, чтобы ослабить проверки.
До первого успешно материализованного кандидата повтор сохраняет исходный вид операции:
`create` без базы либо `edit` существующей игры; диагностические findings передаются отдельно.
Создание возвращает полный набор. Правка возвращает только новые/изменённые сценарии;
пропущенные автоматически наследуются, косметическая правка может вернуть `checks=[]`.
После объединения обязательны все три категории, уникальные ID и максимум 12 сценариев.

Сценарий начинается с чистой страницы. Действия: `click`/`tap` с selector и/или x/y
(CSS-пиксели относительно отображаемого selector либо viewport, не доли 0–1), `press`, `key_down`, `key_up`, `wait`,
`blur`. У pointer-действия все поля `selector`, `x`, `y` обязательны, ненужные — null.
Для центра кнопки указываются selector и x=y=null. Координаты Canvas рассчитываются
для отображаемого размера при заданном viewport, с учётом масштаба внутренних координат.
Для адаптивных сцен удобнее `click_fraction`/`tap_fraction`: обязательный selector и x/y
в диапазоне [0,1]. Исполнитель сам измеряет CSS-прямоугольник и отправляет настоящий ввод.
Обычные click/tap сохраняют единицы CSS-пикселей; дробные значения не угадываются.
Наблюдение: `text`+selector, `attribute`+selector+attribute, `state`+path (чтение window).
Снимок состояния читает только собственные поля с данными: ни вложенные getters,
ни `toJSON`, ни функции не вызываются. Допускаются JSON-значения, массивы и обычные объекты;
циклы, глубина свыше 12, более 512 значений или данные сверх 8 КиБ дают недоступное
наблюдение вместо изменения игры во время проверки. Это не обещание защиты от намеренно
враждебных Proxy или переопределения встроенных функций самой игрой.
Каждый сегмент state-пути должен быть собственным обычным полем объекта: getter,
унаследованные свойства и вызовы функций не выполняются. Доступный на window простой
объект — необязательная альтернатива DOM-наблюдениям; имена и форма состояния свободны.
Оператор `changed`/`increased`/`decreased` сравнивает до всех действий и после них;
`eq`/`not_eq`/`contains` сравнивает итог с value, `visible` проверяет видимость элемента.
Ненужное value — null. Максимум 30 действий и суммарно 10 секунд ожиданий на сценарий
ограничивает размер короткой приёмки, а не длительность генерации. Непроверенный
долгий исход показывается человеку, не объявляется успешным автоматически.

## Codex

Установленный `codex app-server` использует существующий локальный пользовательский
вход. Один ephemeral thread/turn, `environments: []`, пустые runtime roots/dynamic tools,
отдельная временная папка. Авторизация не копируется. Временный каталог моделей содержит
только несекретные метаданные реального каталога; shell/apply_patch/прочие инструменты
отключены в метаданных и feature flags. Эффективные MCP-серверы выключаются явно.
Процесс не наследует переменные БД, API-ключи приложения или ключ vLLM. После завершения
соединение закрывается; скрытых повторов транспорта нет.
Глобальные developer instructions оператора не добавляются. Фоновая и послеходовая
compaction выключены. Точные messages + JSON schema допускаются до **256 000 UTF-8 байт**:
превышение отклоняется до открытия модельного соединения без обрезания исходников.
Профиль фиксирует context window 872 000 и auto-compaction threshold 800 000 токенов;
этот порог выше допустимого входа, максимального выхода 128 000 и служебного запаса.
Политика предотвращает случайную локальную compaction из пользовательской конфигурации;
она не измеряет внутренние inference серверной модели.

Профиль проверен для `codex-cli 0.163.0-alpha.10.2`. При другой версии адаптер отказывает
**до вызова модели**: команда должна проверить сохранение границы инструментов и обновить
профиль. Это проверка безопасности актуального интерфейса, не поддержка старых проектов.
Выбор модели берётся из реального `models_cache.json`. По умолчанию gpt-6-luna, low,
стандартный tier. Профиль использует отдельное имя провайдера `gameforge_codex` с
`requires_openai_auth`, потому что установленный CLI запрещает переопределять built-in
openai; пользовательские credentials остаются в Codex.

## API локальной модели

Настройки оператора: `GAMEFORGE_VLLM_URL` (с `/v1`), `GAMEFORGE_VLLM_MODEL`, необязательный
`GAMEFORGE_VLLM_API_KEY`, `GAMEFORGE_VLLM_JSON_MODE=json_object|json_schema|none`,
`GAMEFORGE_VLLM_STREAM=true|false`. `/models` доступен через read-only `probe()`.
Не предполагается наличие Responses API, tool calls, vision или конкретного chat template.
Каждый запрос получает `execution_limits` из настроек сервера: проверенный предел контекста
и `max_output_tokens`. Последний передаётся API как `max_tokens`; слишком большой вход
отклоняется до отправки (консервативная оценка по UTF-8 и запас на chat template).
Политика 60 секунд без сетевых данных — inactivity transport guard, не deadline запроса
с прогрессом. Повтор после неизвестного результата автоматически не отправляется.

Живой vLLM пока не испытан: тесты проверяют локальный HTTP-протокол, не качество модели.
Отсутствующий usage остаётся `None`; он никогда не превращается в нулевую стоимость.
`GenerationError` сохраняет code/message/usage/outcome_unknown/raw_response.
Идентификатор вызова провайдера сохраняется в provider_metadata и на успешном ответе,
и на ошибке, если он уже получен (Codex thread/turn, API request ID).
Полный ответ, даже пришедший после отмены, передаётся backend для учёта; fence запрещает применять
его к отменённому заданию. Полные исходники и ответы доступны только в приватной диагностике.

Источник профиля провайдера: [официальный код Codex](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs): `to_api_provider` выбирает endpoint по режиму сохранённой авторизации, а не имени alias.

Резерв — верхняя оценка ответственности одного вызова, не расход: `estimate_reservation`
учитывает худшую цену входа/записи кеша и официальный максимум выхода. Для произвольного
платного API оператор задаёт `context_window`, `max_output_tokens` и максимальные тарифные
множители. Использование неучтённого автоматического повтора в адаптере запрещено.
